# Угрозы информации и анализ сетевого трафика в консоли с TShark

*Полная версия: пошаговая практика, заполненные таблицы, ответы и подробные объяснения.*

> **Как пользоваться решением:** `scanme.nmap.org` — живой публичный узел. IP-адрес, задержки, число пакетов и HTTP-код могут меняться. Поэтому в экспериментальных таблицах используются обозначения вида `<IP из вашего захвата>` и `<кадр N>`. Это не «неполный ответ», а правильный способ не подменять реальные данные выдуманными. Фиксированными являются логика протоколов, признаки и метод анализа.

> **Главная идея:** вся работа выполняется **только в терминале**. Графический интерфейс Wireshark не используется. Для захвата и анализа применяется **TShark** — консольная версия анализатора протоколов из семейства Wireshark. Учебный сетевой обмен создаётся только вашим компьютером при обращении к `scanme.nmap.org`.

---

# 0. Что именно мы будем делать

В этой работе вы не будете «ломать» удалённый сервер и не будете выполнять эксплуатацию уязвимостей. Вы создадите небольшой обычный сетевой обмен и разберёте его как технический след.

Практика состоит из последовательности:

```text
доменное имя
    ↓
DNS-запрос и DNS-ответ
    ↓
IP-адрес удалённого узла
    ↓
TCP-соединение
    ↓
HTTP-запрос и HTTP-ответ
    ↓
анализ конфиденциальности, целостности и доступности
```

Мы используем:

- `tshark` — захват и разбор пакетов;
- `capinfos` — краткая информация о файле захвата;
- `curl` — создание обычного HTTP-запроса;
- `nslookup` — создание и просмотр DNS-запроса;
- `scanme.nmap.org` — публичный учебный узел проекта Nmap.

> **Важно:** Nmap в этой работе не нужен. Название `scanme.nmap.org` не означает, что его обязательно надо сканировать. Здесь узел используется только как понятная публичная учебная цель для обычного DNS- и HTTP-обмена.

# 1. Что такое Wireshark и TShark

## 1.1. Wireshark

Wireshark — анализатор сетевых протоколов. Он умеет получать сетевые пакеты с интерфейса, сохранять их в файл и разбирать структуру протоколов.

Обычный Wireshark имеет графический интерфейс. Для этой практики он не нужен.

## 1.2. TShark

**TShark** — терминальная версия Wireshark.

Простыми словами:

- Wireshark показывает пакеты в окнах и таблицах;
- TShark показывает те же данные текстом в терминале;
- оба используют общий механизм разбора сетевых протоколов;
- TShark удобно использовать на сервере, в WSL, по SSH и в автоматизированных сценариях.

В этой работе команда:

```bash
tshark
```

является основным инструментом.

## 1.3. Что такое Dumpcap

В состав набора Wireshark также входит `dumpcap`.

`dumpcap` — специализированная утилита захвата пакетов. На Linux права на захват обычно выдаются именно ей, чтобы не запускать весь анализатор от имени `root`.

Для новичка достаточно запомнить:

> **TShark анализирует, а низкоуровневый захват при необходимости выполняется через механизм dumpcap.**

Поэтому правильнее настроить права захвата один раз, чем постоянно писать `sudo tshark`.

## 1.4. Что такое PCAP и PCAPNG и почему это важно

Во время захвата TShark не просто печатает строки на экран. Он может сохранить **копии наблюдаемых сетевых кадров** в специальный файл захвата.

В разговорной речи такие файлы часто называют **PCAP** — от *packet capture*, то есть «захват пакетов». При этом технически существуют разные форматы файлов:

- **PCAP** — более старый и простой формат захвата;
- **PCAPNG** (*PCAP Next Generation*) — более современный формат, который умеет хранить не только сами захваченные кадры, но и дополнительные сведения о захвате и интерфейсах;
- в этой работе используется файл `scanme_console.pcapng`, то есть именно **PCAPNG**.

Для новичка удобно запомнить так:

```text
сетевой обмен
    ↓
TShark наблюдает кадры на интерфейсе
    ↓
кадры и служебные сведения записываются в .pcapng
    ↓
этот же файл позже можно разбирать много раз
```

> **Почему файл захвата является информационным активом:** в нём могут оказаться IP-адреса, внутренние доменные имена, номера портов, время соединений, используемые протоколы и, если протокол не шифрует содержимое, сами передаваемые данные. Поэтому `.pcap`/`.pcapng` нельзя воспринимать как «безопасный технический мусор». Это самостоятельный набор сведений о работе сети.

Даже если в учебном задании мы создаём только безопасный тестовый обмен, правило остаётся тем же: **захватывать нужно только необходимое и передавать файл другим людям только после проверки его содержимого**.

# 2. Установка: только консольный режим

## 2.1. Arch Linux / Manjaro и системы на базе Arch

Для этой работы **не нужен** пакет `wireshark-qt`.

Установите консольный пакет:

```bash
sudo pacman -S wireshark-cli
```

Это важный момент: пакет `wireshark-cli` содержит TShark и другие консольные утилиты Wireshark без Qt-интерфейса.

Для создания тестового трафика также понадобятся `curl` и `nslookup`. В Arch `nslookup` входит в пакет `bind`:

```bash
sudo pacman -S curl bind
```

### Разрешение обычному пользователю выполнять захват

Пакет `wireshark-cli` использует группу `wireshark`. Добавьте в неё своего пользователя:

```bash
sudo usermod -aG wireshark "$USER"
```

После этого **выйдите из пользовательского сеанса и войдите снова**. Простое открытие ещё одного терминала может не обновить список групп текущего пользователя.

Проверка членства в группах:

```bash
groups
```

В списке должна появиться группа:

```text
wireshark
```

Проверка TShark:

```bash
tshark --version
```

Проверка доступных интерфейсов:

```bash
tshark -D
```

Если `tshark -D` выводит список интерфейсов, базовая установка готова.

> **Не запускайте TShark через `sudo` без необходимости.** Для учебной системы правильнее настроить права `dumpcap`/группу `wireshark`, чем выполнять весь анализатор с максимальными привилегиями.

## 2.2. Ubuntu / Debian / Linux Mint

Установите именно консольный анализатор:

```bash
sudo apt update
sudo apt install tshark curl dnsutils
```

Здесь:

- `tshark` — консольный анализатор;
- `curl` — HTTP-клиент;
- `dnsutils` — содержит `nslookup` и `dig`.

Во время установки может появиться вопрос о возможности захвата пакетов обычными пользователями. Для учебного компьютера можно разрешить такой режим.

Если вопрос не появился, настройку можно вызвать повторно:

```bash
sudo dpkg-reconfigure wireshark-common
```

Затем добавьте пользователя в группу:

```bash
sudo usermod -aG wireshark "$USER"
```

После этого выйдите из пользовательского сеанса и войдите снова.

Проверка:

```bash
tshark --version
```

```bash
tshark -D
```

Если список интерфейсов отображается, переходите к практике.

## 2.4. Windows — PowerShell, без запуска графического Wireshark

В Windows официальный дистрибутив Wireshark включает TShark. Отдельный официальный «только TShark» установщик обычно не требуется.

Откройте PowerShell.

Установить пакет через Windows Package Manager можно командой:

```powershell
winget install -e --id WiresharkFoundation.Wireshark
```

Во время установки убедитесь, что установлен **Npcap**. Это драйвер захвата пакетов для Windows.

После установки **графическую программу запускать не нужно**.

Проверка через полный путь:

```powershell
& 'C:\Program Files\Wireshark\tshark.exe' --version
```

Список интерфейсов:

```powershell
& 'C:\Program Files\Wireshark\tshark.exe' -D
```

Если команда `tshark` уже доступна в `PATH`, можно писать короче:

```powershell
tshark --version
```

Если PowerShell отвечает, что `tshark` не найден, это не означает, что программа не установлена. Используйте полный путь:

```text
C:\Program Files\Wireshark\tshark.exe
```

### Как выполнять дальнейшие команды в Windows

В инструкции ниже команды записаны как:

```bash
tshark ...
```

Если `tshark` не находится автоматически, заменяйте начало команды на:

```powershell
& 'C:\Program Files\Wireshark\tshark.exe' ...
```

Например:

```powershell
& 'C:\Program Files\Wireshark\tshark.exe' -D
```

## 2.5. WSL — отдельно от обычной Windows

WSL — это Linux-среда внутри Windows. Для этой работы важно не смешивать два разных сетевых контекста.

### Правило для новичка

Если вы запускаете:

```bash
curl
```

внутри WSL, то и захват выполняйте `tshark` **внутри той же WSL-среды**.

Не создавайте трафик браузером Windows, а затем не пытайтесь найти его в WSL-захвате. Это разные сетевые контексты.

Для Ubuntu в WSL:

```bash
sudo apt update
sudo apt install tshark curl dnsutils
```

Если нужно настроить права:

```bash
sudo dpkg-reconfigure wireshark-common
```

```bash
sudo usermod -aG wireshark "$USER"
```

После этого в PowerShell Windows можно полностью остановить WSL:

```powershell
wsl --shutdown
```

Затем снова открыть дистрибутив.

Проверить:

```bash
tshark --version
```

```bash
tshark -D
```

Обычно в WSL 2 среди интерфейсов будет что-то похожее на `eth0`, но ориентируйтесь на **свой фактический вывод**, а не на название из примера.

> Для этой практики WSLg и графические Linux-приложения не нужны вообще.

# 3. Если TShark установлен, но захват не работает

Не переходите сразу к `sudo tshark`.

Сначала выполните:

```bash
tshark -D
```

Возможны три ситуации.

### Ситуация 1. Интерфейсы видны

Например:

```text
1. eth0
2. any
3. lo
```

Это хороший признак. Можно переходить к выбору интерфейса.

### Ситуация 2. Интерфейсы есть, но при захвате ошибка доступа

На Linux проверьте членство в группе:

```bash
groups
```

Если группы `wireshark` нет, повторите настройку пользователя и войдите в систему заново.

### Ситуация 3. На Windows нет нормальных сетевых интерфейсов

Проверьте, установлен ли Npcap. Без него TShark сможет читать готовые `.pcapng`, но живой захват будет ограничен или недоступен.

# 4. Что такое `scanme.nmap.org`

`scanme.nmap.org` — демонстрационный узел проекта Nmap.

В этой работе он нужен для трёх простых вещей:

1. у нас есть заранее известное доменное имя;
2. мы можем выполнить обычное DNS-разрешение имени;
3. мы можем создать обычный HTTP-запрос и затем увидеть его в собственном захвате.

Мы будем обращаться к:

```text
scanme.nmap.org
```

и:

```text
http://scanme.nmap.org/
```

## 4.1. Доменное имя и URL — не одно и то же

`scanme.nmap.org` — доменное имя.

`http://scanme.nmap.org/` — URL.

В URL:

```text
http://        → схема / протокол прикладного уровня
scanme.nmap.org → имя узла
/              → путь к ресурсу
```

## 4.2. Почему используется HTTP

HTTP здесь нужен **только в учебных целях**, чтобы вы увидели, что незашифрованный прикладной протокол может быть читаем в сетевом захвате.

Не отправляйте через HTTP:

- реальные логины;
- пароли;
- токены;
- персональные данные;
- банковскую информацию;
- рабочие документы.

В практической команде мы отправим только обычный запрос к корню сайта.

## 4.3. Что произойдёт, когда мы обратимся к `scanme.nmap.org`

Перед тем как HTTP-клиент сможет отправить запрос к серверу, системе обычно нужно узнать IP-адрес по доменному имени. Здесь появляется **DNS-резолвер**.

**Резолвер** — это компонент DNS, к которому клиент обращается с вопросом «какой IP-адрес соответствует этому имени?». В домашней сети таким адресатом может быть DNS-служба маршрутизатора, DNS-сервер провайдера, корпоративный DNS или публичный рекурсивный DNS-сервис. В самой операционной системе также может быть локальный компонент, который передаёт запрос настроенному резолверу и использует кэш.

Упрощённая последовательность нашей лабораторной работы выглядит так:

```text
nslookup / curl
    ↓
локальная DNS-подсистема
    ↓
настроенный DNS-резолвер
    ↓
DNS-ответ с A-записью (IPv4)
    ↓
клиент получает IP scanme.nmap.org
    ↓
TCP-соединение с этим IP на порт 80
    ↓
HTTP GET /
```

> **Зачем это понимать:** когда вы видите в захвате DNS-пакет, адрес назначения запроса обычно является адресом резолвера, а не адресом `scanme.nmap.org`. Сам IP учебного веб-узла появляется **внутри DNS-ответа**, например в поле `dns.a`.

Поэтому нельзя путать три разных объекта:

1. **ваш клиент** — компьютер, который спрашивает имя;
2. **DNS-резолвер** — система, которая отвечает на DNS-запрос клиента;
3. **веб-сервер `scanme.nmap.org`** — конечный узел, к которому после разрешения имени создаётся TCP/HTTP-соединение.

# 5. Мини-теория по информационной безопасности

## 5.1. Информация при передаче

Информация может:

- храниться;
- обрабатываться;
- передаваться.

В этой работе рассматривается третий вариант — **передача информации по сети**.

При передаче важны не только данные страницы. По сети также идут служебные сведения:

- IP-адреса;
- номера портов;
- DNS-запросы;
- параметры TCP;
- HTTP-заголовки;
- время обмена.

Эти сведения являются частью цифрового следа.

## 5.2. Конфиденциальность

**Конфиденциальность** отвечает на вопрос:

> Кто может увидеть информацию?

Если данные доступны тому, кто не должен их видеть, конфиденциальность нарушается.

Сетевой пример — чтение незашифрованного HTTP-трафика наблюдателем, который имеет техническую возможность видеть этот канал.

## 5.3. Целостность

**Целостность** отвечает на вопрос:

> Можно ли доверять данным и уверены ли мы, что они не были незаметно изменены?

Сетевые примеры риска:

- подмена DNS-ответа;
- изменение содержимого сообщения;
- получение данных от неожиданного источника.

Но важно различать **признак** и **доказательство**. Неожиданный IP-адрес ещё не доказывает DNS-spoofing.

## 5.4. Доступность

**Доступность** отвечает на вопрос:

> Можно ли воспользоваться информацией или сервисом тогда, когда это требуется?

Сетевые признаки возможной проблемы доступности:

- сервер не отвечает;
- SYN отправляется повторно;
- соединение обрывается;
- DNS-запросы остаются без ответа;
- запросы выполняются с большой задержкой.

Повторный SYN сам по себе не доказывает DoS/DDoS. Причиной может быть сеть, межсетевой экран, перегрузка, ошибка маршрутизации или временная недоступность сервиса.

## 5.5. Подлинность

**Подлинность** связана с вопросом:

> Действительно ли источник является тем, за кого себя выдаёт?

IP-адрес — технический идентификатор сетевого узла, а не доказательство личности человека.

## 5.6. Угроза, уязвимость, риск и инцидент

| Термин | Простое объяснение |
|---|---|
| Угроза | То, что потенциально может нарушить безопасность |
| Уязвимость | Слабое место, которое делает реализацию угрозы возможной |
| Риск | Вероятность реализации угрозы вместе с тяжестью возможных последствий |
| Событие | Зафиксированный технический факт |
| Инцидент | Событие или цепочка событий, которые реально затронули безопасность и требуют реакции |

Удобная учебная связка:

```text
ценный актив + угроза + уязвимость → риск
```

## 5.7. Классификация угроз

В работе угрозы будем рассматривать минимум по четырём признакам:

| Признак | Варианты |
|---|---|
| Источник | внутренний / внешний / не установлен |
| Намеренность | преднамеренная / непреднамеренная / не установлена |
| Что затрагивается | конфиденциальность / целостность / доступность |
| Возможный масштаб | отдельный узел / сегмент / сервис / процесс |

> Если данных недостаточно, ответ **«не установлено»** лучше необоснованной догадки.

## 5.8. Белла — ЛаПадула и Биба — только смысл

Для этой практики модели не нужно рассчитывать математически.

Достаточно понимать различие:

- **Белла — ЛаПадула** помогает мыслить о конфиденциальности: кто может читать сведения и куда их допустимо передавать;
- **Биба** помогает мыслить о целостности: кто может изменять данные и каким источникам можно доверять.

Связь с нашей практикой:

- читаемый HTTP-поток заставляет думать о конфиденциальности;
- неожиданный источник DNS-данных заставляет думать о целостности и доверии к источнику.

# 6. Мини-теория по сети для новичка

## 6.1. Сетевой интерфейс

Сетевой интерфейс — точка, через которую система отправляет и принимает сетевой трафик.

Примеры:

- Ethernet;
- Wi-Fi;
- виртуальный интерфейс WSL;
- VPN-интерфейс;
- loopback.

TShark показывает список интерфейсов командой:

```bash
tshark -D
```

Для захвата нужно выбрать интерфейс, через который идёт именно ваш тестовый трафик.

## 6.2. IP-адрес

IP-адрес используется для доставки пакетов между узлами IP-сети.

Пример:

```text
192.0.2.10
```

Не запоминайте IP `scanme.nmap.org` из чужого отчёта. Получите фактический адрес в своём DNS-захвате.

## 6.3. Порт

Порт помогает определить сетевую службу внутри узла.

Например:

- DNS часто использует порт `53`;
- HTTP обычно использует TCP-порт `80`;
- HTTPS обычно использует TCP-порт `443`.

Порт — это не «дырка» сам по себе. Это числовой идентификатор точки взаимодействия транспортного уровня.

## 6.4. DNS

DNS преобразует доменное имя в IP-адрес.

Упрощённо:

```text
Клиент: какой IP у scanme.nmap.org?
DNS: вот адрес, который соответствует этому имени.
```

В захвате нас будут интересовать:

- имя запроса;
- запрос или ответ;
- адрес DNS-сервера;
- полученный A/AAAA-адрес.

### Что такое DNS-резолвер — подробнее

Слово **resolver / резолвер** означает «разрешатель имени». Его задача — помочь клиенту получить нужную DNS-информацию.

Пример:

```text
Человек вводит: scanme.nmap.org
Приложению нужен: IP-адрес
Резолвер получает DNS-вопрос и возвращает ответ
```

В типичном сценарии клиент не обязан самостоятельно обходить все DNS-серверы Интернета. Он отправляет запрос настроенному **рекурсивному резолверу**, а тот при необходимости получает сведения из DNS-иерархии, использует кэш и возвращает итоговый ответ клиенту.

В нашей работе важно различать:

- **DNS query** — вопрос клиента;
- **DNS response** — ответ;
- **A-запись** — IPv4-адрес;
- **AAAA-запись** — IPv6-адрес;
- **TTL** — время, в течение которого DNS-ответ разрешено хранить в кэше;
- **кэш DNS** — временно сохранённый результат предыдущего разрешения имени;
- **резолвер** — система, которая обслуживает запрос клиента.

> Если два DNS-запроса дали разные IP, это ещё не означает атаку: могут измениться кэш, набор A-записей, балансировка, CDN или инфраструктура сервиса. Поэтому сетевой факт сначала фиксируют, а причину устанавливают отдельно.


## 6.5. TCP

TCP создаёт логическое соединение между двумя конечными точками.

Начало типичного TCP-соединения:

```text
клиент → сервер : SYN
сервер → клиент : SYN, ACK
клиент → сервер : ACK
```

Это называется **трёхэтапным рукопожатием TCP**.

### TCP — подробнее: что это и зачем он нужен

**TCP (Transmission Control Protocol)** — транспортный протокол, задача которого состоит в передаче потока байтов между двумя конечными точками с контролем порядка и доставки.

В этой лабораторной работе TCP нужен потому, что обычный HTTP-запрос к порту `80` передаётся поверх TCP.

Конечную точку TCP удобно представить как пару:

```text
IP-адрес + TCP-порт
```

Например:

```text
клиент:<временный порт>  →  сервер:80
```

Клиентский порт обычно выбирается операционной системой временно. Серверный порт `80` известен заранее как стандартный порт обычного HTTP.

Перед передачей HTTP TCP устанавливает состояние соединения:

1. **SYN** — клиент просит начать соединение;
2. **SYN,ACK** — сервер сообщает, что получил запрос и тоже готов установить соединение;
3. **ACK** — клиент подтверждает ответ сервера.

После этого TCP:

- нумерует данные;
- позволяет обнаруживать потери;
- повторно передаёт часть данных при необходимости;
- восстанавливает правильный порядок байтов для приложения.

> **Важно:** надёжная доставка не равна защищённой доставке. TCP сам по себе **не шифрует** прикладные данные. Поэтому HTTP поверх TCP может оставаться читаемым, а HTTPS добавляет криптографическую защиту TLS.


## 6.6. HTTP

HTTP — прикладной протокол обмена веб-запросами и ответами.

Пример запроса:

```text
GET / HTTP/1.1
Host: scanme.nmap.org
```

HTTP без TLS не обеспечивает криптографическую конфиденциальность содержимого.

### Как HTTP связан с TCP и почему в работе используется `curl`

HTTP относится к **прикладному уровню**: он описывает смысл веб-обмена — метод запроса, имя узла, путь к ресурсу, заголовки и ответ сервера.

Но HTTP не доставляет IP-пакеты самостоятельно. В нашем сценарии стек выглядит так:

```text
HTTP — что именно просит веб-клиент
  ↓
TCP — надёжный транспорт потока байтов
  ↓
IP — доставка между сетевыми адресами
  ↓
канальный уровень — передача по конкретному интерфейсу
```

Команда `curl` выступает в роли простого консольного веб-клиента. Она удобна тем, что создаёт предсказуемый запрос без графического браузера и позволяет увидеть технические детали соединения через ключ `-v`.

**HTTP** и **HTTPS** — не одно и то же:

- HTTP в рассматриваемом сценарии передаёт прикладной текст без TLS;
- HTTPS — это HTTP, работающий через защищённое TLS-соединение;
- TCP используется и там, и там в классическом HTTP/1.1/HTTP/2-сценарии, но шифрование обеспечивает не TCP, а TLS.


## 6.7. Пакет, кадр и сегмент

Для первого занятия можно использовать слово «пакет» как общее, но полезно понимать уровни:

```text
кадр канального уровня
  └─ IP-пакет
      └─ TCP-сегмент
          └─ HTTP-данные
```

Один сетевой обмен содержит несколько вложенных протокольных уровней.

### Как эти уровни попадают в файл захвата

Когда TShark записывает трафик, в одном захваченном кадре можно увидеть вложенные данные нескольких уровней. Поэтому одна строка анализа может одновременно содержать:

- адрес канального уровня;
- IP источника и назначения;
- TCP-порты и флаги;
- HTTP-поля.

Файл `.pcapng` хранит наблюдаемые кадры, а TShark позже «разбирает» их и показывает отдельные протокольные поля.

Удобная мыслительная модель:

```text
PCAPNG = сохранённый технический след
TShark -r = повторно открыть след
-Y = выбрать интересующие пакеты
-T fields / -e = вывести только нужные поля
```

Именно поэтому файл захвата ценен для анализа: сетевой обмен уже закончился, но его наблюдаемые признаки остаются в сохранённом артефакте.

# 7. Основные ключи TShark, которые встретятся в работе

| Ключ | Что означает |
|---|---|
| `-D` | показать доступные интерфейсы |
| `-i N` | захватывать с интерфейса номер N |
| `-f '...'` | применить **capture filter** во время захвата |
| `-a duration:45` | остановить захват автоматически через 45 секунд |
| `-w file.pcapng` | записать пакеты в файл |
| `-r file.pcapng` | прочитать уже сохранённый файл |
| `-Y '...'` | применить **display filter** при анализе |
| `-T fields` | выводить выбранные поля, а не полное описание |
| `-e field.name` | добавить конкретное поле в вывод |
| `-E header=y` | вывести заголовки полей |
| `-V` | показать подробное дерево разбора пакета текстом |
| `-q -z follow,tcp,ascii,N` | собрать содержимое TCP-потока N в консоли |

## 7.1. Capture filter и display filter

Это разные фильтры.

### Capture filter

Применяется **до записи пакетов**:

```bash
-f "udp port 53 or tcp port 53 or tcp port 80"
```

Ненужные пакеты вообще не попадут в файл.

### Display filter

Применяется **после захвата**:

```bash
-Y 'dns'
```

или:

```bash
-Y 'http.request'
```

Пакеты остаются в файле, но TShark показывает только подходящие.

> В этой работе capture filter используется ещё и как мера минимизации данных: мы не хотим случайно записывать весь трафик компьютера.

### Как не путать два вида фильтров

Для новичка полезно представить процесс как две двери.

**Первая дверь — capture filter.** Она стоит **до файла захвата**:

```text
сеть → capture filter → PCAPNG
```

Если пакет не прошёл эту дверь, его в файле вообще не будет. В TShark такой фильтр задаётся ключом `-f` и использует синтаксис захвата libpcap/BPF.

Пример из работы:

```bash
-f "udp port 53 or tcp port 53 or tcp port 80"
```

Он означает: «сохраняй DNS по UDP/TCP 53 и TCP-трафик порта 80».

**Вторая дверь — display filter.** Она применяется уже к сохранённому файлу:

```text
PCAPNG → display filter → строки, которые видит аналитик
```

Пример:

```bash
-Y 'dns.qry.name == "scanme.nmap.org"'
```

Он ничего не удаляет из `scanme_console.pcapng`; TShark просто показывает только подходящие пакеты.

> **Почему capture filter важен для безопасности:** если вы заранее не записали лишний трафик, его нельзя случайно раскрыть позже. Это техническая реализация принципа минимизации данных.

> **Почему мы не пишем capture filter вида `host scanme.nmap.org`:** до DNS-разрешения клиент ещё должен обратиться к своему DNS-резолверу, а DNS-пакет идёт между клиентом и резолвером, а не между клиентом и веб-сервером `scanme.nmap.org`. Поэтому в учебной команде фильтрация сделана по нужным портам.

## Решение этапа 1


### Пример: что конкретно должно получиться

Допустим, `tshark -D` напечатал:

```text
1. eth0
2. any
3. lo
```

Это **пример формы вывода**, а не значения, которые нужно копировать.

Как его читать:

```text
1. eth0   ← интерфейс с номером 1; в WSL/Linux это может быть основной сетевой интерфейс
2. any    ← псевдоинтерфейс захвата с нескольких Linux-интерфейсов; для нашей работы лучше понимать конкретную точку захвата
3. lo     ← loopback; трафик к внешнему scanme.nmap.org обычно идёт не через него
```

Если после проверки маршрута выяснилось, что тестовый обмен проходит через `eth0`, в отчёт попадёт примерно такая логика:

```text
ОС: Ubuntu в WSL 2
TShark: <фактическая версия>
Интерфейс: 1 / eth0
Почему выбран: через eth0 проходит внешний трафик curl/nslookup
```

> **Что проверяет преподаватель:** студент не угадал номер интерфейса, а получил его из `tshark -D` и может объяснить, почему именно через эту точку должен проходить тестовый обмен.

### Заполненная таблица 1. Среда

| Параметр | Эталонный ответ | Почему именно так |
|---|---|---|
| ОС | `<фактическая ОС студента>` | Это характеристика рабочей среды. Её нельзя угадывать по методичке: команды установки и интерфейсы различаются между Windows, Linux, WSL и macOS. |
| Версия TShark | `<строка из tshark --version>` | Версия берётся из реального вывода программы. Она подтверждает, каким инструментом выполнен анализ. |
| Номер интерфейса | `<номер из tshark -D>` | `-i` принимает номер или имя интерфейса. Правильное значение зависит от конкретного компьютера. |
| Имя интерфейса | `<например eth0 / Wi-Fi / en0>` | Имя помогает другому специалисту понять, где именно выполнялся захват. |
| Почему выбран именно он | `Через него проходит тестовый трафик к scanme.nmap.org` | Мы выбираем интерфейс не по названию, а по функции: он должен видеть именно тот обмен, который генерирует `curl` и `nslookup`. |

### Почему каждая ячейка заполнена именно так

**ОС.** В ответ нельзя автоматически написать «Linux» только потому, что команды в примере похожи на Linux. Студент фиксирует реальную среду. Это влияет на права захвата, имя интерфейса и форму команд.

**Версия TShark.** Это не декоративная строка. Если два студента получили разный формат вывода, версия помогает объяснить различия. Версия должна быть скопирована из `tshark --version`, а не придумана.

**Номер и имя интерфейса.** Это пара значений одного объекта. Номер удобен для команды `-i`, имя удобно для отчёта. На одном компьютере `1` может быть Ethernet, на другом — виртуальный интерфейс.

**Обоснование выбора.** Формулировка «потому что он первый» неверна. Правильный критерий — наличие нужного тестового трафика.

### Ответы на вопросы этапа 1


> **Напоминание о технологии:** этот этап посвящён **сетевому интерфейсу**, TShark и механизму захвата `dumpcap`. TShark может видеть только те кадры, которые доступны выбранной точке захвата. Поэтому правильный интерфейс — это часть методики анализа, а не формальность.

> **Как обосновывать ответы:** связывайте команду с её задачей: `tshark -D` перечисляет точки захвата, `-i` выбирает одну из них, а настройка прав позволяет захватывать без запуска всего анализатора от `root`.

**1. Зачем сначала выполнять `tshark -D`?**  
Команда показывает, какие интерфейсы вообще доступны TShark. Захват всегда выполняется с конкретного интерфейса. Если его не определить, можно начать запись с интерфейса, через который тестовый обмен не проходит.

**2. Почему неправильный интерфейс даёт пустой или бесполезный файл?**  
Пакеты проходят по определённому сетевому пути. Если `curl` отправляет запрос через Wi-Fi, а TShark слушает неиспользуемый Ethernet, нужные пакеты туда не попадут. Файл при этом технически может быть создан, но полезного обмена в нём не будет.

**3. Почему нельзя копировать номер интерфейса из инструкции?**  
Нумерация локальна для конкретной системы. Номер `1` не означает «Wi-Fi» или `eth0` во всех ОС. Поэтому сначала читается `tshark -D`, затем выбирается собственное значение.

**4. Почему не рекомендуется постоянно запускать `sudo tshark`?**  
TShark — большой анализатор протоколов. Давать всему процессу права `root` без необходимости хуже, чем выдать минимальные разрешения специализированному механизму захвата `dumpcap`. На Linux правильная настройка группы `wireshark` уменьшает объём кода, который работает с повышенными привилегиями.

### Дополнительное пояснение к ответам этапа 1

1. **`tshark -D` нужен для инвентаризации точек захвата.** TShark не «видит Интернет целиком»: он получает кадры с конкретного сетевого интерфейса. Поэтому сначала мы узнаём, какие интерфейсы доступны, а уже затем выбираем один через `-i`. Это делает захват воспроизводимым: другой человек понимает, где именно велось наблюдение.
2. **Неправильный интерфейс означает неправильную точку наблюдения.** Если HTTP идёт через Wi-Fi, а захват выполняется на отключённом Ethernet, пакет физически не проходит через выбранную точку. Полученный PCAPNG может быть корректным файлом, но не содержать нужного эксперимента.
3. **Номер интерфейса — локальное значение.** Он формируется на конкретной машине и зависит от ОС, виртуальных адаптеров, VPN, WSL и других сетевых компонентов. Поэтому `1` — это не универсальное обозначение Wi-Fi или Ethernet.
4. **Минимальные привилегии снижают риск.** Для захвата пакетов нужны специальные права, но анализатор протоколов не обязан целиком работать как `root`. Механизм `dumpcap` и группа `wireshark` позволяют отделить привилегированную операцию захвата от обычного анализа.

# 10. Этап 2. Контролируемый захват DNS и HTTP

Работайте с **двумя терминалами**.


### Что происходит на этом этапе — простыми словами

Здесь одновременно работают несколько технологий:

1. **TShark** слушает выбранный сетевой интерфейс.
2. **Capture filter** не позволяет записывать в лабораторный файл всё подряд.
3. **DNS** создаёт обмен с резолвером, когда мы выполняем `nslookup`.
4. **TCP** создаёт соединение к веб-серверу на порт `80`.
5. **HTTP** создаёт прикладной запрос `GET /`.
6. **PCAPNG** сохраняет наблюдаемые кадры, чтобы их можно было разобрать после завершения обмена.

То есть мы не «ищем атаку». Мы специально создаём маленький нормальный сетевой сценарий и учимся читать его технические следы.

## 10.1. Терминал 1 — запустите захват

Подставьте номер своего интерфейса вместо `<N>`:

```bash
tshark -i <N> -f "udp port 53 or tcp port 53 or tcp port 80" -a duration:45 -w scanme_console.pcapng
```

Что означает команда:

- `-i <N>` — выбранный интерфейс;
- `-f ...` — записывать только DNS и TCP/80;
- `-a duration:45` — завершить захват через 45 секунд;
- `-w ...` — сохранить результат в `pcapng`.

После запуска не закрывайте первый терминал.


### Разбор команды захвата буквально по частям

```bash
tshark -i <N> -f "udp port 53 or tcp port 53 or tcp port 80" -a duration:45 -w scanme_console.pcapng
```

- `tshark` — запускает консольный анализатор;
- `-i <N>` — говорит, **где наблюдать трафик**; `<N>` берётся из `tshark -D`;
- `-f "..."` — задаёт **capture filter**, то есть правило отбора **до записи в файл**;
- `udp port 53` — позволяет записать обычный DNS по UDP;
- `tcp port 53` — оставляет возможность увидеть DNS по TCP, если он будет использован;
- `tcp port 80` — записывает TCP-соединение обычного HTTP;
- `-a duration:45` — ограничивает время захвата, чтобы лабораторный файл не рос бесконечно;
- `-w scanme_console.pcapng` — сохраняет результат как файл захвата PCAPNG.

> **Что должно происходить после запуска:** терминал может почти ничего не печатать, потому что при использовании `-w` основная цель — записать кадры в файл. Не закрывайте этот процесс, пока во втором терминале не создадите DNS- и HTTP-трафик.

## 10.2. Терминал 2 — создайте DNS-трафик

Выполните:

```bash
nslookup scanme.nmap.org
```

Смысл команды: вы явно просите DNS разрешить имя `scanme.nmap.org`.


### Что именно делает `nslookup`

`nslookup` — консольная утилита для DNS-запросов. В нашем случае она формирует вопрос о `scanme.nmap.org` и отправляет его DNS-системе, настроенной для вашей среды.

Упрощённо:

```text
nslookup
  ↓
DNS-запрос к резолверу
  ↓
DNS-ответ
  ↓
A-запись с IPv4-адресом
```

В выводе `nslookup` вы можете увидеть адрес DNS-сервера и один или несколько адресов имени. Но для отчёта по захвату важнее подтвердить эти сведения **в самом PCAPNG через TShark**, потому что задача работы — научиться анализировать сетевой след.

## 10.3. Терминал 2 — создайте HTTP-трафик

Linux / WSL / macOS:

```bash
curl -4 -v --max-time 10 http://scanme.nmap.org/ -o /dev/null
```

Windows PowerShell:

```powershell
curl.exe -4 -v --max-time 10 http://scanme.nmap.org/ -o NUL
```

Почему используется `-4`:

- для первого занятия так проще связать DNS A-запись с IPv4-пакетами;
- это уменьшает число вариантов разбора.

Почему используется `-v`:

- `curl` показывает служебную информацию о соединении;
- её можно сопоставить с TShark.

Почему используется `--max-time 10`:

- команда не будет ждать бесконечно, если узел временно недоступен.

Почему ответ отправляется в `/dev/null` или `NUL`:

- содержимое страницы нам не нужно;
- нужен сам сетевой обмен.

Через 45 секунд первый терминал завершит TShark автоматически.

Проверьте, что файл существует.

Linux / WSL / macOS:

```bash
ls -lh scanme_console.pcapng
```

Windows PowerShell:

```bash
capinfos scanme_console.pcapng > 02_capture_info.txt
```

Выведите результат:

### Вопросы к этапу 2

1. Зачем в команде захвата ограничивать трафик портами 53 и 80?
2. Чем такая минимизация полезна с точки зрения конфиденциальности?
3. Почему мы сохраняем сначала `pcapng`, а анализ выполняем после завершения захвата?
4. Что доказывает наличие файла `scanme_console.pcapng`, а чего оно не доказывает?

## Решение этапа 2


### Пример: что конкретно должно получиться

После запуска захвата и выполнения `nslookup` + `curl` должен появиться файл:

```text
scanme_console.pcapng
```

Пример **формы**, а не фиксированных чисел, которые надо копировать:

```text
$ capinfos scanme_console.pcapng
File name:           scanme_console.pcapng
File type:           Wireshark/... - pcapng
Number of packets:   <ненулевое число>
Capture duration:    <около 45 секунд или фактическое значение>
File size:           <фактический размер>
```

Как это комментировать:

- `File type ... pcapng` — файл распознан как файл сетевого захвата;
- `Number of packets` больше нуля — TShark действительно записал какие-то кадры;
- длительность около заданного окна показывает, что автоостановка сработала;
- размер файла у разных студентов будет отличаться — это нормально.

> **Важно:** даже корректный `capinfos` ещё не доказывает наличие нужного DNS/HTTP. Следующий шаг — прочитать содержимое файла TShark и найти конкретные протоколы.

### Что должно получиться

После команды захвата должен существовать файл `scanme_console.pcapng`, а `capinfos` должен показать, что файл распознаётся как корректный захват и содержит ненулевое число пакетов.

Пример логики фиксации результата:

| Параметр | Эталонный ответ |
|---|---|
| Файл | `scanme_console.pcapng` |
| Формат | `pcapng` или формат, который фактически показывает `capinfos` |
| Пакеты | `<фактическое ненулевое количество>` |
| Длительность | `около 45 секунд либо фактическое значение из capinfos` |
| Состав захвата | DNS на 53 и HTTP/TCP на 80 согласно capture filter |

### Объяснение

Файл не обязан иметь одинаковый размер у всех студентов. Даже при одинаковой команде количество DNS-пакетов, повторных передач и служебных TCP-пакетов может различаться. Проверяется не совпадение числа байтов с эталоном, а то, что захват корректно создан и в нём есть нужный обмен.

### Ответы на вопросы этапа 2


> **Напоминание о технологии:** здесь одновременно используются **capture filter**, DNS, TCP, HTTP и файл **PCAPNG**. Capture filter действует до записи и минимизирует данные. PCAPNG сохраняет наблюдаемые кадры, чтобы анализ можно было повторить после завершения обмена.

> **Как обосновывать ответы:** разделяйте «файл создан» и «в файле есть нужный обмен». `capinfos` подтверждает техническую корректность артефакта, а наличие DNS/HTTP подтверждается только последующим разбором пакетов.

**1. Зачем ограничивать трафик портами 53 и 80?**  
Чтобы записывать только то, что относится к учебной задаче: DNS-разрешение и HTTP-соединение. Так файл меньше и его проще анализировать.

**2. Чем это полезно для конфиденциальности?**  
Чем шире захват, тем выше вероятность случайно записать чужие для задачи DNS-имена, внутренние адреса, метаданные приложений или незашифрованный трафик. Минимизация уменьшает объём лишних сведений.

**3. Почему сначала сохраняем PCAPNG, а потом анализируем?**  
Так исходный технический след отделён от интерпретации. Один и тот же файл можно несколько раз анализировать разными фильтрами, не повторяя сетевой обмен. Это повышает воспроизводимость.

**4. Что доказывает наличие файла?**  
Только то, что TShark создал файл захвата. Сам факт существования файла не доказывает, что выбран правильный интерфейс, что внутри есть DNS/HTTP или что произошёл инцидент безопасности. Содержимое ещё нужно проверить.

### Дополнительное пояснение к ответам этапа 2

1. **Порты 53 и 80 выбраны из логики эксперимента.** DNS традиционно использует 53, а обычный HTTP в нашем сценарии — TCP/80. Capture filter не пытается «найти угрозу», а оставляет только протоколы, которые нужны для учебной цепочки DNS → TCP → HTTP.
2. **Минимизация защищает конфиденциальность ещё до анализа.** Если фоновые пакеты не попали в PCAPNG, их нельзя случайно открыть, экспортировать или отправить кому-то позже. Это особенно важно на рабочем ноутбуке, где одновременно могут работать почта, мессенджеры, VPN и корпоративные сервисы.
3. **PCAPNG отделяет наблюдение от интерпретации.** Сначала мы сохраняем исходный технический след, затем многократно применяем к нему display filters и вывод разных полей. Это полезно для проверки: аналитик может повторить разбор без повторного сетевого запроса.
4. **Файл сам по себе доказывает только факт записи.** Наличие `scanme_console.pcapng` не говорит, что в нём есть нужный DNS-ответ, успешный TCP handshake или HTTP GET. Каждый такой факт нужно подтвердить отдельным фильтром и конкретными полями.

# 11. Этап 3. Анализ DNS полностью из консоли


### Напоминание перед анализом DNS

Сейчас мы больше не создаём трафик. Мы читаем уже сохранённый `scanme_console.pcapng`.

Технологическая цепочка этого этапа:

```text
доменное имя → DNS query → резолвер → DNS response → A-запись → IPv4
```

**Резолвер** здесь является DNS-сервисом, которому клиент задал вопрос. Поэтому в запросе адрес назначения — это обычно адрес резолвера. В ответе направления меняются местами, а нужный IP `scanme.nmap.org` находится в данных DNS-ответа (`dns.a`).

Ключ `-r` означает «читать файл захвата», а `-Y` означает «показывать из него только пакеты, подходящие под display filter».

## 11.1. Сначала просто покажите DNS-пакеты

```bash
tshark -r scanme_console.pcapng -Y 'dns'
```

Теперь ограничьте вывод запросами, где встречается нужное имя:

```bash
tshark -r scanme_console.pcapng -Y 'dns.qry.name == "scanme.nmap.org"'
```

## 11.2. Сформируйте компактную таблицу DNS

```bash
tshark -r scanme_console.pcapng \
  -Y 'dns.qry.name == "scanme.nmap.org"' \
  -T fields \
  -E header=y \
  -E separator=, \
  -e frame.number \
  -e frame.time_relative \
  -e ip.src \
  -e ipv6.src \
  -e ip.dst \
  -e ipv6.dst \
  -e dns.flags.response \
  -e dns.qry.name \
  -e dns.a \
  -e dns.aaaa \
  > 03_dns.csv
```

В PowerShell команду можно ввести одной строкой:

```powershell
tshark -r scanme_console.pcapng -Y 'dns.qry.name == "scanme.nmap.org"' -T fields -E header=y -E separator=, -e frame.number -e frame.time_relative -e ip.src -e ipv6.src -e ip.dst -e ipv6.dst -e dns.flags.response -e dns.qry.name -e dns.a -e dns.aaaa > 03_dns.csv
```

## 11.3. Как понимать поля

- `frame.number` — номер пакета внутри файла;
- `frame.time_relative` — время относительно начала захвата;
- `ip.src` / `ipv6.src` — IPv4 или IPv6 отправителя;
- `ip.dst` / `ipv6.dst` — IPv4 или IPv6 получателя;
- `dns.flags.response` — признак запроса/ответа; в текстовом выводе формат может отображаться как `0/1` или `False/True`;
- `dns.qry.name` — запрошенное имя;
- `dns.a` — IPv4-ответ;
- `dns.aaaa` — IPv6-ответ.

### Вопросы к этапу 3

1. Как отличить DNS-запрос от DNS-ответа?
2. Что показывает поле `dns.a`?
3. Почему IP `scanme.nmap.org` нужно брать из собственного захвата, а не из методички?
4. Доказывает ли необычный DNS-ответ факт DNS-spoofing? Почему?
5. Какое свойство информации прежде всего связано с подменой DNS-ответа?

## Решение этапа 3


### Пример: что конкретно должно получиться

После формирования `03_dns.csv` логически ожидается как минимум пара «запрос → ответ». Условный пример с заполнителями:

```text
frame.number,frame.time_relative,ip.src,ipv6.src,ip.dst,ipv6.dst,dns.flags.response,dns.qry.name,dns.a,dns.aaaa
12,1.204,<CLIENT_IP>,,<RESOLVER_IP>,,0,scanme.nmap.org,,
13,1.226,<RESOLVER_IP>,,<CLIENT_IP>,,1,scanme.nmap.org,<IP_SCANME>,
```

Как читать строки:

```text
кадр 12: клиент → резолвер, response=0
          это DNS-вопрос «какой адрес у scanme.nmap.org?»

кадр 13: резолвер → клиент, response=1
          это DNS-ответ; <IP_SCANME> находится в поле dns.a
```

`<CLIENT_IP>`, `<RESOLVER_IP>` и `<IP_SCANME>` нужно заменить **своими фактическими значениями**.

> **Напоминание:** адрес резолвера и адрес веб-сервера — разные сущности. Резолвер отвечает на DNS-вопрос; веб-сервер используется уже после получения IP.

### Заполненная таблица 2. DNS

| Что нужно определить | Эталонный ответ | Почему |
|---|---|---|
| IP вашего клиента | `<IP источника в DNS-запросе>` | В запросе клиент является отправителем, поэтому его адрес читается из `ip.src`. |
| IP/IPv6 DNS-сервера | `<адрес назначения в запросе / источник в ответе>` | Клиент отправляет запрос резолверу, а ответ приходит обратно от него. |
| Имя в запросе | `scanme.nmap.org` | Это имя мы явно передали `nslookup`, и оно должно быть видно в `dns.qry.name`. |
| IPv4-адрес `scanme.nmap.org` | `<значение dns.a из ответа>` | A-запись DNS содержит IPv4-адрес. Фактическое значение может меняться. |
| Был ли ответ DNS | `Да`, если есть строка с `dns.flags.response = 1` | Бит response позволяет отличить ответ от запроса. |
| Сколько времени прошло до ответа | `<разность frame.time_relative ответа и запроса>` | Это наблюдаемая задержка между парой запрос–ответ в конкретном захвате. |

### Подробное объяснение ячеек

**IP клиента.** Берём адрес именно из строки запроса. Если перепутать запрос и ответ, адреса поменяются местами.

**IP DNS-сервера.** Это не IP `scanme.nmap.org`. DNS-сервер — посредник разрешения имени. Он отвечает на вопрос об адресе другого узла.

**Имя запроса.** Поле `dns.qry.name` подтверждает, что найден именно наш учебный запрос, а не фоновый DNS другого приложения.

**IPv4-адрес узла.** Используется `dns.a`, потому что A-запись относится к IPv4. Мы специально запускаем `curl -4`, чтобы дальнейший разбор был проще.

**Наличие ответа.** Истинное значение `dns.flags.response` (`1`/`True`) является явным протокольным признаком ответа DNS.

**Время ответа.** Это не «скорость Интернета вообще», а задержка одной конкретной операции DNS в данном захвате.

### Ответы на вопросы этапа 3


> **Напоминание о технологии:** **DNS** отвечает за разрешение доменного имени, а **резолвер** обслуживает DNS-запрос клиента. Поле `dns.a` содержит IPv4-ответ. DNS-захват показывает технические сообщения, но сам по себе не устанавливает причину необычного результата.

> **Как обосновывать ответы:** сначала укажите, какое поле TShark наблюдается (`dns.flags.response`, `dns.qry.name`, `dns.a`), затем объясните, какой смысл оно имеет в DNS и чего по нему нельзя доказать без дополнительных источников.

**1. Как отличить запрос от ответа?**  
У запроса признак response ложный (`0`/`False`), у ответа — истинный (`1`/`True`). Дополнительно направления IP обычно противоположны.

**2. Что показывает `dns.a`?**  
IPv4-адрес из DNS A-записи. Это результат разрешения доменного имени в IPv4.

**3. Почему IP нельзя брать из методички?**  
DNS-записи могут меняться. Кроме того, задача учит читать собственный технический след. Копирование чужого IP ломает сам смысл анализа.

**4. Необычный DNS-ответ доказывает spoofing?**  
Нет. Другой IP может появиться из-за балансировки, изменения инфраструктуры, нескольких допустимых адресов, кеширования или другой конфигурации резолвера. Для вывода о подмене нужны дополнительные признаки.

**5. Какое свойство связано с подменой DNS?**  
Прежде всего целостность: нас интересует, не было ли значение адреса искажено или подменено. Одновременно затрагивается подлинность источника ответа — доверяем ли мы тому, откуда пришли данные.

### Дополнительное пояснение к ответам этапа 3

1. **Запрос и ответ различаются ролью сообщения.** В DNS поле `dns.flags.response` показывает, является сообщение вопросом или ответом. Это надёжнее, чем угадывать направление только по IP-адресам.
2. **`dns.a` — именно IPv4-результат разрешения имени.** A-запись отвечает на вопрос «какой IPv4 связан с именем?». Для IPv6 используется AAAA, поэтому мы не смешиваем эти два типа данных.
3. **Фактический IP берётся из собственного захвата.** DNS — динамическая система: адреса сервисов могут меняться, а один домен может иметь несколько адресов. Копирование IP из чужого отчёта разрушает смысл практики и может привести к неверной связи DNS и TCP.
4. **Необычный ответ — наблюдение, а не диагноз.** Чтобы доказать DNS-spoofing, нужно установить факт подмены: сравнить источник, авторитетные данные, повторяемость, инфраструктуру резолвера и другие признаки. Один «неожиданный» адрес может быть полностью легитимным.
5. **Подмена DNS прежде всего затрагивает целостность.** Клиент использует ответ как управляющие данные для дальнейшего соединения. Если адрес изменён неправомерно, нарушается правильность информации. Одновременно возникает вопрос подлинности источника ответа.

# 12. Этап 4. Анализ TCP-соединения

HTTP на порту 80 работает поверх TCP, поэтому сначала найдём транспортное соединение.


### Напоминание перед анализом TCP

DNS уже дал клиенту IP-адрес. Теперь веб-клиент должен создать транспортное соединение с этим IP.

В нашем сценарии:

```text
клиент:<временный TCP-порт> → <IP scanme.nmap.org>:80
```

TCP нужен HTTP как транспорт: он устанавливает соединение, следит за порядком байтов и поддерживает повторную передачу. Для первого анализа нас интересует именно **handshake SYN → SYN,ACK → ACK**.

Поле `tcp.stream` — это номер, которым TShark внутри конкретного файла объединяет пакеты одного TCP-разговора. Это не сетевой порт и не глобальный идентификатор Интернета; номер действует только внутри данного захвата.

## 12.1. Выведите TCP-пакеты порта 80

```bash
tshark -r scanme_console.pcapng -Y 'tcp.port == 80'
```

## 12.2. Сохраните компактную таблицу

```bash
tshark -r scanme_console.pcapng \
  -Y 'tcp.port == 80' \
  -T fields \
  -E header=y \
  -E separator=, \
  -e frame.number \
  -e frame.time_relative \
  -e tcp.stream \
  -e ip.src \
  -e tcp.srcport \
  -e ip.dst \
  -e tcp.dstport \
  -e tcp.flags.syn \
  -e tcp.flags.ack \
  -e tcp.len \
  > 04_tcp.csv
```

PowerShell — одной строкой:

```powershell
tshark -r scanme_console.pcapng -Y 'tcp.port == 80' -T fields -E header=y -E separator=, -e frame.number -e frame.time_relative -e tcp.stream -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport -e tcp.flags.syn -e tcp.flags.ack -e tcp.len > 04_tcp.csv
```

## 12.3. Как найти TCP handshake

Ищите три последовательных логических шага одного `tcp.stream`.

### Шаг A. SYN

Признаки:

```text
tcp.flags.syn = 1
tcp.flags.ack = 0
```

Направление:

```text
ваш компьютер → scanme.nmap.org:80
```

### Шаг B. SYN, ACK

Признаки:

```text
tcp.flags.syn = 1
tcp.flags.ack = 1
```

Направление обратное:

```text
scanme.nmap.org:80 → ваш компьютер
```

### Шаг C. ACK

Признаки:

```text
tcp.flags.syn = 0
tcp.flags.ack = 1
```

Это подтверждает установление соединения на транспортном уровне.

> В потоке будет много ACK-пакетов. Поэтому смотрите на порядок пакетов сразу после SYN и SYN,ACK, а не ищите любой ACK в конце файла.

### Вопросы к этапу 4

1. Зачем TCP выполняет handshake до передачи HTTP-запроса?
2. Как определить клиентскую сторону соединения?
3. Как определить серверную сторону?
4. Что означает повторяющийся SYN без SYN,ACK?
5. Почему повторяющийся SYN нельзя автоматически назвать DoS-атакой?

## Решение этапа 4


### Пример: что конкретно должно получиться

В `04_tcp.csv` нужно найти три первых логических шага **одного и того же `tcp.stream`**. Условный пример:

```text
frame.number,tcp.stream,ip.src,tcp.srcport,ip.dst,tcp.dstport,tcp.flags.syn,tcp.flags.ack,tcp.len
21,0,<CLIENT_IP>,<CLIENT_PORT>,<IP_SCANME>,80,1,0,0
22,0,<IP_SCANME>,80,<CLIENT_IP>,<CLIENT_PORT>,1,1,0
23,0,<CLIENT_IP>,<CLIENT_PORT>,<IP_SCANME>,80,0,1,0
```

Комментарий по строкам:

```text
21: SYN      — клиент просит установить TCP-соединение
22: SYN,ACK  — сервер подтверждает запрос и отвечает своим SYN
23: ACK      — клиент подтверждает ответ; handshake завершён
```

Все три строки имеют одинаковый `tcp.stream = 0` **только в этом условном примере**. В вашем файле номер может быть любым.

> Если вы нашли `GET`, но не можете найти handshake, сначала убедитесь, что смотрите тот же `tcp.stream`, а не другой TCP-разговор из файла.

### Заполненная таблица 3. TCP handshake

| Этап | Кадр | Источник | Назначение | SYN | ACK | Что означает |
|---|---:|---|---|---:|---:|---|
| SYN | `<кадр N>` | `<IP клиента>:<временный порт>` | `<IP scanme>:80` | 1 | 0 | Клиент просит начать TCP-соединение. |
| SYN,ACK | `<кадр N+1>` | `<IP scanme>:80` | `<IP клиента>:<временный порт>` | 1 | 1 | Сервер подтверждает SYN клиента и отправляет собственный SYN. |
| ACK | `<кадр N+2>` | `<IP клиента>:<временный порт>` | `<IP scanme>:80` | 0 | 1 | Клиент подтверждает ответ сервера; соединение установлено. |

### Почему ячейки такие

**Порт 80 на серверной стороне.** Мы специально запросили `http://...`, поэтому удалённой точкой является HTTP-порт 80.

**Временный клиентский порт.** Клиент обычно выбирает динамический исходящий порт. Его номер нельзя заранее зафиксировать в методичке.

**SYN/ACK.** Это флаги TCP, а не текстовые комментарии. Комбинации `1/0`, `1/1`, `0/1` помогают увидеть последовательность handshake.

**Номера кадров.** Они зависят от конкретного файла, поэтому должны быть взяты из `frame.number` студента.

### Ответы на вопросы этапа 4


> **Напоминание о технологии:** **TCP** — транспортный протокол. Handshake `SYN → SYN,ACK → ACK` нужен для установления состояния соединения перед передачей HTTP. Повторные SYN являются сетевым симптомом, а не названием причины.

> **Как обосновывать ответы:** используйте направление пакетов, номера портов и флаги TCP. Клиент инициирует соединение временным портом, сервер в нашей лаборатории принимает его на TCP/80.

**1. Зачем нужен handshake?**  
TCP согласует состояние соединения между двумя сторонами перед передачей прикладных данных. Стороны подтверждают, что готовы обмениваться сегментами и вести учёт последовательности данных.

**2. Как определить клиента?**  
Клиент инициирует соединение первым SYN и обычно использует временный исходящий порт, обращаясь к известному серверному порту 80.

**3. Как определить сервер?**  
В нашем сценарии сервер принимает соединение на TCP/80 и отвечает `SYN,ACK`.

**4. Что означает несколько SYN без SYN,ACK?**  
Клиент пытается установить соединение, но в наблюдаемом захвате не получает ожидаемого ответа. Это признак неуспешного установления соединения.

**5. Почему это не равно DoS?**  
Такой симптом возникает и при обычных проблемах: сервер выключен, порт фильтруется, потеряны пакеты, есть проблема маршрута или межсетевого экрана. DoS — это уже объяснение причины, а не просто видимый симптом.

### Дополнительное пояснение к ответам этапа 4

1. **Handshake нужен для состояния TCP.** До HTTP две стороны должны согласовать транспортное соединение. SYN, SYN/ACK и ACK показывают, что обе стороны видят друг друга и готовы поддерживать поток байтов.
2. **Клиент определяется по инициативе.** Именно клиент первым отправляет SYN к известному серверному порту. В нашей лаборатории это `curl`, который обращается к серверу на TCP/80.
3. **Сервер определяется по роли и порту.** Он принимает запрос на известной сервисной точке и отвечает SYN,ACK. Временный порт клиента служит для конкретного исходящего соединения.
4. **Повторный SYN означает отсутствие ожидаемого подтверждения в наблюдаемой точке.** TCP повторяет попытку, когда подтверждение не пришло. Это может быть сеть, firewall, сервер или потеря пакета.
5. **DoS/DDoS — гипотеза о причине.** Для неё нужно гораздо больше контекста: масштаб запросов, множество источников, состояние сервера, метрики загрузки и события средств защиты. Один клиент с несколькими SYN показывает проблему установления соединения, но не мотив и не источник воздействия.

## Решение этапа 5


### Пример: что конкретно должно получиться

Пример формы строк в `05_http.csv`:

```text
frame.number,frame.time_relative,tcp.stream,ip.src,ip.dst,http.request.method,http.host,http.request.uri,http.response.code
```

Первая строка — запрос клиента:

- поля метода/Host/URI обычно пусты;

```text
Host: scanme.nmap.org

Accept: */*

HTTP/1.1 <HTTP_CODE> ...
...
```

> Заголовки, код ответа и версия `curl` могут отличаться. Критерий успеха — вы нашли собственный HTTP-запрос и можете связать его с конкретным TCP stream.

### Заполненная таблица 4. HTTP

| Параметр | Эталонный ответ | Почему |
|---|---|---|
| Метод HTTP | `GET` | `curl` запрашивает ресурс и по умолчанию использует GET для такого обращения. |
| Host | `scanme.nmap.org` | Клиент обращается к этому доменному имени; поле `http.host` показывает виртуальный хост HTTP. |
| URI | `/` | В URL `http://scanme.nmap.org/` после имени указан корневой путь `/`. |
| Номер TCP stream | `<фактическое число>` | TShark присваивает потокам номера внутри конкретного файла; число заранее неизвестно. |
| Код ответа | `<фактический код, если ответ получен>` | Код зависит от текущего поведения сервера. Его нельзя придумывать. |
| Читается ли HTTP-текст | `Да, если обмен действительно прошёл как незашифрованный HTTP` | HTTP/1.x без TLS передаёт прикладной текст без криптографического шифрования содержимого. |

### Объяснение ячеек

**GET.** Мы не отправляем форму и не меняем данные на сервере. Наша задача — получить обычный ресурс.

**Host.** Один IP может обслуживать несколько имён. `Host` говорит HTTP-серверу, к какому имени относится запрос.

**URI `/`.** Это корень сайта, потому что дополнительный путь в команде не указан.

**TCP stream.** Это служебный индекс TShark для объединения пакетов одного TCP-диалога. Он удобен для команды `follow,tcp,ascii`.

**HTTP-код.** В живой системе нельзя обещать конкретный код навсегда. Корректный ответ — тот, который реально присутствует в захвате.

### Ответы на вопросы этапа 5


> **Напоминание о технологии:** **HTTP** описывает веб-запрос, **TCP** доставляет поток байтов, а **TLS** в HTTPS обеспечивает криптографическую защиту прикладного содержимого. Команда `follow,tcp,ascii` реконструирует полезную нагрузку выбранного TCP-потока для чтения.

> **Как обосновывать ответы:** не смешивайте функции уровней. TCP может доставить HTTP надёжно, но это не означает, что HTTP зашифрован. Конфиденциальность появляется за счёт TLS, а не за счёт самого handshake TCP.

**1. Что означает GET?**  
Это HTTP-метод запроса представления ресурса. В нашем случае запрашивается корневая страница.

**2. Для чего Host?**  
Поле указывает доменное имя, к которому относится запрос. Это позволяет одному веб-серверу обслуживать несколько виртуальных сайтов.

**3. Что показывает код ответа?**  
Категорию результата обработки HTTP-запроса: например успешное выполнение, перенаправление, ошибка клиента или ошибка сервера. Конкретный код надо читать из захвата.

**4. Почему HTTP виден?**  
Потому что между HTTP и TCP в данном сценарии нет TLS-шифрования. Наблюдатель, который легитимно имеет доступ к точке захвата, может разобрать прикладной текст.

**5. Шифрует ли TCP?**  
Нет. TCP обеспечивает надёжную доставку потока байтов, порядок и повторную передачу, но не криптографическую конфиденциальность.

**6. Чем HTTPS отличается?**  
HTTPS использует HTTP поверх TLS. TLS шифрует прикладное содержимое между участниками защищённого соединения, поэтому обычный пассивный захват не показывает HTTP-текст в открытом виде без дополнительных ключей/условий расшифрования.

### Дополнительное пояснение к ответам этапа 5

1. **GET — прикладная операция HTTP.** Он говорит серверу, какое представление ресурса хочет получить клиент. В нашем URL путь `/` означает корень веб-сайта.
2. **Host нужен из-за виртуального хостинга.** Один IP может обслуживать несколько доменных имён. Заголовок `Host` помогает серверу понять, для какого имени предназначен запрос.
3. **Код ответа описывает результат HTTP-обработки.** Он относится к прикладному уровню, а не к TCP. Даже если TCP-соединение успешно, HTTP-сервер может вернуть перенаправление или ошибку.
4. **HTTP виден потому, что в учебном сценарии отсутствует TLS.** TShark восстанавливает байты TCP-потока и может интерпретировать их как HTTP. Видимость зависит от точки захвата и фактического протокола.
5. **TCP не является шифрованием.** Он решает задачи доставки, порядка и повторной передачи. Если поверх TCP передаётся открытый текст, TCP не скрывает его содержимое.
6. **HTTPS добавляет TLS.** TLS защищает прикладные данные криптографически. Поэтому пассивный наблюдатель обычно видит факт соединения и часть метаданных, но не открытый HTTP-текст без специальных условий расшифрования.

# 14. Этап 6. Свяжите уровни сети одной командой


### Напоминание: что такое инкапсуляция

**Инкапсуляция** — это вложение данных одного протокола внутрь другого при передаче по сети.

В нашей лабораторной работе полезно видеть цепочку:

```text
HTTP-запрос
  находится внутри TCP-сегмента
    который находится внутри IP-пакета
      который передаётся в кадре конкретного канального интерфейса
```

TShark разбирает эти вложенные заголовки, поэтому из одного захваченного кадра может вывести поля разных уровней. Это не четыре разных события — это разные уровни описания одного сетевого обмена.

Выполните:

```bash
tshark -r scanme_console.pcapng \
  -Y 'http.request' \
  -T fields \
  -E header=y \
  -E separator=, \
  -e frame.number \
  -e eth.src \
  -e eth.dst \
  -e ip.src \
  -e ip.dst \
  -e tcp.srcport \
  -e tcp.dstport \
  -e http.request.method \
  -e http.host \
  -e http.request.uri \
  > 07_layers.csv
```

Если поля `eth.src` и `eth.dst` пусты, это не обязательно ошибка. Тип канального заголовка зависит от интерфейса захвата.

### Вопросы к этапу 6

1. Почему один HTTP-запрос одновременно содержит признаки нескольких уровней сети?
2. Какой уровень отвечает за IP-адреса?
3. Какой уровень отвечает за TCP-порты?
4. Какой уровень содержит `GET`, `Host` и URI?
5. Почему отсутствие Ethernet-полей не всегда означает повреждённый захват?

## Решение этапа 6


### Пример: что конкретно должно получиться

Одна строка `07_layers.csv` может логически выглядеть так:

```text
frame.number,eth.src,eth.dst,ip.src,ip.dst,tcp.srcport,tcp.dstport,http.request.method,http.host,http.request.uri
24,<L2_SRC>,<L2_DST>,<CLIENT_IP>,<IP_SCANME>,<CLIENT_PORT>,80,GET,scanme.nmap.org,/
```

Эту строку нужно читать сверху вниз по стеку:

```text
<L2_SRC>/<L2_DST>          → канальный уровень конкретной точки захвата
<CLIENT_IP>/<IP_SCANME>    → сетевой уровень IP
<CLIENT_PORT>/80           → транспортный уровень TCP
GET / + Host               → прикладной уровень HTTP
```

Если `eth.src`/`eth.dst` пусты, но IP/TCP/HTTP заполнены, это может быть нормой для выбранного типа интерфейса. Главное — не придумывать Ethernet-адреса, которых нет в фактическом захвате.

### Заполненная таблица 5. Уровни наблюдения

| Уровень | Что нашли | Эталонное значение | Для чего это нужно |
|---|---|---|---|
| Канальный | адреса/заголовок канального уровня | `<eth.src/eth.dst либо другой тип заголовка>` | Показывает локальную доставку кадра на наблюдаемом интерфейсе. |
| Сетевой | IP-адреса | `<IP клиента> → <IP scanme>` | Показывает сетевые конечные точки IP-обмена. |
| Транспортный | TCP-порты | `<временный порт> → 80` | Показывает конкретное TCP-соединение и сервисную точку. |
| Прикладной | HTTP | `GET`, `scanme.nmap.org`, `/` | Показывает смысл прикладного запроса. |

### Почему каждая строка расположена именно на этом уровне

Канальный заголовок решает задачу передачи в пределах конкретной технологии канала. IP работает уровнем выше и описывает сетевые адреса. TCP использует порты для транспортных конечных точек. HTTP уже описывает прикладную операцию веб-клиента.

### Ответы на вопросы этапа 6


> **Напоминание о технологии:** **инкапсуляция** означает, что HTTP-данные передаются внутри TCP, TCP — внутри IP, а IP — внутри канального кадра. TShark способен разобрать все доступные заголовки одной захваченной единицы трафика.

> **Как обосновывать ответы:** называйте не только «уровень», но и его задачу: IP отвечает за сетевую адресацию, TCP — за транспортные конечные точки и поток, HTTP — за прикладной смысл запроса.

**1. Почему признаки нескольких уровней находятся в одном обмене?**  
Прикладные данные инкапсулируются: HTTP помещается в TCP, TCP — в IP, IP — в кадр канального уровня. TShark разбирает вложенные заголовки.

**2. Где IP-адреса?**  
На сетевом уровне IP.

**3. Где TCP-порты?**  
На транспортном уровне TCP.

**4. Где GET, Host и URI?**  
На прикладном уровне HTTP.

**5. Почему Ethernet-поля могут отсутствовать?**  
Не каждый интерфейс предоставляет Ethernet II как канальный формат. Виртуальные, loopback и некоторые специальные типы захвата могут иметь другой link-layer header. Это свойство точки захвата, а не автоматически ошибка файла.

### Дополнительное пояснение к ответам этапа 6

1. **Несколько уровней видны из-за инкапсуляции.** HTTP не заменяет TCP и IP — он использует их. Поэтому TShark может из одного кадра извлечь поля нескольких протоколов.
2. **IP-адреса принадлежат сетевому уровню.** Они нужны для доставки между сетевыми узлами и не определяют конкретное приложение внутри узла.
3. **TCP-порты принадлежат транспортному уровню.** Они позволяют различать конкретные транспортные конечные точки и процессы/сервисы в рамках IP-узла.
4. **GET, Host и URI — прикладные данные HTTP.** Они объясняют, что именно хочет сделать веб-клиент после того, как транспорт уже создан.
5. **Канальный формат зависит от точки захвата.** Ethernet — распространённый, но не единственный вариант. Виртуальный или loopback-интерфейс может предоставлять другой link-layer тип, при этом IP/TCP/HTTP остаются корректно анализируемыми.

# 15. Этап 7. Связь сетевого анализа со свойствами информации


### Напоминание: TShark показывает факт, а свойства ИБ помогают его интерпретировать

TShark отвечает на технические вопросы: какие адреса наблюдались, какие флаги TCP были установлены, какой HTTP-метод передавался, какой DNS-ответ получен.

Информационная безопасность добавляет смысл:

- **конфиденциальность** — кто может прочитать сведения;
- **целостность** — можно ли доверять неизменности и правильности данных;
- **доступность** — можно ли получить сервис вовремя;
- **подлинность** — можно ли доверять заявленному источнику.

Поэтому корректная логика всегда двухэтапная:

```text
наблюдаемый сетевой факт → осторожная интерпретация риска
```

Нельзя перепрыгивать сразу к формуле «увидел странный пакет = доказал атаку».

### Вопросы к этапу 7

1. Почему TShark является средством наблюдения, а не средством шифрования?
2. Как незашифрованный HTTP связан с конфиденциальностью?
3. Как неожиданный DNS-ответ связан с целостностью и подлинностью?
4. Как повторные соединения и тайм-ауты могут быть связаны с доступностью?
5. Почему технический признак ещё не равен установленной причине инцидента?

## Решение этапа 7


### Пример: что конкретно должно получиться

Здесь нет единственного числового вывода. Результат — **правильно сформулированная связь между техническим признаком и свойством информации**.

Пример:

```text
Наблюдение: в follow,tcp,ascii читается HTTP-запрос.
Технология: HTTP без TLS поверх TCP.
Свойство ИБ: конфиденциальность.
Почему: наблюдатель в точке захвата может прочитать прикладной текст.
Чего не доказано: что посторонний действительно перехватил эти данные.
Мера: использовать HTTPS/TLS и минимизировать содержимое захватов.
```

Это и есть требуемая логика ответа: **факт → технология → свойство → ограничение вывода → мера защиты**.

### Заполненная таблица 6. Свойства информации

| Свойство | Сетевой риск | Что может показать TShark | Чего захват не доказывает | Возможная мера |
|---|---|---|---|---|
| Конфиденциальность | Чтение незашифрованного прикладного содержимого | Видимый HTTP-текст, URI, заголовки, метаданные | Что посторонний реально похитил данные | Использование HTTPS/TLS, минимизация передаваемых сведений, сегментация |
| Целостность | Подмена или искажение сетевых данных | Неожиданный ответ, несоответствие ожидаемому источнику, изменение наблюдаемого значения | Причину изменения и виновное лицо по одному пакету | Защищённые протоколы, проверка источника, DNSSEC там, где применимо, контроль конфигурации |
| Доступность | Невозможность установить соединение или получить ответ вовремя | Повторные SYN, тайм-ауты, отсутствие ответов, повторные передачи | Что причиной является именно DoS/DDoS | Мониторинг, резервирование, корректная фильтрация, анализ маршрута и нагрузки |
| Подлинность | Ответ от неожиданного или недоверенного источника | Адрес источника, параметры DNS/сетевого обмена | Личность человека или абсолютную доверенность сервиса только по IP | Проверка сертификатов в защищённых протоколах, доверенные DNS-механизмы, аутентификация |

### Почему таблица заполнена именно так

TShark видит **наблюдаемые сетевые факты**. Свойство информации — это уже смысл этих фактов для защиты. Поэтому в отдельной колонке обязательно указано, чего захват не доказывает: это дисциплинирует анализ и не позволяет превращать один технический признак в обвинение или окончательный диагноз.

### Ответы на вопросы этапа 7


> **Напоминание о технологии:** TShark — средство **наблюдения и анализа**, а не средство защиты канала. Он показывает сетевой факт. CIA-свойства и подлинность помогают интерпретировать, какой риск этот факт может создавать.

> **Как обосновывать ответы:** каждый вывод должен иметь три части: что наблюдалось технически, какое свойство ИБ с этим связано и чего данный захват ещё не доказывает.

**1. Почему TShark не шифрует?**  
Его функция — захватывать и разбирать трафик. Он наблюдает уже существующий обмен. Шифрование создаётся протоколом вроде TLS и настройками приложения.

**2. HTTP и конфиденциальность.**  
Если прикладной текст передаётся без TLS, он потенциально доступен тому, кто имеет техническую возможность видеть трафик в соответствующей точке сети.

**3. DNS и целостность/подлинность.**  
Неверный или неожиданный ответ может направить клиента не туда. Нас интересует и правильность значения, и доверие к источнику. Но для доказательства атаки одного различия недостаточно.

**4. Тайм-ауты и доступность.**  
Они показывают, что сервисом может быть невозможно воспользоваться вовремя. Но причина может находиться на клиенте, сервере, сети или фильтрующем устройстве.

**5. Почему признак не равен причине?**  
Пакет описывает наблюдаемое событие. Причина требует контекста: конфигурации, журналов сервера, маршрута, загрузки, изменений, событий защиты и иногда данных других систем.

### Дополнительное пояснение к ответам этапа 7

1. **TShark наблюдает, а не защищает.** Он читает сетевой трафик и декодирует протоколы. Защиту конфиденциальности создают криптографические протоколы и настройки, например TLS.
2. **Открытый HTTP связан с конфиденциальностью через видимость содержимого.** Если наблюдатель имеет доступ к точке сети, прикладные поля могут быть прочитаны. Это показывает риск раскрытия, но не доказывает, что внешний субъект уже воспользовался им.
3. **DNS связан с целостностью и подлинностью, потому что ответ влияет на дальнейший маршрут.** Неправильный адрес может направить клиента к нежелательному узлу, а анализ должен проверить как значение, так и источник.
4. **Повторы и тайм-ауты являются признаками возможной проблемы доступности.** Они показывают, что нормальная операция не завершается вовремя. Для причины нужны логи, мониторинг и контекст.
5. **Причина не содержится в одном пакете как готовая подпись.** Захват показывает сетевой симптом. Конфигурация сервера, firewall, маршрут, журналы и временная картина помогают превратить симптом в обоснованный вывод.

## Кейс 1. Тестовое значение видно в HTTP-потоке


> **Пояснение терминов кейса для новичка.** `follow,tcp,ascii` — режим TShark, который собирает данные одного TCP-потока и показывает их как текст. `POST` — HTTP-метод, обычно используемый для отправки данных на сервер. `Content-Type: application/x-www-form-urlencoded` означает, что поля формы передаются в виде пар `имя=значение`. Если такой HTTP работает без TLS, текст может быть читаем в точке захвата.

Специалист выполнял проверку учебной веб-формы. В терминальном выводе `follow,tcp,ascii` обнаружен фрагмент:

```text
POST /demo-form HTTP/1.1
Host: training.example
Content-Type: application/x-www-form-urlencoded

user=student07&note=demo
```

Данные синтетические. Реальных персональных данных в форме нет.

### Решение кейса 1

#### Заполненная таблица

| Параметр | Ответ |
|---|---|
| Объект защиты | Содержимое HTTP-запроса и передаваемые значения формы |
| Подтверждённый факт | В `follow,tcp,ascii` читается тело HTTP POST с учебными значениями |
| Основное свойство | Конфиденциальность |
| Потенциальная угроза | Перехват незашифрованного прикладного трафика |
| Источник угрозы | Не установлен: потенциальным наблюдателем может быть лицо/система с доступом к соответствующей точке сети |
| Намеренность | Не установлена |
| Чего факт не доказывает | Что реальный посторонний уже перехватил, сохранил или использовал данные |
| Рекомендация | Использовать HTTPS/TLS; не передавать чувствительные данные по HTTP; минимизировать содержимое захватов |

#### Почему каждая ячейка такая

**Объект защиты** — не «TShark» и не «компьютер». Ценность представляет содержание запроса. Именно его чтение посторонним было бы проблемой.

**Подтверждённый факт** формулируется узко: текст виден в нашем собственном захвате. Мы не утверждаем больше, чем показали данные.

**Конфиденциальность** выбрана потому, что вопрос состоит в возможности прочитать сведения.

**Источник и намеренность** не определяются по фрагменту. В кейсе нет наблюдаемого злоумышленника.

**Рекомендация HTTPS** адресует именно проблему открытого прикладного содержимого.

#### Ответы на вопросы

**1. Почему форма читается?**  
Потому что это обычный HTTP без TLS. Содержимое передаётся как прикладные байты без криптографического сокрытия от наблюдателя канала.

**2. Какое свойство главное?**  
Конфиденциальность, потому что риск — несанкционированное ознакомление с передаваемыми значениями.

**3. Можно ли утверждать кражу?**  
Нет. Наш захват доказывает техническую возможность увидеть данные в выбранной точке наблюдения. Он не доказывает наличие другого наблюдателя или факт последующего использования данных.

**4. Что меняет HTTPS?**  
Между HTTP и TCP появляется TLS. При обычном пассивном захвате прикладное содержимое не читается открытым текстом, хотя часть метаданных соединения всё ещё наблюдаема.

**5. Зачем проверять учебный PCAP?**  
Захват может случайно включить не только учебный обмен. Даже в лаборатории рядом могут оказаться DNS-имена, адреса и метаданные других приложений.

#### Расширенное обоснование ответов для новичка

1. **Почему содержимое читается.** HTTP формирует прикладной текст, TCP доставляет этот текст как поток байтов, а в кейсе нет TLS. TShark, находясь в точке, где трафик доступен для захвата, может восстановить байты одного TCP stream. Поэтому `POST`, заголовки и тело формы видны. Это объясняет **механизм**, а не доказывает факт внешней утечки.
2. **Почему главное свойство — конфиденциальность.** Мы не наблюдаем подмену поля `note` и не наблюдаем отказ сервиса. Проблема состоит именно в возможности прочитать значение не тем субъектом, которому оно предназначено.
3. **Почему нельзя писать «данные украдены».** Захват создан самим специалистом. Он показывает, что данные технически читаемы в этой точке. Для утверждения о краже нужен отдельный факт доступа постороннего субъекта, копирования или использования сведений.
4. **Что делает HTTPS.** В HTTPS прикладной HTTP передаётся внутри TLS. TCP всё так же доставляет байты, но полезная нагрузка защищённого TLS-сеанса для обычного пассивного наблюдателя выглядит как шифрованные данные.
5. **Почему проверяем даже учебный файл.** PCAPNG может содержать соседний фоновый трафик, если capture filter был слишком широким. Поэтому безопасность зависит и от протокола, и от дисциплины самого захвата.

2. Какие легитимные причины могут давать разные адреса?
3. Что нужно сравнить в DNS-ответах кроме самого адреса?
4. Как связан этот кейс с целостностью?
5. Как связан этот кейс с подлинностью источника?

### Решение кейса 2

#### Заполненная таблица

| Параметр | Ответ |
|---|---|
| Объект защиты | Корректность результата DNS-разрешения имени |
| Подтверждённый факт | В двух захватах одному имени соответствовали разные IPv4-адреса |
| Основное свойство | Целостность; дополнительно подлинность источника |
| Источник угрозы | Не установлен |
| Намеренность | Не установлена |
| Нормальные версии | Балансировка, несколько A-записей, изменение инфраструктуры, разные резолверы, кеш/TTL |
| Опасная версия | Подмена DNS-ответа или неверная конфигурация, направляющая клиента не к ожидаемому ресурсу |
| Что проверить | DNS-сервер, TTL, набор ответов, время, повторяемость, конфигурацию резолвера, данные авторитетного DNS |

#### Почему каждая ячейка такая

Мы не называем кейс «DNS-spoofing», потому что данные подтверждают только **расхождение адресов**. Классификация «целостность» уместна, потому что проверяется правильность значения. Подлинность добавляется потому, что важно понять, доверенному ли источнику принадлежит ответ.

#### Ответы на вопросы

**1. Почему разные IP не равны spoofing?**  
Одно доменное имя может легитимно иметь несколько адресов, а инфраструктура может менять их во времени.

**2. Легитимные причины.**  
DNS-балансировка, резервирование, CDN, миграция сервера, несколько A-записей или различия между резолверами.

**3. Что сравнить кроме IP?**  
Адрес источника DNS-ответа, время, TTL, имя запроса, тип записи, наличие нескольких ответов, повторяемость результата и настройки резолвера.

**4. Связь с целостностью.**  
Клиент принимает DNS-ответ как данные, влияющие на дальнейший маршрут. Если значение подменено, нарушена правильность этих данных.

**5. Связь с подлинностью.**  
Нужно понимать, от какого DNS-источника получен ответ и можно ли ему доверять. Один IP-пакет сам по себе не даёт полной гарантии подлинности.

#### Расширенное обоснование ответов для новичка

1. **Почему два IP — ещё не атака.** DNS по своей природе допускает несколько A-записей и изменение ответа во времени. Резолвер также может вернуть закэшированное значение, а разные резолверы могут иметь разные актуальные данные.
2. **Какие нормальные причины проверяем.** Балансировка распределяет клиентов по нескольким серверам; CDN выбирает близкую площадку; миграция меняет инфраструктуру; TTL определяет срок кэширования; несколько A-записей позволяют вернуть набор адресов.
3. **Почему смотрим не только `dns.a`.** Важны источник ответа, флаг response, имя запроса, TTL, тип записи, время и повторяемость. Это позволяет понять контекст DNS-сообщения.
4. **Почему это вопрос целостности.** DNS-ответ является данными, на основании которых клиент выбирает дальнейший адрес назначения. Если значение не соответствует ожидаемому состоянию, возникает вопрос правильности этих данных.
5. **Почему это ещё и подлинность.** Нужно понимать, действительно ли ответ пришёл через ожидаемую доверенную DNS-инфраструктуру. Но IP источника сам по себе не является абсолютной гарантией подлинности.

## Кейс 3. SYN повторяется, ответа нет


> **Пояснение терминов кейса для новичка.** `SYN` — флаг TCP, с которого клиент начинает установление соединения. Ожидаемый ответ доступного TCP-сервиса — `SYN,ACK`. Если ответ не пришёл, TCP-клиент может повторить SYN. **DoS/DDoS** — это уже предположение о причине нарушения доступности; одних повторных SYN недостаточно, чтобы такую причину доказать.

В выводе TShark видно несколько похожих строк:

```text
client → server:80  SYN
client → server:80  SYN
client → server:80  SYN
```

`SYN,ACK` в наблюдаемом фрагменте отсутствует.

- какие причины нужно проверить;
- почему нельзя сразу объявлять DoS/DDoS;
- какие дополнительные данные запросить.

### Вопросы

1. Что означает отсутствие SYN,ACK?
2. Почему клиент повторяет SYN?
3. Какие сетевые или серверные причины возможны?
4. Как отличить проблему доступности от доказанной атаки?
5. Какие дополнительные источники данных нужны администратору?

### Решение кейса 3

#### Заполненная таблица

| Параметр | Ответ |
|---|---|
| Объект защиты | Доступность сетевого сервиса |
| Подтверждённый факт | Клиент несколько раз отправил SYN; SYN,ACK в наблюдаемом фрагменте нет |
| Основное свойство | Доступность |
| Источник проблемы | Не установлен |
| Намеренность | Не установлена |
| Возможные причины | Потеря пакетов, фильтрация, неверный маршрут, сервер/порт недоступен, перегрузка, временный сбой |
| Что нельзя утверждать | Нельзя по этим строкам доказать DoS/DDoS |
| Что проверить | Серверные логи, firewall, маршрут, мониторинг, другие клиенты, нагрузку, временной диапазон |

#### Почему каждая ячейка такая

**Доступность** — главный объект анализа, потому что клиент не может завершить установление соединения. **Источник** и **намеренность** остаются неизвестными: сетевой симптом одинаково возможен и при аварии, и при фильтрации, и при атаке.

#### Ответы на вопросы

**1. Что значит отсутствие SYN,ACK?**  
В наблюдаемой точке клиент не получил ожидаемое подтверждение попытки соединения.

**2. Почему SYN повторяется?**  
TCP повторяет попытку, если ожидаемый ответ не пришёл за установленное время.

**3. Возможные причины.**  
Потеря пакета по пути, закрытый/фильтруемый порт, сервер выключен, проблема маршрутизации, перегрузка или фильтрация межсетевым экраном.

**4. Как отличить от атаки?**  
Нужен контекст: масштаб, множество источников, серверная нагрузка, журналы firewall/IDS, показатели сети и поведение других клиентов. Три SYN одного клиента — недостаточно.

**5. Что ещё запросить?**  
Логи сервера, состояние сервиса, правила firewall, трассировку/маршрут, метрики нагрузки, мониторинг доступности и захват с другой точки сети.

#### Расширенное обоснование ответов для новичка

1. **Отсутствие SYN,ACK.** В TCP это означает, что в выбранной точке захвата мы не увидели ожидаемый второй шаг handshake. Формулировка специально ограничена «не увидели», потому что пакет теоретически мог потеряться до точки наблюдения или после неё.
2. **Почему SYN повторяется.** TCP предполагает повторные попытки при отсутствии подтверждения. Это механизм надёжности, а не обязательно признак атаки.
3. **Почему причин много.** Ответ может блокировать firewall; порт может быть недоступен; сервер может быть выключен; маршрут может быть нарушен; пакеты могут теряться; сервер может быть перегружен.
4. **Как отделить доступность от атаки.** Недоступность — наблюдаемый эффект. DoS/DDoS — возможная причина. Для причины нужны масштаб, множество источников, метрики нагрузки, IDS/IPS/firewall и серверные логи.
5. **Зачем дополнительные источники.** PCAP показывает только то, что наблюдалось в одной точке. Лог сервера показывает, дошёл ли запрос до сервера; firewall — было ли решение о блокировке; мониторинг — насколько широко проявилась проблема.

## Кейс 4. Слишком широкий PCAP отправили во внешний чат


> **Пояснение терминов кейса для новичка.** **PCAP** часто используют как общее название файла захвата пакетов. В этом кейсе файл имеет расширение `.pcapng`, то есть технически это формат **PCAPNG**. Такой файл может содержать копии сетевых кадров и служебные сведения о соединениях, поэтому сам является информационным активом. **Capture filter** — фильтр, который применяется *до записи* и определяет, какие пакеты вообще попадут в файл. Если администратор его не указал, TShark может записать гораздо больше фонового трафика, чем требуется для конкретной задачи.

> В нашем лабораторном примере capture filter задаётся ключом `-f`. Например, `-f "udp port 53 or tcp port 53 or tcp port 80"` ограничивает захват нужными DNS- и HTTP/TCP-пакетами. Это не просто удобство анализа, а мера минимизации: чем меньше лишнего мы записали, тем меньше лишнего можем случайно раскрыть.

Администратор хотел проверить HTTP-запрос, но забыл указать capture filter и записывал весь трафик рабочего ноутбука 30 минут.

Затем он отправил полный файл `workstation_full.pcapng` во внешний чат технической поддержки.

Позже выяснилось, что в файле присутствуют:

- внутренние DNS-имена;
- адреса корпоративных узлов;
- несколько незашифрованных тестовых HTTP-запросов;
- служебные метаданные сетевых соединений.

#### Заполненная таблица

|---|---|
| Объект защиты | Файл `workstation_full.pcapng` и содержащиеся в нём сетевые сведения |
| Источник угрозы | Внутренний: действие администратора организации |
| Намеренность | Непреднамеренная |
| Основное свойство | Конфиденциальность |
| Уязвимость процесса | Слишком широкий захват и отсутствие проверки/минимизации перед внешней передачей |
| Подтверждённый факт | Полный PCAP отправлен во внешний чат; в нём есть внутренние имена, адреса и HTTP-данные |
| Возможные последствия | Раскрытие топологии, внутренних имён, метаданных и содержимого незашифрованного обмена |
| Рекомендация | Узкий capture filter, короткая длительность, локальная проверка, экспорт минимального набора строк/пакетов вместо полного файла |

#### Почему каждая ячейка такая

**Источник внутренний**, потому что опасное действие совершил администратор, находящийся внутри рабочего процесса. Это не означает злой умысел.

**Намеренность непреднамеренная**, потому что в условии описана ошибка: администратор хотел решить сетевую задачу, а не раскрыть сведения.

**Конфиденциальность** нарушается или ставится под риск, потому что сведения переданы за пределы ожидаемого круга получателей.

**Уязвимость процесса** состоит не в самом существовании TShark, а в отсутствии минимизации и проверки перед передачей артефакта.

#### Ответы на вопросы

**1. Почему PCAP — актив?**  
Он может содержать адреса, имена узлов, протоколы, временные метки и иногда прикладное содержимое. Это самостоятельный набор информации о системе.

**2. Какое свойство главное?**  
Конфиденциальность: вопрос в том, кто получил доступ к сетевым сведениям.

**3. Преднамеренная ли это угроза?**  
По условию — нет. Ошибка администратора относится к непреднамеренной антропогенной угрозе.

**4. Почему минимизация нужна ещё при захвате?**  
Если лишние пакеты не записаны, их невозможно случайно раскрыть позже. Это безопаснее, чем собирать всё и надеяться правильно очистить файл после.

**5. Что передавать вместо полного PCAP?**  
Минимальный текстовый вывод TShark, отдельный CSV с нужными полями или специально отфильтрованный небольшой PCAP, если он действительно нужен. Перед передачей результат всё равно проверяется.

#### Расширенное обоснование ответов для новичка

1. **Почему PCAP/PCAPNG — информационный актив.** Файл захвата хранит не «абстрактные пакеты», а технические сведения о реальной сети: кто с кем связывался, в какое время, через какие протоколы и иногда какие данные передавались. Такие сведения помогают администрировать сеть, но могут помогать и постороннему изучать её структуру.
2. **Почему главное свойство — конфиденциальность.** Файл был передан внешнему получателю, а внутри присутствовали сведения, которые не требовались для задачи поддержки. Значит, основной риск — расширение круга лиц, способных ознакомиться с информацией.
3. **Почему угроза непреднамеренная.** Условие прямо говорит, что администратор забыл фильтр и хотел проверить HTTP-запрос. Ошибка остаётся угрозой безопасности, даже если злого умысла не было.
4. **Почему capture filter важен до захвата.** Display filter (`-Y`) может скрыть лишние строки при просмотре, но лишние пакеты всё равно остаются внутри исходного PCAPNG. Capture filter (`-f`) не записывает их вообще. Поэтому для минимизации чувствительных данных `-f` принципиально сильнее, чем последующая визуальная фильтрация.
5. **Что передавать безопаснее.** Если поддержке нужны только несколько полей, лучше экспортировать минимальный текст/CSV. Если нужен сетевой артефакт, следует создать отдельный узкий отфильтрованный файл и проверить его перед передачей. Полный исходный PCAPNG сохраняют локально с контролем доступа.

## Подробные ответы на итоговые вопросы


> **Напоминание перед итоговыми ответами:** в ответах снова встречаются все технологии лабораторной работы: TShark и `dumpcap` для захвата, PCAPNG для сохранения следа, capture/display filters для минимизации и анализа, DNS и резолвер для разрешения имени, TCP для транспортного соединения, HTTP для прикладного запроса и TLS для конфиденциальности HTTPS. При каждом ответе полезно спрашивать: «какую задачу решает эта технология и что конкретно подтверждает наблюдаемый факт?»

**1. Чем TShark отличается от графического Wireshark?**  
TShark работает в терминале и печатает результаты текстом. Он использует тот же стек разбора протоколов семейства Wireshark, но не требует графического окна. Это удобно для серверов, WSL, SSH и воспроизводимых команд.

**2. Зачем `tshark -D`?**  
Чтобы увидеть доступные точки захвата и выбрать ту, где реально проходит тестовый трафик.

**3. `-f` и `-Y`.**  
`-f` — capture filter: решает, какие пакеты вообще записывать во время захвата. `-Y` — display filter: решает, какие уже записанные пакеты показать при анализе.

**4. Почему PCAP может быть чувствительным?**  
Потому что он хранит технический след реальных соединений: адреса, имена, временные метки, протоколы и иногда содержимое сообщений.

**5. Связь DNS и TCP.**  
DNS обычно даёт IP-адрес по доменному имени. Затем клиент использует этот IP как сетевую точку назначения при создании TCP-соединения.

**6. Что показывает handshake?**  
Что клиент и сервер обменялись SYN/SYN,ACK/ACK и согласовали состояние TCP-соединения перед передачей прикладных данных.

**7. Почему TCP не гарантирует конфиденциальность?**  
Его задача — надёжность и порядок доставки, а не шифрование. Для конфиденциальности нужен отдельный криптографический слой, например TLS.

**8. Почему HTTP удобен для демонстрации?**  
Потому что в незашифрованном HTTP легко увидеть связь между сетевым пакетом и прикладным текстом. Это наглядно показывает, зачем нужен защищённый канал.

**9. Почему один необычный пакет не равен атаке?**  
У сетевых аномалий много обычных причин. Для атрибуции и определения намерения нужны дополнительные источники и контекст.

**10. Как разделить факт, гипотезу и вывод?**  
Факт: «наблюдаются три SYN без SYN,ACK». Гипотеза: «возможна фильтрация или недоступность сервера». Вывод появляется после проверки логов, маршрута, состояния сервиса и других данных.

**11. Что связано с чтением посторонним?**  
Конфиденциальность.

**12. Что связано с подменой?**  
Целостность; в вопросах источника также важна подлинность.

**13. Что связано с невозможностью использовать сервис вовремя?**  
Доступность.

**14. Белла — ЛаПадула и сеть.**  
Модель помогает задавать вопрос «кто имеет право видеть информацию и куда её допустимо передавать». В сетевом примере это поддерживает рассуждение о раскрытии данных в незашифрованном канале.

**15. Биба и сетевые данные.**  
Модель акцентирует целостность и доверие к источникам изменений. В сетевом анализе это полезно, когда мы проверяем, можно ли доверять полученному значению DNS или другому входному сетевому сообщению.

### Дополнительная памятка к итоговым ответам

Чтобы новичку было проще не заучивать ответы механически, используйте короткую карту:

| Если в вопросе встречается | Вспомните технологию | Зачем она нужна |
|---|---|---|
| `tshark -D`, `-i` | интерфейс захвата | выбрать точку, где виден нужный трафик |
| `-f` | capture filter | не записывать лишние пакеты в PCAPNG |
| `-Y` | display filter | выбрать нужные пакеты из уже записанного файла |
| `.pcapng` | файл захвата | сохранить технический сетевой след для повторного анализа |
| `nslookup`, `dns.a` | DNS и резолвер | получить IP по доменному имени |
| `SYN/SYN,ACK/ACK` | TCP | установить транспортное соединение |
| `GET`, `Host`, URI | HTTP | описать прикладной веб-запрос |
| HTTPS | TLS поверх HTTP/TCP | защитить конфиденциальность и целостность прикладного обмена |
| повторный SYN / тайм-аут | доступность | увидеть симптом проблемы связи, но не автоматически её причину |

При объяснении любого результата используйте формулу:

```text
какой протокол/инструмент → какую задачу он решает → что мы наблюдаем → какой вывод допустим → чего ещё не доказано
```

# 20. Как писать вывод

Плохой вывод:

```text
Я установил TShark и посмотрел пакеты. Всё работает.
```

Хороший вывод должен ответить:

1. что именно вы захватили;
2. как DNS связал доменное имя с адресом;
3. как установилось TCP-соединение;
4. какой HTTP-запрос был обнаружен;
5. что можно увидеть в незашифрованном HTTP;
6. какое свойство информации с этим связано;
7. какие признаки относятся к целостности и доступности;
8. почему технический анализ не позволяет без дополнительных данных объявить событие атакой.

## Пример итогового вывода

В ходе работы сетевой обмен с учебным узлом был захвачен и проанализирован полностью из терминала с помощью TShark. Сначала был определён фактический интерфейс захвата, после чего capture filter ограничил запись DNS-трафиком и HTTP на TCP-порту 80. В DNS-пакетах было подтверждено разрешение имени `scanme.nmap.org` в фактический IPv4-адрес, полученный в текущем сеансе. Далее в TCP-потоке были выделены этапы установления соединения SYN, SYN,ACK и ACK. В HTTP-разборе были найдены прикладные поля запроса, включая метод, имя узла и путь. Консольный `follow,tcp,ascii` показал, что незашифрованный HTTP может быть читаем в точке захвата, что напрямую связано с риском для конфиденциальности. При этом необычный DNS-ответ следует рассматривать как повод проверять целостность и подлинность, а повторные SYN — как признак возможной проблемы доступности, но не как автоматическое доказательство атаки. Практика показывает, что TShark даёт технические факты, а причина и намеренность устанавливаются только после сопоставления с другими источниками. Отдельным объектом защиты является сам файл PCAP, поэтому при захвате и передаче результатов необходимо применять минимизацию данных.

# 21. Типовые ошибки новичка

## Ошибка 1. Установлен `wireshark-qt` вместо `wireshark-cli` в Arch

Для этой работы Qt-интерфейс не нужен.

Используйте:

```bash
sudo pacman -S wireshark-cli
```

## Ошибка 2. `tshark -D` не выполнен до захвата

В итоге студент копирует чужой номер интерфейса и записывает не тот трафик.

## Ошибка 3. Запуск `sudo tshark` вместо настройки прав

Это маскирует проблему прав и без необходимости запускает большой анализатор с повышенными привилегиями.

## Ошибка 4. Захват всего трафика

Файл становится большим и может содержать лишнюю чувствительную информацию.

В нашей работе используется:

```text
udp port 53 or tcp port 53 or tcp port 80
```

## Ошибка 5. Перепутаны `-f` и `-Y`

`-f` работает во время захвата.

`-Y` работает при чтении и анализе.

## Ошибка 6. В отчёт скопирован IP из примера

IP должен быть получен из вашего фактического DNS-ответа.

## Ошибка 7. Не найден DNS

Проверьте, что во время захвата вы действительно выполнили:

```bash
nslookup scanme.nmap.org
```

## Ошибка 8. HTTP не найден

Проверьте, что использовали именно:

```text
http://scanme.nmap.org/
```

а не HTTPS, и что capture filter включал TCP-порт 80.

## Ошибка 9. Любой повторный SYN назван DoS

Это только сетевой признак неуспешного соединения. Причина требует дополнительной проверки.

## Ошибка 10. Полный PCAP отправлен без проверки

Файл захвата может содержать больше информации, чем кажется.
