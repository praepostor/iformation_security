# Анализ Ethernet-кадров, сетевой адресации и доверия в Wireshark — полное решение

*Полная версия*

| Параметр | Описание |
|---|---|
| **Цель работы** | Научиться захватывать небольшой объём собственного сетевого трафика в Wireshark, находить Ethernet-кадры, читать MAC- и IP-адреса, видеть DNS, TCP и HTTP внутри одного сетевого обмена и объяснять ИБ-риски по наблюдаемым фактам. |
| **Что будет сделано руками** | Выбор сетевого интерфейса → настройка capture filter → захват DNS и HTTP-трафика → анализ Ethernet II → анализ TCP-соединения → анализ HTTP-запроса → просмотр статистики → разбор ИБ-кейсов. |
| **Учебный внешний узел** | `scanme.nmap.org`. В этой работе он используется только как имя обычного DNS/HTTP-обращения. Сканирование портов, подбор паролей, DoS/DDoS и эксплуатация уязвимостей не выполняются. Фактический IP, который вернёт DNS, может отличаться между моментами/сетями; это значение только наблюдается в Wireshark. |
| **Итоговый результат** | Заполненные таблицы, 4 обязательных скриншота, ответы на вопросы, разбор пяти кейсов и итоговый вывод. |
| **Уровень** | Начальный. Все основные термины поясняются по ходу работы. |
| **Рекомендуемое время** | 120–150 минут. |

> **Правило цели этой лабораторной работы:** во всех практических действиях в качестве удалённого веб-узла вводите **только имя `scanme.nmap.org`** или URL `http://scanme.nmap.org/`. Не подставляйте в команды числовой IP-адрес, который покажет DNS. IP-адреса в таблицах ниже нужны только как **наблюдаемые поля из вашего собственного захвата Wireshark**: вы их переписываете из Packet Details, но не используете как отдельную цель. Это позволяет выполнить работу без списка IP-адресов и без отдельного тестового контура.

> **Почему именно `scanme.nmap.org`:** это публичный учебный узел проекта Nmap. В этой работе мы не выполняем сканирование, подбор паролей, нагрузочное тестирование или эксплуатацию. Мы создаём только один обычный DNS-запрос и один обычный HTTP-запрос, чтобы увидеть собственный сетевой обмен в Wireshark.

> **Главное правило безопасности:** захватывайте трафик только на собственном учебном устройстве и только на том интерфейсе, на котором вы имеете право выполнять анализ. Не перехватывайте чужой трафик и не публикуйте файлы захвата в открытом доступе.

> **Почему это важно:** файл `pcap` или `pcapng` может содержать IP- и MAC-адреса, доменные имена, URL, незашифрованные HTTP-заголовки, cookies, служебные идентификаторы и другие сведения. Поэтому файл захвата сам является **информационным активом** — ценным объектом, который нужно хранить и передавать аккуратно.


> **Как пользоваться этой версией:** точные IP-адреса, MAC-адреса, номера кадров, временные клиентские порты и количество пакетов зависят от вашего компьютера и сети. Ниже приведены **условные примеры**, которые показывают структуру правильного результата. Студент не должен подгонять свой захват под эти числа. Он должен найти те же *смыслы и поля* в собственном PCAPNG.

> **Напоминание о технологии:** Wireshark пассивно анализирует тот трафик, который попал в захват. Он показывает сетевые факты, но не устанавливает личность злоумышленника, мотив и юридическую квалификацию. Любой вывод об атаке должен подтверждаться другими источниками: журналами, конфигурацией, метриками и контекстом.

# 1. Установка Wireshark

## 1.1. Что именно мы устанавливаем

**Wireshark** — графический анализатор сетевых протоколов. Он принимает захваченные кадры и пакеты, разбирает их по протоколам и показывает поля в удобном виде.

Важно отличать два компонента:

- **Wireshark GUI** — графическое окно, в котором мы будем нажимать кнопки, выбирать пакеты и раскрывать поля;
- **механизм захвата** — компонент, который получает пакеты от операционной системы. В Windows для этого обычно используется **Npcap**, а в Linux/macOS доступ к захвату организуется через системные механизмы и `dumpcap`.

> **Для этой работы нужен именно графический Wireshark.** Здесь важно научиться работать с окном программы: выбирать интерфейс, запускать и останавливать захват, применять фильтры, выбирать пакет и раскрывать его поля.

## 1.2. Windows

### Шаг 1. Скачайте установщик

1. Откройте официальный сайт Wireshark.
2. Перейдите в раздел **Download**.
3. Выберите установщик для вашей архитектуры Windows. Для большинства современных ПК это x64.
4. Запустите скачанный `.exe`.

### Шаг 2. Установите Wireshark

1. Нажимайте **Next** по шагам мастера.
2. Оставьте графический компонент Wireshark включённым.
3. Когда мастер предложит установить **Npcap**, не снимайте этот пункт.
4. Завершите установку.

**Npcap** — драйвер захвата пакетов для Windows. Простыми словами, именно он даёт Wireshark возможность получать сетевые пакеты с интерфейсов Windows.

### Шаг 3. Проверка

1. Откройте меню **Пуск**.
2. Найдите **Wireshark**.
3. Запустите программу.
4. На стартовом экране должен появиться список интерфейсов: например, `Wi-Fi`, `Ethernet`, виртуальные адаптеры и другие.
5. Рядом с активным интерфейсом обычно виден небольшой движущийся график трафика.

Если интерфейсы видны, но захват не запускается, сначала проверьте установку Npcap. Не используйте запуск Wireshark от имени администратора как постоянное решение.

## 1.3. Linux: Ubuntu / Debian и производные

Откройте терминал и выполните:

```bash
sudo apt update
sudo apt install wireshark
```

Во время установки система может спросить, разрешать ли обычным пользователям захват пакетов.

Если появляется вопрос вида **«Should non-superusers be able to capture packets?»**, для учебного компьютера выберите **Yes**.

Если вопрос не появлялся или вы выбрали другой вариант, можно повторно открыть настройку:

```bash
sudo dpkg-reconfigure wireshark-common
```

Затем добавьте своего пользователя в группу `wireshark`:

```bash
sudo usermod -aG wireshark "$USER"
```

После этого **выйдите из пользовательской сессии и войдите снова**. Простое закрытие терминала может быть недостаточно, потому что состав групп обычно перечитывается при новом входе.

Запуск:

```bash
wireshark
```

> **Почему не рекомендуется `sudo wireshark`:** графический анализатор обрабатывает сложные входные данные. Безопаснее дать минимально необходимые права специальному компоненту захвата, а само графическое приложение запускать от обычного пользователя.

## 1.6. Windows Subsystem for Linux — WSL

### Сначала главное: WSL — это отдельная Linux-среда

**WSL (Windows Subsystem for Linux)** позволяет запускать Linux внутри Windows без обычной отдельной виртуальной машины, которой пользователь управляет вручную.

Для Wireshark важно понимать, **где создаётся трафик**:

- если браузер, PowerShell или приложение работает в Windows, проще использовать **Wireshark для Windows** и захватывать Windows-интерфейс;
- если команда `curl` выполняется внутри WSL и вы хотите анализировать именно сетевое представление WSL, можно использовать **Wireshark внутри WSL**.

Это не одно и то же. WSL имеет собственное сетевое представление, поэтому список интерфейсов и MAC-адреса могут отличаться от Windows.

### Проверка WSL 2 и GUI

В PowerShell:

```powershell
wsl -l -v
```

Для графических Linux-приложений нужен WSL 2.

Если WSL уже установлен, полезно обновить его:

```powershell
wsl --update
wsl --shutdown
```

После этого снова откройте вашу Linux-дистрибуцию.

### Установка Wireshark внутри Ubuntu в WSL

```bash
sudo apt update
sudo apt install wireshark
```

Если требуется разрешить захват обычным пользователем:

```bash
sudo dpkg-reconfigure wireshark-common
sudo usermod -aG wireshark "$USER"
```

После нового входа в WSL запустите:

```bash
wireshark
```

Если Windows и WSL настроены с поддержкой WSLg, графическое окно появится как обычное приложение Windows.

> **Для новичка:** если задача — просто выполнить эту лабораторную работу на обычном Windows-ноутбуке, используйте нативный Wireshark для Windows. WSL-вариант нужен только если преподаватель специально просит анализировать трафик Linux-среды WSL.

Если после Homebrew-установки список доступных интерфейсов пуст, не запускайте приложение постоянно через `sudo`. Для новичка проще использовать официальный `.dmg` и установить предлагаемый компонент **ChmodBPF**, который настраивает права захвата.

# 2. Wireshark с нуля: что находится перед вами

## 2.1. Что такое сетевой трафик

**Сетевой трафик** — это данные, которыми устройства обмениваются по сети. Когда браузер открывает страницу, система делает DNS-запрос, создаёт TCP-соединение и отправляет HTTP/HTTPS-запросы. На каждом уровне появляются свои заголовки и служебные поля.

Wireshark не «видит смысл всей сети сразу». Он получает последовательность отдельных кадров/пакетов и помогает собрать из них техническую картину.

## 2.2. Что такое захват пакетов

**Packet capture / захват пакетов** — запись сетевых единиц данных, которые проходят через выбранный интерфейс и доступны механизму захвата.

Захват не означает, что Wireshark автоматически видит весь трафик организации. Обычно на обычном ноутбуке виден:

- трафик самого ноутбука;
- широковещательный/многоадресный трафик, доставленный ему;
- отдельные служебные кадры;
- дополнительный трафик только в специально настроенных сетевых сценариях.

## 2.3. Что такое сетевой интерфейс

**Сетевой интерфейс** — программно представленный сетевой адаптер или канал связи.

Примеры:

- Wi-Fi-адаптер;
- Ethernet-карта;
- VPN-интерфейс;
- виртуальный интерфейс WSL/виртуальной машины;
- loopback — внутренний интерфейс для обмена внутри самого компьютера.

> **Почему выбор интерфейса важен:** если вы генерируете трафик через Wi-Fi, а захватываете неактивный Ethernet, нужных кадров в захвате не будет.

## 2.4. Главное окно Wireshark

После захвата основное окно обычно состоит из трёх основных областей.

### 1. Packet List — список пакетов

Это верхняя таблица.

Каждая строка — один захваченный пакет/кадр. Обычно видны столбцы:

- **No.** — порядковый номер;
- **Time** — время относительно начала захвата или другой выбранный формат времени;
- **Source** — источник;
- **Destination** — назначение;
- **Protocol** — протокол, который Wireshark считает наиболее полезным показать для этой строки;
- **Length** — длина;
- **Info** — краткое описание.

### 2. Packet Details — подробности пакета

Это средняя область с деревом протоколов.

Типичная цепочка для обычного HTTP-запроса:

```text
Frame
└── Ethernet II
    └── Internet Protocol Version 4
        └── Transmission Control Protocol
            └── Hypertext Transfer Protocol
```

Стрелка или треугольник слева раскрывает уровень.

### 3. Packet Bytes — байты пакета

Это нижняя область.

Слева показаны байты в шестнадцатеричном виде, справа — их ASCII-представление там, где оно возможно.

Если выбрать поле в **Packet Details**, Wireshark подсветит соответствующие байты в **Packet Bytes**.

> **Зачем это нужно новичку:** средняя панель объясняет смысл поля, а нижняя показывает, что это поле реально занимает определённые байты в захваченном кадре.

## 2.5. Display filter — фильтр отображения

**Display filter** не удаляет пакеты из файла. Он только говорит Wireshark: «покажи мне сейчас строки, которые соответствуют условию».

Примеры:

```text
dns
```

показывает DNS;

```text
tcp.port == 80
```

показывает TCP-пакеты, где один из портов равен 80;

```text
http.request
```

показывает HTTP-запросы.

Поле display filter расположено над **Packet List**. После ввода нажмите **Enter** или кнопку применения фильтра.

## 2.6. Capture filter — фильтр захвата

**Capture filter** применяется **до записи**. Пакеты, не подходящие под условие, вообще не попадут в файл захвата.

В этой работе будет использован:

```text
arp or udp port 53 or tcp port 53 or tcp port 80
```

Разберём по частям:

- `arp` — оставить ARP-кадры;
- `udp port 53` — оставить классический DNS по UDP;
- `tcp port 53` — оставить DNS по TCP, если он встретится;
- `tcp port 80` — оставить TCP-трафик HTTP на порту 80;
- `or` — логическое «ИЛИ»: подходит любое из перечисленных условий.

> **Главное различие:** capture filter уменьшает объём **записываемых** данных, display filter меняет только то, что **показывается на экране** после захвата.

# 3. Сетевая теория

## 3.1. Кадр, пакет, сегмент — это не одно и то же

Новички часто называют всё словом «пакет». Для разговора это допустимо, но в лабораторной полезно различать уровни.

| Термин | Уровень | Простое объяснение |
|---|---|---|
| **Ethernet frame / Ethernet-кадр** | Канальный уровень | То, что передаётся внутри локального Ethernet-сегмента между соседними сетевыми участниками. Содержит MAC-адреса. |
| **IP packet / IP-пакет** | Сетевой уровень | Единица IP. Содержит IP-адрес источника и назначения. Может проходить через несколько маршрутизаторов. |
| **TCP segment / TCP-сегмент** | Транспортный уровень | Часть TCP-обмена. Содержит порты, sequence number, flags и другие поля. |
| **HTTP message** | Прикладной уровень | Запрос или ответ веб-протокола: например `GET /`. |

## 3.2. Инкапсуляция

**Инкапсуляция** — вложение данных одного уровня внутрь структуры другого уровня.

Для нашего HTTP-запроса упрощённая логика такая:

```text
HTTP-запрос
↓ помещается в
TCP-сегмент
↓ помещается в
IP-пакет
↓ помещается в
Ethernet-кадр
```

На принимающей стороне уровни разбираются в обратном порядке.

> **Почему это важно для ИБ:** разные поля отвечают за разные части доверия. MAC помогает локальной доставке, IP определяет сетевое назначение, TCP обеспечивает состояние соединения, HTTP описывает прикладное действие.

## 3.3. Ethernet II

**Ethernet** — семейство технологий локальных сетей. В этой работе нас интересует распространённый формат **Ethernet II**.

Упрощённая структура:

| Поле | Типичный размер | Зачем нужно |
|---|---:|---|
| Преамбула + служебный старт | 8 байт перед основными полями | Синхронизация передачи на физическом уровне. Обычно Wireshark её не показывает как часть обычного захвата. |
| Destination MAC | 6 байт | Кому локально предназначен кадр. |
| Source MAC | 6 байт | От какого локального интерфейса пришёл кадр. |
| EtherType | 2 байта | Какой протокол находится внутри: например IPv4 или ARP. |
| Payload / данные | Переменный размер | Инкапсулированный протокол и его данные. |
| FCS | 4 байта | Контроль ошибок Ethernet. Часто сетевой адаптер проверяет/удаляет FCS до передачи данных Wireshark, поэтому поле может отсутствовать в захвате. |

## 3.4. MAC-адрес

**MAC-адрес** — адрес канального уровня, обычно 48 бит, записанный шестью парами шестнадцатеричных цифр:

```text
3c:52:82:aa:bb:cc
```

MAC используется для локальной доставки Ethernet-кадра.

### Source MAC

MAC отправителя данного локального кадра.

### Destination MAC

MAC следующего локального получателя кадра.

### OUI

**OUI (Organizationally Unique Identifier)** — исторически первые 24 бита глобально назначенного MAC-префикса, связанные с организацией-производителем.

Важно: современные ОС и виртуальные среды могут использовать **locally administered / randomized MAC**, поэтому по первым байтам нельзя всегда надёжно определить производителя физического устройства.

> В старых учебных описаниях оставшуюся часть MAC иногда называют «серийным номером». Для практической работы безопаснее говорить **индивидуальная часть идентификатора интерфейса**: это не обязательно буквальный серийный номер оборудования.

## 3.5. Unicast, broadcast, multicast

**Unicast** — кадр одному конкретному получателю.

**Broadcast** — широковещательный кадр всем участникам локального broadcast domain. Классический Ethernet broadcast MAC:

```text
ff:ff:ff:ff:ff:ff
```

**Multicast** — доставка группе получателей.

## 3.6. IP-адрес

**IP-адрес** — логический адрес сетевого уровня. Он нужен, чтобы сетевой уровень понимал, от какого узла идёт IP-пакет и к какому сетевому назначению его нужно маршрутизировать.

В этой лабораторной работе мы **не вводим числовой IP удалённого узла вручную**. Сначала DNS разрешает имя `scanme.nmap.org`, а затем Wireshark показывает фактический IP уже внутри захваченного пакета. В отчёте обозначайте такие значения, например, как `<IP_вашего_ПК>` и `<IP_scanme_из_захвата>`, а рядом переписывайте фактическое значение только из собственного PCAPNG.

IP нужен для доставки между сетями.

Ключевое отличие:

- MAC действует на текущем локальном участке;
- IP описывает сетевой источник/назначение и обычно сохраняется через маршрутизируемый путь, хотя существуют NAT и другие механизмы, которые могут менять адреса.

## 3.7. Коммутатор и маршрутизатор

**Коммутатор / switch** в простом Ethernet-сценарии пересылает кадры внутри локальной сети, ориентируясь на MAC-адреса.

**Маршрутизатор / router** соединяет разные IP-сети и принимает решение, куда передать IP-пакет дальше.

## 3.8. Шлюз по умолчанию

**Default gateway / шлюз по умолчанию** — маршрутизатор, которому компьютер обычно передаёт IP-пакеты, предназначенные не для своей локальной сети.

Пример логики:

```text
Ваш ПК
   |
   | Ethernet destination MAC = MAC локального next hop
   v
Домашний/офисный маршрутизатор или другой локальный next hop
   |
   | дальше по маршрутизируемой сети
   v
scanme.nmap.org
```

Здесь специально нет числового IP: имя `scanme.nmap.org` разрешит DNS, а фактический адрес вы увидите в своём захвате Wireshark.

Очень важный вывод:

> Когда вы обращаетесь к удалённому серверу, **IP destination** может быть адресом удалённого сервера, а **Ethernet destination MAC** — адресом локального следующего узла, обычно шлюза.

MAC-адрес удалённого веб-сервера через Интернет ваш компьютер обычно не знает и не должен знать: между ними находятся маршрутизаторы, и Ethernet-заголовок меняется на каждом канальном участке.

## 3.9. ARP

**ARP (Address Resolution Protocol)** — протокол IPv4-локальной сети, который помогает узнать, какой MAC-адрес соответствует нужному локальному IPv4-адресу.

Упрощённый смысл ARP-запроса:

```text
«Кто в моём локальном сегменте использует нужный мне локальный IPv4? Сообщите свой MAC».
```

В этой работе не нужно вручную подставлять адрес шлюза. Если ARP попадёт в захват естественным образом, вы прочитаете локальный IPv4 и MAC прямо из полей пакета.

Первоначальный ARP Request часто является broadcast, потому что отправитель ещё не знает MAC владельца IP.

> **ИБ-смысл:** если соответствие IP ↔ MAC неожиданно меняется, это повод для проверки. Но один изменившийся MAC сам по себе ещё не доказывает атаку: устройство могли заменить, сеть могла использовать резервирование, виртуальный шлюз или другую штатную схему.

## 3.10. DNS

**DNS (Domain Name System)** переводит удобное имя сервиса в сетевой адрес.

Пользователь пишет:

```text
scanme.nmap.org
```

а приложение получает IP-адрес, к которому можно строить соединение.

### Что такое DNS resolver

**Resolver / DNS-резолвер** — компонент, которому ваш компьютер задаёт вопрос о доменном имени.

Простыми словами:

```text
Приложение: «Мне нужен scanme.nmap.org»
        ↓
Резолвер: «Я выясню, какой IP соответствует этому имени»
        ↓
Ответ: «Используй такой IP»
```

Резолвером может быть:

- DNS-сервер организации;
- домашний маршрутизатор, пересылающий запросы дальше;
- DNS-сервис провайдера;
- публичный DNS-сервис;
- локальный системный stub-resolver, который затем обращается к настоящему DNS-серверу.

> **ИБ-смысл:** DNS-ответ влияет на направление подключения. Поэтому доверие к имени требует доверия к процессу разрешения имени и, для защищённых веб-сервисов, дополнительной проверки TLS-сертификата.

## 3.11. TCP

**TCP (Transmission Control Protocol)** — транспортный протокол с установлением соединения и контролем последовательности данных.

### Зачем TCP

TCP помогает двум приложениям:

- установить логическое соединение;
- нумеровать передаваемые данные;
- подтверждать получение;
- повторно передавать потерянные данные;
- регулировать поток.

### Трёхстороннее рукопожатие

Перед передачей обычных данных TCP обычно выполняет:

```text
Клиент → Сервер: SYN
Сервер → Клиент: SYN, ACK
Клиент → Сервер: ACK
```

**SYN** — запрос на начало и синхронизацию TCP-соединения.

**ACK** — подтверждение.

## 3.12. Порт

**TCP/UDP port / порт** — число, которое помогает операционной системе понять, какому приложению передать сетевой обмен.

Для обычного HTTP традиционно используется TCP-порт 80.

У клиента при этом обычно появляется **ephemeral port / временный клиентский порт**, например `52144`. Это не «открытый веб-сервис» на ноутбуке, а временный номер конкретного исходящего соединения.

## 3.13. HTTP

**HTTP (Hypertext Transfer Protocol)** — прикладной протокол запрос/ответ.

Пример:

```text
GET / HTTP/1.1
Host: scanme.nmap.org
```

- `GET` — метод запроса ресурса;
- `/` — путь к корневой странице;
- `Host` — имя веб-узла.

**HTTP сам по себе не шифрует содержимое.** Поэтому незашифрованный HTTP удобно анализировать в учебной работе, но нельзя передавать через него реальные секреты, пароли или чувствительные данные.

## 3.14. HTTPS и TLS

**HTTPS** — HTTP внутри защищённого TLS-канала.

**TLS** шифрует прикладные данные и позволяет клиенту проверять сертификат сервера. При обычном HTTPS Wireshark видит сетевые и транспортные поля, но не обязан показывать открытым текстом содержимое HTTP-запроса.

## 3.15. PCAP и PCAPNG

**PCAP** и **PCAPNG** — форматы файлов сетевого захвата.

`pcapng` — современный формат, который Wireshark обычно использует по умолчанию. Он может хранить не только пакеты, но и дополнительную информацию о захвате.

### Почему такой файл — информационный актив

В нём могут быть:

- адреса устройств;
- домены;
- временная линия действий;
- незашифрованные HTTP-поля;
- cookies или токены, если они передавались открыто;
- служебные имена;
- структура взаимодействия систем.

Поэтому файл нельзя бездумно прикладывать к публичной переписке, GitHub issue или открытому облачному диску.

## 3.16. Сетевое доверие и ИБ

При анализе важно не говорить: «адрес правильный — значит всё безопасно».

Сетевое доверие складывается из нескольких признаков:

- имя;
- IP-адрес;
- MAC локального следующего узла;
- маршрут и шлюз;
- сертификат для TLS;
- учётная запись;
- устройство;
- время и контекст события;
- журналы.

Один признак не заменяет остальные.

## 3.17. Доступность и сетевой захват

**Доступность** — возможность выполнить нужное действие в нужный момент и получить результат за приемлемое время.

Wireshark может показать признаки сетевой деградации:

- повторные TCP-передачи;
- сбросы соединения;
- длительные паузы;
- ошибки прикладного протокола;
- необычно большое число служебных кадров.

Но важное правило:

> **Один признак в PCAP не доказывает DoS/DDoS.** Для вывода нужны контекст нагрузки, несколько источников данных, метрики сервиса, журналы, число источников и понимание того, какой ресурс исчерпывается.

## 3.18. Мини-словарь терминов, которые встретятся в кейсах

Ниже термины, которые в реальной работе часто произносят без пояснения. Для начинающего специалиста важно понимать их буквально.

- **DHCP (Dynamic Host Configuration Protocol)** — протокол автоматической выдачи сетевых настроек устройству. Через DHCP клиент может получить IP-адрес, маску сети, шлюз по умолчанию и адрес DNS-сервера. ИБ-риск возникает, если параметры пришли от неправильного или ошибочно настроенного источника.
- **Сегмент сети** — часть сети, внутри которой устройства имеют общий сетевой контекст. В учебных примерах это может быть отдельная офисная подсеть или VLAN.
- **VLAN (Virtual Local Area Network)** — логическое разделение одной физической коммутируемой инфраструктуры на отдельные канальные сегменты. Устройства из разных VLAN обычно не общаются напрямую без маршрутизации.
- **STP (Spanning Tree Protocol)** — механизм, который помогает коммутируемой Ethernet-сети избегать опасных L2-петель. L2-петля — ситуация, когда кадры могут циркулировать по замкнутому пути и создавать лишний broadcast-трафик.
- **MAC table / таблица MAC-адресов коммутатора** — таблица, где коммутатор запоминает, за каким физическим или логическим портом он видел определённый MAC-адрес. Она помогает понять локальное положение устройства.
- **HA (High Availability, высокая доступность)** — архитектура с резервированием, где отказ одного компонента не должен полностью остановить сервис.
- **Failover / аварийное переключение** — переход с основного компонента на резервный. Из-за штатного failover адрес или MAC шлюза иногда может измениться.
- **VRRP (Virtual Router Redundancy Protocol)** — один из протоколов резервирования шлюза. Несколько маршрутизаторов могут представлять один виртуальный шлюз, поэтому при переключении сетевые признаки могут отличаться от простого сценария «один IP — одно физическое устройство».
- **Метрика** — числовой показатель состояния системы. Например, время ответа, число запросов или доля ошибок.
- **RPS (Requests Per Second)** — число запросов в секунду. Большой RPS сам по себе не доказывает атаку: важно, справляется ли сервис и насколько дороги запросы.
- **Latency** — задержка, то есть сколько времени проходит до получения результата или ответа.
- **Error rate** — доля запросов, завершившихся ошибкой.
- **p95 / p99 latency** — показатели «хвоста» задержек: p95 означает, что примерно 95% измерений не превышают это значение, а оставшаяся часть медленнее. Они помогают увидеть проблему, которую может скрыть среднее значение.
- **Узкое место (bottleneck)** — компонент или ограниченный ресурс, который первым перестаёт справляться и тормозит весь пользовательский сценарий.
- **Backend** — серверная часть приложения, которая выполняет бизнес-логику, обращается к базе данных и другим сервисам. Пользователь обычно не видит её напрямую.
- **API (Application Programming Interface)** — программный интерфейс, через который одна программа обращается к другой по формализованным запросам.
- **Rate limiting** — ограничение частоты запросов, чтобы один пользователь, ключ или сценарий не забрал слишком много общего ресурса.
- **Graceful degradation / контролируемая деградация** — заранее продуманный режим, при котором система временно ограничивает второстепенные функции, но сохраняет критичные действия.
- **Sanitization / санитизация данных** — удаление, маскирование или замена чувствительной информации перед передачей файла другому человеку. Для PCAPNG это может означать подготовку безопасной учебной копии вместо публикации исходного захвата.

# 4. Рабочая ситуация

> **Чем эта работа отличается от исходной лабораторной:** здесь нет Mininet, готовых узлов H1/H3, списка IP-адресов и задания `ping` по выданной топологии. Мы используем другой сценарий: собственный короткий захват → DNS для `scanme.nmap.org` → один HTTP-запрос → разбор Ethernet II, TCP и HTTP. Исходная лабораторная используется только как методическая основа для изучения полей Ethernet II и интерфейса Wireshark; задания и кейсы здесь другие.

Вы — начинающий специалист, которому нужно понять, **как один обычный запрос к удалённому веб-узлу выглядит на разных сетевых уровнях**.

Вы должны:

1. захватить ограниченный объём собственного трафика;
2. получить DNS-ответ для `scanme.nmap.org`;
3. создать одно обычное HTTP-соединение;
4. найти Ethernet II;
5. определить Source MAC и Destination MAC;
6. найти IP-адреса;
7. найти TCP-порты и SYN/SYN-ACK/ACK;
8. найти HTTP GET;
9. сравнить канальный и сетевой уровни;
10. сохранить результат и провести первичную ИБ-интерпретацию.

> Практическая цепочка работы: **DNS → TCP → HTTP → Ethernet-анализ → ИБ-интерпретация**. Мы создаём только небольшой объём обычного клиентского трафика и затем пассивно изучаем его в Wireshark.

# 5. Подготовка к захвату: интерфейс Wireshark шаг за шагом

## 5.1. Откройте Wireshark

После запуска вы увидите **Welcome Screen**.

Слева или в центральной части будет раздел **Capture** со списком сетевых интерфейсов.

### Как понять, какой интерфейс нужен

Если вы подключены по Wi-Fi:

1. найдите строку `Wi-Fi`, `wlan0`, `wlp...` или аналогичную;
2. посмотрите на маленький график активности;
3. откройте в браузере любую разрешённую страницу;
4. убедитесь, что график на этом интерфейсе заметно меняется.

Если подключение по кабелю — ищите `Ethernet`, `eth0`, `enp...`, `eno...`.

В macOS имена могут выглядеть как `en0`, `en1`.

В WSL — обычно будет виртуальный интерфейс Linux, часто `eth0`.

> **Очень важная проверка именно для этой работы:** после короткого пробного захвата выберите любой обычный IP-пакет и посмотрите среднюю панель **Packet Details**. Там должна присутствовать строка **Ethernet II**, если выбранный интерфейс даёт Ethernet-представление кадров. На некоторых Wi-Fi, VPN, loopback или виртуальных интерфейсах Wireshark может показывать другой тип канального заголовка, например IEEE 802.11 или специальный pseudo-header. Это не ошибка Wireshark, но такой интерфейс хуже подходит для задания, где нужно именно сравнивать поля Ethernet II. Если `Ethernet II` не появляется ни в одном подходящем пакете, зафиксируйте это и уточните у преподавателя, какой интерфейс использовать.

## 5.2. Откройте Capture Options

1. Один раз щёлкните нужный интерфейс.
2. В верхнем меню выберите **Capture → Options…**.
3. Откроется окно **Capture Options**.
4. Оставайтесь на вкладке **Input**.

В таблице интерфейсов найдите выбранную строку.

## 5.3. Установите capture filter

В столбце **Capture Filter** дважды щёлкните ячейку выбранного интерфейса и введите:

```text
arp or udp port 53 or tcp port 53 or tcp port 80
```

Если в вашей версии окно выглядит немного иначе, найдите поле **Capture filter for selected interfaces** и введите тот же фильтр.

### Что мы сознательно НЕ записываем

Такой фильтр не должен записывать весь трафик ноутбука. Это уменьшает вероятность случайно собрать лишние данные других приложений.

### Что мы сознательно записываем

- ARP — если он появится естественным образом;
- классический DNS;
- TCP на порту 80 для учебного HTTP-запроса.

## 5.4. Начните захват

Нажмите **Start** в нижней части окна Capture Options.

Альтернативный путь в других версиях:

- выбрать интерфейс на стартовом экране;
- использовать **Capture → Start**.

После запуска строки начнут появляться в **Packet List**.

# 6. Создание учебного трафика

## 6.1. Сначала DNS

Откройте терминал/PowerShell **в той же операционной среде, трафик которой вы захватываете**.

Выполните:

```text
nslookup scanme.nmap.org
```

### Что делает `nslookup`

`nslookup` явно просит настроенный DNS-резолвер разрешить имя `scanme.nmap.org` в IP-адрес.

Это удобно для лабораторной работы, потому что мы создаём понятное событие DNS, которое затем ищем в Wireshark.

### Если команда `nslookup` не найдена

`nslookup` — отдельная диагностическая утилита DNS. На Windows и macOS она обычно уже доступна. В минимальной Linux-системе пакет может отсутствовать. Тогда установите его:

Ubuntu / Debian:

```bash
sudo apt install dnsutils
```

Arch Linux / Manjaro:

```bash
sudo pacman -S bind
```

Fedora:

```bash
sudo dnf install bind-utils
```

После установки снова выполните `nslookup scanme.nmap.org`.

> **Не копируйте найденный IP в следующую команду.** Результат `nslookup` нужен только для понимания работы DNS и последующего сравнения с Wireshark. HTTP-запрос ниже снова выполняется **по имени `scanme.nmap.org`**. Так мы видим естественную цепочку «имя → DNS → IP внутри пакета», а не работаем со списком числовых адресов.

## 6.2. Затем обычный HTTP-запрос

### Windows PowerShell / CMD

```powershell
curl.exe http://scanme.nmap.org/
```

### Linux / WSL / macOS

```bash
curl http://scanme.nmap.org/
```

### Что делает `curl`

`curl` — клиент для сетевых протоколов. Здесь он выполняет один обычный HTTP-запрос к веб-странице.

## Решение этапа 1. DNS — пример ожидаемого результата

### Что конкретно должно появиться на экране

> **Как читать примеры ниже:** значения в угловых скобках (`<...>`) — это не команды и не готовые адреса. Это места, где студент должен подставить значение, которое он увидел **в своём** Wireshark. Имя удалённого узла в командах остаётся `scanme.nmap.org`.


После фильтра `dns` в верхней панели **Packet List** должна остаться хотя бы одна строка запроса и, как правило, строка ответа. Условный пример:

```text
No.  Time      Source         Destination    Protocol  Info
12   3.214     <IP_вашего_ПК>      <IP_DNS_резолвера>  DNS  Standard query ... A scanme.nmap.org
13   3.232     <IP_DNS_резолвера>  <IP_вашего_ПК>      DNS  Standard query response ...
```

Это **не эталонные адреса**. В вашей сети DNS-резолвер может иметь другой IPv4, IPv6 или локальный адрес.

После выбора строки запроса в средней панели **Packet Details** ожидается логика примерно такого вида:

```text
Frame 12: ... bytes on wire
Ethernet II, Src: <MAC вашего интерфейса>, Dst: <MAC локального следующего узла>
Internet Protocol Version 4, Src: <IP вашего ПК>, Dst: <IP DNS-резолвера>
User Datagram Protocol, Src Port: <временный порт>, Dst Port: 53
Domain Name System (query)
    Queries
        scanme.nmap.org: type A, class IN
```

### Пример заполненной таблицы 1

| Поле | Пример |
|---|---|
| Номер кадра | `12` — условный номер в конкретном захвате |
| Source MAC | `<MAC_вашего_интерфейса>` |
| Destination MAC | `<MAC_следующего_локального_узла>` |
| EtherType | `IPv4 (0x0800)` — если DNS-пакет идёт внутри IPv4 |
| Source IP | `<IP_вашего_ПК>` |
| Destination IP | `<IP_DNS_резолвера>` |
| Транспортный протокол DNS | Обычно UDP; возможен TCP в отдельных ситуациях |
| Имя DNS-запроса | `scanme.nmap.org` |
| Тип DNS-записи | Часто `A` для IPv4; может также встретиться `AAAA` для IPv6 |

### Почему каждая ячейка заполнена именно так

- **Номер кадра** берётся из столбца `No.`. Он нужен для ссылки на конкретное событие внутри PCAPNG.
- **Source MAC** берётся из `Ethernet II → Source`. Это локальный отправитель данного Ethernet-кадра.
- **Destination MAC** берётся из `Ethernet II → Destination`. Это локальный получатель/следующий узел на данном канальном участке.
- **EtherType** объясняет, какой протокол инкапсулирован в Ethernet. `0x0800` означает IPv4.
- **Source IP** и **Destination IP** относятся уже к IP-уровню. Они не обязаны совпадать по смыслу с MAC-адресами.
- **UDP/TCP** показывает транспорт DNS. Классический небольшой запрос часто идёт по UDP 53.
- **Имя** берётся из дерева `Domain Name System → Queries`.
- **Тип A/AAAA** показывает, какой адрес клиент спрашивает: IPv4 или IPv6.

### Ответы на вопросы этапа 1

#### 1. Что такое DNS-резолвер и зачем он нужен вашему компьютеру?

**Ответ:** DNS-резолвер — компонент, который принимает вопрос о доменном имени и помогает получить соответствующий IP-адрес.

**Напоминание технологии:** приложениям удобнее использовать имена вроде `scanme.nmap.org`, а IP-маршрутизации нужен числовой адрес. DNS соединяет эти два представления.

**Обоснование:** без разрешения имени приложение не знает, к какому IP строить соединение. В PCAP мы видим, кому отправлен запрос и какой ответ получен. Это важно для ИБ, потому что недостоверный ответ может направить клиента к неправильному ресурсу.

#### 2. Почему DNS-имя и IP-адрес — разные сущности?

**Ответ:** имя — удобный логический идентификатор сервиса, IP — сетевой адрес, используемый для маршрутизации.

**Напоминание технологии:** одному имени могут соответствовать несколько IP, а IP может меняться из-за балансировки, миграции или архитектуры.

**Обоснование:** поэтому нельзя навсегда «прибить» безопасность только к одному IP без понимания архитектуры. Нужно проверять имя, адрес, сертификат и контекст.

#### 3. Что показывает Source MAC?

**Ответ:** локальный MAC-адрес отправителя выбранного Ethernet-кадра.

**Напоминание технологии:** MAC относится к канальному уровню Ethernet. Он действует на текущем локальном участке, а не описывает весь путь через Интернет.

#### 4. Что показывает Destination MAC?

**Ответ:** локальный MAC-адрес следующего получателя Ethernet-кадра на текущем участке.

**Обоснование:** если DNS-сервер находится за пределами локальной сети, Destination MAC обычно будет MAC локального шлюза/виртуального next hop, а не MAC удалённого DNS-сервера.

#### 5. Можно ли по одному Destination MAC сделать вывод о конечном сервере в Интернете?

**Ответ:** нет.

**Напоминание технологии:** маршрутизатор пересоздаёт канальный заголовок на каждом участке. Конечный IP может сохраняться, а Ethernet Source/Destination меняются от hop к hop.

#### 6. Почему EtherType важен?

**Ответ:** он помогает получателю и анализатору понять, как интерпретировать полезную нагрузку Ethernet.

**Пример:** `0x0800` → IPv4, `0x0806` → ARP, `0x86DD` → IPv6.

#### 7. Почему DNS-ответ — элемент сетевого доверия?

**Ответ:** именно он влияет на то, к какому адресу клиент направит последующее соединение.

**Обоснование:** привычное имя может остаться тем же, но неверный DNS-ответ изменит конечный адрес. Поэтому DNS — часть основания, на котором строится доверие к подключению.

#### 8. Какие ИБ-последствия возможны при неправильном IP?

**Ответ:** обращение к ложному ресурсу, раскрытие данных, ошибка целостности, отказ доступа или перенаправление процесса.

**Важно:** неправильный IP не всегда означает атаку. Возможна ошибка конфигурации, устаревшая запись, балансировка или аварийное переключение. Нужна дополнительная проверка.

## Решение этапа 2. TCP handshake — пример ожидаемого результата

### Что конкретно искать

После фильтра начального SYN должна остаться строка, где в `Info` есть `[SYN]` и Destination Port = 80.

Условный пример:

```text
No.  Source         Destination     Protocol  Info
20   <IP_вашего_ПК>       <IP_scanme_из_захвата>  TCP  <временный_порт> → 80 [SYN]
21   <IP_scanme_из_захвата> <IP_вашего_ПК>       TCP  80 → <временный_порт> [SYN, ACK]
22   <IP_вашего_ПК>       <IP_scanme_из_захвата>  TCP  <временный_порт> → 80 [ACK]
```

### Пример заполненной таблицы 2

| Шаг | Source IP | Destination IP | Source Port | Destination Port | Source MAC | Destination MAC | Флаги |
|---|---|---|---:|---:|---|---|---|
| SYN | `<IP_ПК>` | `<IP_scanme_из_захвата>` | `<эпhemeral>` | `80` | `<MAC_ПК/локального отправителя>` | `<MAC_next-hop>` | SYN |
| SYN,ACK | `<IP_scanme_из_захвата>` | `<IP_ПК>` | `80` | `<эпhemeral>` | `<MAC_next-hop>` | `<MAC_ПК/локального получателя>` | SYN, ACK |
| ACK | `<IP_ПК>` | `<IP_scanme_из_захвата>` | `<эпhemeral>` | `80` | `<MAC_ПК/локального отправителя>` | `<MAC_next-hop>` | ACK |

### Почему каждая ячейка таблицы заполнена именно так

- **Строка SYN.** Source IP — адрес клиента, потому что соединение начинает ваш компьютер. Destination IP — адрес веб-узла. Source Port — временный клиентский порт, а Destination Port — `80`, стандартная серверная точка обычного HTTP в этом упражнении. Флаг SYN означает начало согласования TCP-состояния. Source MAC относится к локальному отправителю, Destination MAC — к локальному next hop.
- **Строка SYN,ACK.** Направление обмена меняется: серверный IP становится Source, клиентский IP — Destination. Порт `80` теперь Source Port, а временный клиентский порт — Destination Port. Флаги SYN и ACK одновременно показывают, что удалённая сторона подтверждает запрос и синхронизирует свою сторону соединения. На локальном участке входящий Ethernet-кадр также имеет обратное направление MAC-адресов относительно исходящего кадра.
- **Строка ACK.** Клиент снова является источником и подтверждает полученный SYN,ACK. Поэтому IP и порты снова направлены от клиента к серверу, а активным смысловым флагом является ACK.
- **Почему IP и MAC в одной строке описывают разные устройства.** `<IP_scanme_из_захвата>` — конечное маршрутизируемое назначение. `<MAC_next-hop>` — адрес только следующего локального участника. Это не противоречие, а нормальная работа разных уровней сети.
- **Почему значения в угловых скобках не заменены «эталонными числами».** Временный порт, IP после DNS и MAC локального шлюза зависят от конкретной сети и захвата. В полном решении важна правильная логика чтения полей, а не подгонка под чужие адреса.

### Ответы на вопросы этапа 2

#### 1. Зачем TCP выполняет handshake?

**Ответ:** чтобы обе стороны согласовали начало TCP-соединения и начальные параметры состояния.

**Напоминание технологии:** TCP — протокол с состоянием. Он отслеживает последовательность данных и подтверждения, поэтому перед обменом создаётся контекст соединения.

#### 2. Что означает SYN?

**Ответ:** запрос на начало TCP-соединения и синхронизацию последовательностей.

#### 3. Что означает ACK?

**Ответ:** подтверждение получения ожидаемой части TCP-обмена.

**Важно для новичка:** ACK — не «разрешение безопасности». Это техническое подтверждение в TCP.

#### 4. Почему Source Port клиента обычно не 80?

**Ответ:** порт 80 — серверная точка HTTP. Клиенту нужен отдельный временный порт для конкретного исходящего соединения.

#### 5. Что такое временный клиентский порт?

**Ответ:** кратковременно выделенный ОС номер транспорта, который различает конкретную клиентскую сессию.

**Обоснование:** несколько браузерных соединений могут одновременно обращаться к одному серверу: разные исходные порты помогают ОС различать потоки.

#### 6. Почему Source/Destination меняются местами в ответе?

**Ответ:** потому что ответ идёт в обратном направлении. Сервер становится источником, клиент — назначением.

#### 7. Почему удалённый IP и Destination MAC могут относиться к разным устройствам?

**Ответ:** IP описывает конечное сетевое назначение, MAC — локальный следующий hop.

**Напоминание технологии:** Ethernet не переносит один и тот же MAC-заголовок через весь Интернет. Маршрутизаторы меняют канальную упаковку.

#### 8. Какой компонент обычно является локальным Destination MAC?

**Ответ:** default gateway/локальный маршрутизатор либо виртуальный next hop, если используется VPN/виртуальная сеть.

**Почему формулировка осторожная:** в разных архитектурах локальный L2-next-hop может отличаться, поэтому PCAP нужно трактовать вместе с конфигурацией интерфейса.

## Решение этапа 3. HTTP внутри Ethernet — пример ожидаемого результата

### Что должно быть видно

### Пример заполненной таблицы 3

| Поле | Пример |
|---|---|
| Номер кадра | `<номер HTTP request>` |
| HTTP method | `GET` |
| Host | `scanme.nmap.org` |
| URI | `/` |
| Source TCP port | `<временный порт клиента>` |
| Destination TCP port | `80` |
| Source IP | `<IP вашего ПК>` |
| Destination IP | `<IP scanme из вашего собственного DNS/HTTP-захвата>` |
| Source MAC | `<MAC локального отправителя>` |
| Destination MAC | `<MAC локального next hop>` |
| EtherType | Обычно `IPv4 (0x0800)`; при IPv6 будет другой тип |

### Почему каждая ячейка таблицы заполнена именно так

- **Номер кадра** берётся из столбца `No.` выбранной строки `http.request`; он нужен, чтобы другой человек мог быстро найти тот же сетевой факт в PCAPNG.
- **HTTP method `GET`** берётся из `Hypertext Transfer Protocol`. Это прикладное действие — запросить представление ресурса.
- **Host `scanme.nmap.org`** — имя веб-узла из HTTP-заголовка Host. Оно показывает, к какому логическому веб-хосту относится запрос, но само по себе не является криптографическим доказательством подлинности.
- **URI `/`** означает корневой путь веб-ресурса в нашем одном учебном запросе.
- **Source TCP port** — временный клиентский порт, назначенный ОС для конкретного соединения.
- **Destination TCP port `80`** — порт HTTP в этом упражнении, поэтому именно его `curl` использует для `http://...` без явного другого порта.
- **Source IP** — сетевой адрес клиента на выбранном пути; **Destination IP** — IP, к которому фактически строится HTTP-соединение после разрешения имени.
- **Source MAC** и **Destination MAC** берутся из Ethernet II и относятся к локальному канальному участку. Для удалённого сервера Destination MAC обычно будет MAC локального next hop, а не удалённой машины.
- **EtherType** говорит, какой сетевой протокол вложен в Ethernet. При IPv4 ожидается `0x0800`; при IPv6 значение будет другим, поэтому студент записывает фактическое поле.

**Связь технологий:** HTTP описывает действие приложения. TCP переносит байты между процессами. IP доставляет пакет между сетями. Ethernet доставляет его до следующего участника на локальном участке. Это и есть инкапсуляция: один пользовательский запрос одновременно имеет поля нескольких уровней.

### Ответы на вопросы этапа 3

#### 1. Почему HTTP внутри TCP, TCP внутри IP, IP внутри Ethernet?

**Ответ:** это результат инкапсуляции по уровням.

**Зачем технология так устроена:** каждый уровень решает свою задачу. Приложению не нужно самостоятельно управлять Ethernet, а Ethernet не нужно понимать смысл HTTP метода GET.

#### 2. Что такое инкапсуляция?

**Ответ:** добавление служебных заголовков нижних уровней вокруг данных верхнего уровня для передачи по сети.

#### 3. Почему HTTP-заголовки видны открытым текстом?

**Ответ:** в этой работе используется обычный HTTP без TLS-шифрования.

**ИБ-смысл:** это наглядно показывает, почему чувствительные данные нельзя передавать через незашифрованный HTTP.

#### 4. Почему нельзя использовать реальные логины/пароли?

**Ответ:** они могут попасть в PCAP открытым текстом и стать доступны любому, кто получит файл или имеет право наблюдать этот участок трафика.

#### 5. Какое свойство в первую очередь защищает TLS?

**Ответ:** конфиденциальность содержимого канала. TLS также даёт защиту целостности канала и проверку сертификата сервера, поэтому его роль шире одного свойства.

#### 6. Почему Ethernet Destination MAC не доказывает подлинность веб-сервера?

**Ответ:** это адрес локального следующего hop, а не криптографическое подтверждение удалённого сервиса.

#### 7. Как TLS-сертификат дополняет сетевые признаки?

**Ответ:** он позволяет клиенту проверить, что сервер предъявил сертификат для ожидаемого имени, построенный до доверенного удостоверяющего центра при обычной PKI-проверке.

**Важно:** корректный сертификат — сильный признак, но безопасность также зависит от доверенных CA, конечного устройства и приложения.

#### 8. Что можно считать фактом из кадра?

**Ответ:** конкретные зафиксированные поля: время, MAC, IP, порты, флаги, открытый HTTP-метод/Host и байты.

**Чего кадр не доказывает:** личность человека, законность действия, намерение, полную архитектуру и отсутствие событий вне точки захвата.

## Решение этапа 4. MAC против IP

### Пример заполнения

| Вопрос | Пример правильного ответа |
|---|---|
| Какой IP является конечным IP назначения? | `<IP_scanme_из_захвата>` — берётся из `Internet Protocol → Destination` |
| Какой MAC является Destination MAC? | `<MAC_next-hop>` — берётся из `Ethernet II → Destination` |
| Это MAC scanme.nmap.org? | Нет, обычно нет |
| Что обычно представляет этот MAC? | Локальный шлюз/маршрутизатор либо виртуальный next hop |
| Что может изменить картину? | VPN, виртуальный адаптер, контейнерная/виртуальная сеть, IPv6/другой link-layer |

### Почему каждая строка таблицы заполнена именно так

- **Конечный IP** берётся из поля `Internet Protocol → Destination`: IP относится к маршрутизируемой конечной точке.
- **Destination MAC** берётся из `Ethernet II → Destination`: MAC относится к локальной доставке этого конкретного кадра.
- **Ответ «это не MAC scanme»** основан на границе L2: удалённый сервер находится за маршрутизатором, поэтому его MAC не переносится через весь Интернет.
- **Локальный шлюз/next hop** указан как типичный получатель исходящего Ethernet-кадра. В VPN и виртуальных сетях роль next hop может выполнять виртуальный интерфейс.
- **Оговорка про архитектуру** обязательна: Wireshark показывает наблюдаемую точку, а не универсальную схему всех сетей.

### Ответы на вопросы этапа 4

#### 1. Почему маршрутизатор создаёт новый Ethernet-заголовок?

**Ответ:** Ethernet-адреса действуют только на конкретном канальном участке. Чтобы передать IP-пакет на следующий линк, маршрутизатор упаковывает его в новый кадр с MAC-адресами следующего участка.

#### 2. Почему IP и MAC не взаимозаменяемы?

**Ответ:** они работают на разных уровнях и отвечают на разные вопросы.

- IP: «какому сетевому узлу/адресу в маршрутизируемом пространстве предназначен пакет?»
- MAC: «какому участнику передать кадр на этом локальном линке?»

#### 3. Что такое next hop?

**Ответ:** следующий сетевой узел, которому текущая система передаёт пакет по выбранному маршруту.

#### 4. Почему MAC локален, а IP маршрутизируем?

**Ответ:** L2-доставка заканчивается на границе канального сегмента, а маршрутизаторы используют IP, чтобы продолжать путь между сетями.

#### 5. Как неверное IP ↔ MAC влияет на трафик?

**Ответ:** локальный кадр может уйти не тому интерфейсу, что создаёт риск недоступности, наблюдения или подмены дальнейшего обмена.

#### 6. Почему смена MAC шлюза — не готовое доказательство ARP-spoofing?

**Ответ:** потому что есть легитимные объяснения: замена оборудования, кластер/VRRP, failover, виртуализация, изменение сетевой архитектуры.

**Правильный ИБ-подход:** зафиксировать факт, сравнить с baseline, проверить ARP-таблицы, конфигурацию и журналы, а уже затем выбирать версию.

**Ответ:** агрегирует обмен между парами адресов/портов и помогает увидеть, кто с кем общался и сколько данных передавалось.

**Ответ:** Ethernet conversation связывает канальные адреса текущего участка, а TCP conversation — транспортные endpoint'ы с IP/портами для логического соединения приложения.

## Решение этапа 6. TCP retransmission

### Два правильных варианта результата

**Вариант А — фильтр пустой.** Для короткого стабильного соединения это совершенно нормально.

**Вариант Б — есть несколько строк.** Это тоже не означает автоматически атаку: Wi-Fi, временная потеря, перегрузка, переупорядочивание, особенности точки захвата могут дать такие признаки.

### Пример заполнения

|---|---|

| Что нужно дополнительно? | Метрики latency/error rate/RPS, загрузка канала и узлов, журналы сервиса, число источников, пользовательские симптомы, временная линия |

### Почему каждая строка таблицы заполнена именно так

- **Есть/нет retransmission** — фактический результат display filter; правильными могут быть оба варианта.
- **Количество** записывается из конкретного PCAPNG и не подменяется учебным числом.
- **DoS/DDoS = «нет, не доказано»**, потому что retransmission — сетевой симптом, а не классификация причины.
- **Дополнительные данные** включают RPS, latency, error rate, загрузку ресурсов и логи, поскольку доступность оценивается по всей цепочке сервиса, а не по одному полю TCP.

### Ответы на вопросы этапа 6

#### 1. Почему TCP повторяет данные в обычной сети?

**Ответ:** если ожидаемое подтверждение не пришло вовремя или анализ TCP указывает на пропуск, данные могут быть отправлены повторно для надёжности.

#### 2. Может ли Wi-Fi давать повторы без атаки?

**Ответ:** да. Радиопомехи, слабый сигнал, конкуренция за эфир и временные потери могут влиять на доставку.

#### 3. Почему несколько повторов не доказывают DoS?

**Ответ:** DoS — вывод о нарушении доступности из-за исчерпания ресурса/вредного воздействия. Retransmission — лишь сетевой симптом, имеющий много причин.

#### 4. Какие признаки сопоставлять?

**Ответ:** время события, RPS, latency, error rate, потери, загрузку канала, соединения, CPU/память, базу/очереди, источники и пользовательские жалобы.

#### 5. Как связаны latency, ошибки и повторные запросы?

**Ответ:** медленный ответ может вызвать timeout на клиенте; клиент повторяет запрос; повторы увеличивают нагрузку; это может усилить деградацию. Но для подтверждения такой цепочки нужна временная корреляция, а не один пакет.

## Решение этапа 7. ARP

### Если ARP не было

Правильная запись:

> «В коротком захвате ARP-кадры не наблюдались. Это не означает отсутствие ARP в сети: соответствие могло уже находиться в кэше, а capture filter/интервал не совпал с моментом ARP-обмена».

### Если ARP Request был

Условный пример:

```text
Ethernet II
    Destination: ff:ff:ff:ff:ff:ff
    Source: <MAC отправителя>
Address Resolution Protocol (request)
    Sender IP address: <IP отправителя>
    Sender MAC address: <MAC отправителя>
    Target IP address: <локальный IP, MAC которого ищут>
```

### Пример заполненной таблицы 5

| Поле | Пример |
|---|---|
| ARP наблюдался? | Да / Нет по факту |
| Destination MAC | Для классического ARP Request часто `ff:ff:ff:ff:ff:ff` |
| Sender IP | IP узла, задающего вопрос |
| Sender MAC | MAC этого узла |
| Target IP | локальный IPv4, MAC которого нужно узнать |
| Почему broadcast | отправитель ещё не знает индивидуальный MAC владельца Target IP |

### Почему каждая строка таблицы заполнена именно так

- **Номер кадра** — ссылка на конкретное наблюдение в PCAPNG.
- **Destination MAC `ff:ff:ff:ff:ff:ff`** характерен для обычного ARP Request, потому что отправитель ещё не знает MAC искомого IPv4-адреса и спрашивает локальный broadcast domain.
- **Source MAC/IP** показывают, кто сформировал запрос на наблюдаемом локальном участке.
- **Target IP** — адрес, для которого ищется локальное MAC-соответствие.
- Если ARP отсутствует, таблицу не нужно выдумывать: это означает только, что в выбранном интервале соответствующий ARP-обмен не попал в захват.

### Ответы на вопросы этапа 7

#### 1. Для чего ARP нужен IPv4-узлу?

**Ответ:** чтобы сопоставить локальный IPv4 next hop с MAC-адресом и сформировать Ethernet-кадр.

#### 2. Почему Request часто broadcast?

**Ответ:** индивидуальный MAC пока неизвестен, поэтому вопрос доставляется всем участникам локального broadcast domain.

#### 3. Почему ARP не ищет MAC удалённого сервера через Интернет?

**Ответ:** ARP локален. Для удалённой сети компьютеру нужен MAC своего next hop — обычно шлюза. Дальнейшие маршрутизаторы сами решают локальные L2-сопоставления на своих участках.

#### 4. Какую роль играет шлюз?

**Ответ:** принимает IP-пакет, предназначенный другой сети, и маршрутизирует его дальше.

#### 5. Почему изменения IP ↔ MAC важны?

**Ответ:** они могут означать штатную перестройку или проблему доверия. Сравнение с baseline и журналами помогает отличить варианты.

## Кейс 1. У шлюза неожиданно изменился MAC-адрес

### Термины перед кейсом

**Шлюз по умолчанию** — локальный маршрутизатор, которому рабочая станция передаёт трафик в другие сети.

**ARP** — механизм сопоставления IPv4-адреса локального узла и его MAC-адреса.

**Baseline / базовая линия** — зафиксированное нормальное состояние, с которым сравнивают текущее.

**DHCP** — протокол автоматической выдачи сетевых параметров. В расследовании он полезен, потому что помогает понять, какие IP, шлюз и DNS получил клиент.

**Сертификат** — цифровой объект, который в HTTPS/TLS помогает клиенту проверить заявленное имя сервера и цепочку доверия.

### Ситуация

В учебной документации для рабочей станции зафиксирован **ожидаемый MAC-адрес локального шлюза**. Числовой IPv4 в кейсе намеренно не приводится: студент работает не со списком адресов, а с наблюдаемыми полями собственного захвата.

Утром аналитик открыл короткий PCAPNG, созданный во время обычного обращения к `scanme.nmap.org`, и заметил: у исходящих Ethernet II кадров Destination MAC отличается от ранее зафиксированного baseline. При этом настройка шлюза в ОС выглядит неизменной.

В журнале изменений нет записи о замене сетевого оборудования. Сеть продолжает работать. Неизвестно, связано ли изменение MAC с резервированием, виртуализацией, штатным изменением сети, ошибкой или нежелательным вмешательством.

2. Почему удалённый IP и локальный Destination MAC не обязаны принадлежать одному устройству?

### Полное решение кейса 1

#### Заполненная таблица

| Поле | Ответ |
|---|---|
| Основной актив | Корректное сетевое направление исходящего трафика через ожидаемый локальный next hop при обращении к `scanme.nmap.org` |
| Подтверждённое сетевое наблюдение | В захвате исходящие кадры имеют новый Destination MAC, отличный от baseline |
| Возможный риск | Неверное локальное соответствие/неожиданная смена next hop может перенаправить трафик или ослабить доверие к маршруту |
| Альтернативная штатная версия | Замена маршрутизатора, VRRP/HA/failover (штатное резервирование и переключение шлюза), изменение виртуального шлюза, обновление сетевой архитектуры |

#### Почему каждая ячейка заполнена именно так

- **Основной актив** — корректное направление трафика через доверенный шлюз и связанные пользовательские сессии. MAC-адрес — только технический признак; защищается не «набор цифр», а надёжность сетевого взаимодействия и данные, которые через него проходят.
- **Подтверждённое наблюдение** — новый Destination MAC. Это значение буквально присутствует в Ethernet II кадрах, поэтому его можно назвать фактом без предположения о причине.
- **Возможный риск** — перенаправление или нарушение локального next hop. Мы пишем «возможный», потому что один неожиданный MAC ещё не показывает, было ли воздействие вредоносным.
- **Альтернативная штатная версия** включает HA/VRRP/failover, замену оборудования и виртуализацию. Эти технологии могут легитимно изменить фактический MAC при сохранении одного логического шлюза.
- **Что ещё не доказано** отделено специально: Wireshark не содержит поля «это ARP-spoofing». Для такого вывода нужны независимые признаки и исключение штатных причин.
- **Нужные цифровые следы** выбраны по уровням: neighbor/ARP table показывает локальное соответствие IP↔MAC; MAC table коммутатора — порт, где замечен MAC; DHCP и конфигурация шлюза — ожидаемые параметры; change log — плановые изменения; сертификат — независимый признак конечного веб-ресурса.
- **Первая мера** — сохранить доказательства и проверить baseline до разрушительных действий. Массовая очистка кэшей или перезапуск оборудования может стереть полезный временной контекст.

#### Ответы на вопросы

##### 1. Какие факты подтверждены, а что гипотеза?

**Факты:** baseline содержит один ожидаемый MAC локального шлюза; текущий PCAP содержит другой Destination MAC; настройка шлюза в ОС выглядит неизменной; обращения к `scanme.nmap.org` продолжают проходить.

**Гипотезы:** ARP-spoofing, MITM, факт перехвата данных, злоумышленник или конкретная причина изменения MAC.

**Напоминание технологии:** Wireshark показывает кадр Ethernet, но не происхождение всех сетевых изменений. Поэтому описание причин требует корреляции.

##### 2. Почему удалённый IP и локальный MAC разные?

Потому что IP относится к маршрутизируемому назначению, а Destination MAC — к локальному next hop. Для внешнего сайта этим next hop обычно является шлюз.

##### 3. Почему смена MAC требует проверки?

Потому что меняется один из параметров, на которых строится локальная доставка. Если baseline считается утверждённым, необъяснённое отклонение снижает доверие к пути.

##### 4. Доказывает ли новый MAC ARP-spoofing?

Нет. ARP-spoofing — конкретная версия причины. Для неё нужны дополнительные признаки: противоречивые ARP-ответы, изменения neighbor table, неизвестный MAC на неожиданном порту, отсутствие штатной HA-конфигурации и т. д.

##### 5. Какие штатные причины возможны?

Замена оборудования, failover, виртуальный IP с несколькими MAC в архитектуре, VRRP/HSRP-подобная схема, изменение виртуальной сети, перенос шлюза.

##### 6. Какие данные запросить?

- ARP/neighbor table клиента;
- MAC address table коммутатора;
- журналы портов;
- change management;
- конфигурацию HA/виртуального шлюза;
- DHCP-параметры;
- DNS-ответ и, при отдельной HTTPS-проверке, сертификат ожидаемого сервиса.

**Зачем:** каждый источник проверяет отдельное звено цепочки доверия.

##### 7. Какие свойства ИБ потенциально затронуты?

**Конфиденциальность** — если трафик реально прошёл через нежелательный узел; **целостность** — если ответы могли изменяться; **доступность** — если изменение вызывает нестабильность.

Это пока риски, а не доказанные последствия.

##### 8. Что делать первым?

Сохранить PCAPNG, зафиксировать время, интерфейс, IP/MAC и текущую конфигурацию; проверить утверждённую сетевую схему. Не нужно сразу очищать все таблицы и перезапускать оборудование — это может уничтожить полезный контекст.

## Кейс 2. Одно имя — разные DNS-ответы

### Термины перед кейсом

**DNS** — система сопоставления имени сервиса с IP-адресом.

**DNS resolver** — компонент, которому клиент отправляет DNS-запрос.

**DNS-spoofing** — защитный термин для ситуации, где клиент получает недостоверное соответствие имени и адреса. Сам по себе неожиданный DNS-ответ ещё не доказывает злонамеренную подмену.

**TLS-сертификат** — цифровой сертификат, который помогает клиенту проверить заявленную подлинность HTTPS-сервера.

### Ситуация

Два студента в разное время выполняют одинаковый учебный запрос имени `scanme.nmap.org`. В двух сохранённых PCAPNG DNS-ответы содержат разные числовые адреса. Числовые значения в кейсе намеренно не приводятся: они рассматриваются только как наблюдаемые результаты DNS.

Преподаватель просит определить, означает ли различие автоматическую подмену DNS. Дополнительно известно, что один из студентов при отдельном обращении по HTTPS увидел предупреждение о сертификате, а другой — нет. Документации о причине различия адресов пока нет. Этот кейс **аналитический**: не нужно создавать дополнительную нагрузку или пытаться воспроизводить подозрительное поведение.

### Полное решение кейса 2

#### Заполненная таблица

| Поле | Ответ |
|---|---|
| Проверяемый параметр доверия | DNS-соответствие имени `scanme.nmap.org` и фактического адреса из каждого захвата |
| Подтверждённый факт | В двух PCAPNG для имени `scanme.nmap.org` наблюдаются разные DNS-ответы; предупреждение сертификата отмечено только в одном случае |
| Возможный риск | Возможное направление клиента к неожиданной конечной точке; при неверной подлинности ресурса — риск раскрытия данных |
| Что не доказано | Злонамеренный DNS-spoofing, компрометация DNS-сервера, факт кражи учётных данных |
| Дополнительный признак | TLS-сертификат, его имя/SAN, цепочка доверия и соответствие ожидаемому сервису |
| Нужные журналы | DNS query/response logs, конфигурация зон, change log, DHCP-параметры DNS, proxy/firewall, сертификаты/веб-логи |
| Первичная мера | Не игнорировать предупреждение, не передавать чувствительные данные и проверить источник DNS-ответа, сертификат и архитектурную причину различия |

#### Почему каждая ячейка заполнена именно так

- **Проверяемый параметр доверия — DNS-соответствие.** В условии прямо зафиксировано, что одно имя разрешается в разные IP, поэтому сначала исследуется механизм DNS, а не, например, загрузка CPU сервера.
- **Подтверждённый факт** сформулирован только через наблюдения: разные ответы DNS и предупреждение сертификата. Здесь нет слова «атака», потому что причина ещё не установлена.
- **Возможный риск** связан с направлением трафика. Если IP ведёт не к утверждённому ресурсу, пользователь может передать данные не той конечной точке.
- **Что не доказано** отделено специально: разные DNS-ответы могут быть следствием split-DNS, балансировки, миграции или ошибки администратора. **Split-DNS** — архитектура, где одно имя намеренно имеет разные ответы в разных сетевых зонах.
- **Дополнительный признак — TLS-сертификат**, потому что это независимая проверка ожидаемого имени HTTPS-сервера. DNS говорит «куда идти», а сертификат помогает проверить «с кем установлено защищённое соединение».
- **Журналы** выбраны по цепочке события: DHCP сообщает, какой resolver получил клиент; DNS-журнал — какой ответ был выдан; proxy/firewall — куда ушёл трафик; веб-журнал — какая конечная система приняла запрос.
- **Первичная мера** не обвиняет и не разрушает инфраструктуру: сначала прекращаем передачу чувствительных данных через сомнительную точку и собираем подтверждения.

#### Ответы на вопросы

##### 1. Что проверять первой?

DNS, потому что именно различие в разрешении одного имени уже зафиксировано как расхождение параметра направления.

**Напоминание:** resolver получает ответ, а клиент затем строит соединение к указанному IP.

##### 2. Что доказывает различие ответов?

Только то, что клиенты получили разные сетевые адреса для одного имени в двух контекстах. Это факт сетевой конфигурации/ответа.

##### 3. Доказывает ли это атаку?

Нет. Возможны split-DNS (намеренно разные DNS-ответы в разных сетевых зонах), балансировка, миграция, резервирование или ошибка администрирования. Если архитектурного объяснения нет, событие требует расследования.

##### 4. Почему сертификат важен?

TLS-сертификат — независимый признак конечной точки. Если имя сервиса ожидаемое, а сертификат выдан другому имени или не строит доверенную цепочку, возникает дополнительное расхождение.

##### 5. Какие журналы нужны?

DNS-журнал покажет, какой сервер дал ответ; DHCP — какой resolver получил клиент; change log — кто менял записи; firewall/proxy — куда реально устанавливались соединения; веб-лог — какой сервер принимал обращения.

##### 6. Как связана конфиденциальность?

Если ложный ресурс получает логин, документы или служебные данные, информация раскрывается неразрешённой стороне. Поэтому риск возникает до доказанного «взлома».

##### 7. Почему нельзя игнорировать сертификат?

Потому что пользователь теряет один из ключевых механизмов проверки подлинности HTTPS-конечной точки. Нажатие «продолжить» превращает важное предупреждение в слепое доверие.

##### 8. Осторожный вывод

> «Подтверждено расхождение DNS-ответов между сегментами и предупреждение TLS-сертификата в одном сегменте. Это создаёт риск обращения к неутверждённой конечной точке. Причина — штатная архитектура, ошибка конфигурации или подмена — пока не установлена и требует проверки DNS-зон, DHCP-параметров, сертификата и сетевых журналов».

## Кейс 3. В сегменте резко вырос broadcast ARP

### Термины перед кейсом

**Broadcast** — локальная передача кадра всем участникам broadcast domain.

**ARP Request** часто передаётся broadcast, когда отправитель ищет MAC по локальному IPv4.

**Деградация** — сервис ещё работает, но хуже нормы: растут задержки, ошибки или нестабильность.

**DoS** — нарушение доступности за счёт исчерпания ресурса. Термин нельзя назначать только по одному большому числу пакетов.

**CPU (Central Processing Unit)** — процессор. Его загрузка показывает только один ресурс сервера; нормальный CPU не означает, что сеть, очередь, база данных и другие компоненты тоже в норме.

**Broadcast domain** — область локальной сети, в пределах которой широковещательный Ethernet-кадр доставляется множеству участников.

### Ситуация

В одном учебном сегменте сотрудники жалуются на медленное открытие внутренних ресурсов.

Короткий PCAP показывает, что значительная часть кадров — ARP Request с Destination MAC `ff:ff:ff:ff:ff:ff`. Многие запросы повторяются. В другом сегменте такой картины нет. Сервер приложений по внутреннему мониторингу не показывает высокой загрузки CPU.

|---|---|
| Основной симптом | Медленная работа внутренних ресурсов только в одном сегменте |
| Наблюдаемая технология | Большое число broadcast ARP Request |
| Возможное узкое место | Локальный broadcast domain, канал/коммутатор/клиенты, обрабатывающие избыточный broadcast |

#### Почему каждая ячейка заполнена именно так

- **Основной симптом** взят из пользовательского наблюдения: внутренние ресурсы стали работать медленно только в одном сегменте. Это признак деградации, а не ещё причина.
- **Наблюдаемая технология — broadcast ARP**, потому что именно такие кадры доминируют в коротком PCAP. Wireshark показывает факт сетевого обмена, а не намерение отправителя.
- **Возможное узкое место** связано с L2-сегментом: broadcast получают многие участники, поэтому нагрузка может приходиться на канал, коммутатор, точку доступа или конечные узлы.
- **ИБ-риск** сформулирован как риск доступности. Мы не утверждаем компрометацию конфиденциальности, потому что в условии нет факта чтения данных.
- **Альтернативные причины** включены потому, что массовый ARP бывает и без атаки: L2-петля, конфликт адресов, ошибочная маска, массовый reboot или инвентаризационный инструмент.
- **Что не доказано — DoS и умышленность.** Чтобы назвать событие атакой, нужны дополнительные данные о характере источников, ресурсе, временной линии и контексте.
- **Следующие источники данных** выбраны для проверки локального уровня: STP и MAC table показывают состояние коммутируемой сети, DHCP — адресную конфигурацию, интерфейсные счётчики — ошибки и загрузку.

#### Ответы на вопросы

##### 1. Почему broadcast влияет на многих?

Broadcast доставляется всем участникам соответствующего L2 broadcast domain. Каждый узел и сетевое оборудование должны принять и обработать такой кадр на своём уровне.

##### 2. Что является фактом деградации?

Пользовательские жалобы + различие поведения между сегментами + необычно большая доля ARP в PCAP. Однако точные пороги «много» должны сравниваться с baseline.

##### 3. Почему нормальный CPU сервера не исключает сеть?

Доступность зависит от цепочки ресурсов. Сервер может быть свободен, но пакеты могут задерживаться/теряться до него или клиенты могут тратить ресурсы на лишний broadcast.

##### 4. Можно ли назвать это DoS?

Нет. DoS подразумевает вывод о нарушении доступности через исчерпание ресурса; намерение и механизм ещё не доказаны. Здесь корректно говорить «аномальный broadcast и деградация сегмента».

##### 5. Какие альтернативы?

Ошибочная L2-петля, malfunction устройства, DHCP/маска, массовый reboot, адресный конфликт, инвентаризационный инструмент, некорректная виртуальная сеть.

##### 6. Какие ресурсы могут быть перегружены?

Пропускная способность локального канала, CPU коммутатора/точки доступа, очереди сетевого оборудования, обработка кадров на конечных узлах.

##### 7. Что даёт Wireshark?

Protocol Hierarchy показывает долю ARP; Statistics → Endpoints/Conversations помогает определить активные MAC; временная последовательность показывает частоту и повторяемость. Но для портов коммутатора нужны журналы самого оборудования.

##### 8. Какие меры до установления причины?

Сохранить PCAP и статистику, локализовать затронутый VLAN/сегмент, проверить петли/STP и неизвестные устройства, при необходимости ограничить проблемный порт по процедуре. Не следует хаотично перезапускать всё оборудование.

## Кейс 4. PCAPNG приложили к публичной задаче

### Термины перед кейсом

**PCAP/PCAPNG** — файл сетевого захвата.

**HTTP header / HTTP-заголовок** — служебное поле HTTP-запроса или ответа. Некоторые заголовки могут содержать cookies, токены авторизации и другие чувствительные данные.

**Cookie** — небольшое значение, которое веб-клиент хранит и отправляет серверу; часть cookies может использоваться для сессии.

**Bearer token** — секретный токен, предъявление которого может давать доступ от имени владельца токена.

**Capture filter / фильтр захвата** — правило, которое ограничивает данные ещё **до записи в PCAPNG**. Например, фильтр может разрешить записывать только DNS и TCP/80. Если фильтра нет, Wireshark может сохранить намного больше фонового трафика рабочего компьютера.

**Репозиторий** — хранилище файлов и истории изменений проекта, часто управляемое Git. Публичный репозиторий доступен широкому кругу пользователей, поэтому чувствительный PCAPNG туда помещать нельзя.

**Сессия** — логический период работы пользователя с сервисом после входа. Сессионная cookie может быть частью механизма, который связывает последующие HTTP-запросы с уже аутентифицированным пользователем.

### Ситуация

Администратор расследовал ошибку старого внутреннего HTTP-сервиса и записал 10 минут трафика без capture filter. Затем приложил `incident_full.pcapng` к публично доступной задаче в репозитории.

Позже коллега открыл файл в Wireshark и заметил незашифрованные HTTP-заголовки, внутренние домены и cookie сессии тестового пользователя. Пока неизвестно, использовал ли кто-то эти данные.

### Полное решение кейса 4

#### Заполненная таблица

| Поле | Ответ |
|---|---|
| Информационный актив | `incident_full.pcapng` и содержащаяся в нём сетевая телеметрия/секреты |
| Подтверждённое событие | Файл с лишним трафиком опубликован в публичной задаче; внутри видны HTTP-заголовки, внутренние домены и cookie |

| Профилактическая мера | Минимальный capture filter, короткий интервал, отдельный учебный аккаунт, HTTPS, sanitization и закрытый канал передачи PCAP |

#### Почему каждая ячейка заполнена именно так

- **Информационный актив** — сам PCAPNG и его содержимое. Файл ценен, потому что позволяет повторно восстановить сетевые поля и последовательность обмена.
- **Подтверждённое событие** ограничено фактом публичной публикации и найденными полями. Мы не пишем «данные украдены», потому что скачивание и использование ещё нужно доказать.
- **Чувствительные данные** перечислены по наблюдаемому содержимому. Сессионная cookie особенно важна, потому что в некоторых системах знание действующей cookie может позволить представить запрос как часть чужой сессии.
- **Нарушенное свойство — конфиденциальность**, потому что доступ к данным расширился за пределы разрешённого круга. Целостность и доступность по условию не подтверждены как нарушенные.
- **Что неизвестно** вынесено отдельно, чтобы не смешивать экспозицию с доказанной эксплуатацией.
- **Первая мера** включает ограничение доступа и отзыв сессионных данных: удаление файла уменьшает дальнейшее раскрытие, а отзыв секрета снижает риск использования уже полученной копии.
- **Профилактика** строится по принципу минимизации: capture filter уменьшает собираемый объём, короткий интервал уменьшает экспозицию, HTTPS снижает видимость прикладного содержимого, санитизация и закрытый канал защищают артефакт после захвата.

#### Ответы на вопросы

##### 1. Почему PCAPNG — информационный актив?

Потому что ценность содержится не только в файле как контейнере, но и в записанной телеметрии: адресах, именах, последовательности действий, HTTP-полях и возможных секретах.

**Напоминание технологии:** PCAPNG сохраняет сырые пакеты. То, что в интерфейсе Wireshark выглядит как удобные поля, физически находится в файле и может быть повторно разобрано другим человеком.

##### 2. Что такое capture filter и как повлияло его отсутствие?

Capture filter ограничивает **что вообще записывается**. Без него 10-минутный захват рабочего ноутбука мог включить трафик почты, мессенджеров, внутренних сервисов и других процессов, а не только проблемный HTTP.

##### 3. Что чувствительно?

Cookie сессии — потенциальный секрет; внутренние домены раскрывают инфраструктуру; URL и заголовки могут содержать идентификаторы; незашифрованный HTTP может содержать данные приложения.

##### 4. Какое свойство CIA?

Конфиденциальность, потому что данные оказались доступны шире разрешённого круга.

##### 5. Можно ли утверждать использование cookie?

Нет. Публичная экспозиция подтверждена, а эксплуатация — отдельный факт, который требует логов входа, истории скачиваний и последующих сессий.

##### 6. Что делать сразу?

1. Ограничить доступ к файлу.
2. Зафиксировать URL/время/историю публикации.
3. Отозвать затронутые сессии/токены.
4. Проверить историю Git и вложения, а не только текущую версию.
5. Определить, какие ещё данные попали в PCAP.
6. Проверить журналы доступа к репозиторию.

##### 7. Почему удаления последнего коммита недостаточно?

Git хранит историю. Секретный файл может оставаться в предыдущих commit-объектах, forks, mirrors, кэшах или уже скачанных копиях. Поэтому необходимы отзыв секретов и корректная очистка истории по процедуре.

##### 8. Как безопасно захватывать дальше?

Использовать минимальный BPF capture filter, короткий таймер, отдельную тестовую сессию, не вводить реальные секреты по HTTP, хранить PCAP в закрытом месте и перед передачей проверять его на чувствительные поля.

## Кейс 5. Главная страница работает, отчёт возвращает 503

### Термины перед кейсом

**HTTP 503 Service Unavailable** — ответ приложения/веб-инфраструктуры, означающий, что сервис в данный момент не может нормально обработать запрос.

**Partial outage / частичный отказ** — часть функций работает, но важный пользовательский сценарий не выполняется.

**TCP retransmission** — повторная TCP-передача данных.

**Latency** — задержка/время ожидания ответа.

**Error rate** — доля запросов, завершившихся ошибками.

**Метрика** — числовой показатель состояния системы, который измеряется во времени. Для доступности полезны RPS, latency, error rate, загрузка ресурсов и состояние очередей.

**Узкое место** — ресурс или компонент, который первым достигает своего предела и начинает тормозить весь сценарий.

**Graceful degradation / контролируемая деградация** — режим, при котором второстепенную тяжёлую функцию можно временно ограничить, чтобы сохранить критичные операции сервиса.

### Ситуация

Пользователь открывает главную страницу внутренней аналитической системы без заметной задержки. Но при запуске большого отчёта через несколько секунд получает HTTP 503.

Wireshark в коротком захвате показывает стабильное TCP-соединение к веб-сервису и HTTP-ответ 503. Фильтр retransmission почти ничего не показывает. В логах поддержки есть жалобы только на отчёты; вход и просмотр коротких карточек работают.

#### Заполненная таблица

#### Почему каждая ячейка заполнена именно так

- **Тип нарушения доступности — частичный отказ/деградация**, потому что главная страница и короткие операции работают, а значимый сценарий отчёта завершается ошибкой.
- **Факт из PCAP** формулируется строго: TCP-соединение существует и наблюдается HTTP 503. Это то, что действительно видно в захвате.
- **Что PCAP помогает ослабить** — версию о массовых TCP-потерях на наблюдаемом участке, потому что признаков retransmission мало. Слово «ослабить» важнее слова «исключить»: точка захвата не видит всю инфраструктуру.
- **Что PCAP не объясняет** — внутреннюю причину 503. HTTP-код может сформировать приложение, reverse proxy, load balancer или другой промежуточный веб-компонент.
- **Возможное узкое место** перечислено по цепочке тяжёлого отчёта: backend, база, очередь, внешний API. Сам факт рабочего TCP не подтверждает здоровье этих компонентов.
- **Дополнительные метрики** нужны, чтобы связать пользовательский симптом с ресурсом: RPS показывает поток запросов, p95/p99 — хвост задержек, error rate — долю ошибок, метрики базы/очереди — внутреннее ожидание.
- **Защитная мера** соответствует контролируемой деградации: тяжёлые отчёты ограничиваются или ставятся в очередь, а лёгкие критичные действия остаются доступными.

#### Ответы на вопросы

##### 1. Полностью ли доступен сервис?

Нет. Доступность оценивается по полезному пользовательскому сценарию. Если отчёт — значимая функция и он не выполняется, есть частичный отказ даже при рабочей главной странице.

##### 2. Почему отсутствие retransmission важно?

Оно уменьшает поддержку версии о явной массовой потере TCP-пакетов на наблюдаемом участке. Но не исключает проблемы вне точки захвата и не доказывает, что сеть идеальна.

##### 3. Доказывает ли 503 причину?

Нет. `503 Service Unavailable` — прикладной/веб-инфраструктурный симптом. Его могут вернуть приложение, proxy, load balancer или gateway по разным причинам.

##### 4. Что проверять дальше?

Путь отчёта: reverse proxy (веб-посредник, принимающий запрос перед приложением) / load balancer (распределитель нагрузки) → приложение → очередь/worker (фоновый обработчик задач) → база → внешние API/хранилище. Сопоставлять время PCAP с логами и метриками.

##### 5. Может ли тяжёлый отчёт быть опаснее множества лёгких запросов?

Да. Стоимость операции важнее голого количества: один отчёт может держать DB connection, CPU, память и блокировки значительно дольше простого GET.

##### 6. Какие метрики нужны?

RPS, latency p95/p99, error rate, число соединений, очередь, DB locks/slow queries, пул соединений, время внешних зависимостей.

##### 7. Почему нельзя объявить DoS/DDoS?

Потому что есть частичная недоступность, но нет доказательства умышленного исчерпания ресурса и характера источников. Возможна обычная ошибка архитектуры или легитимный пик тяжёлых запросов.

##### 8. Что предложить как graceful degradation?

Сохранить вход и лёгкие карточки; тяжёлые отчёты временно переводить в очередь, ограничивать частоту, показывать статус «отчёт готовится», использовать кэш и приоритеты критичных функций.

# 17. Итоговые вопросы для обсуждения

1. Чем MAC-адрес отличается от IP-адреса по роли в сети?
2. Почему удалённый IP обычно не означает, что его MAC должен появиться в локальном Ethernet-кадре?
3. Почему DNS является частью цепочки доверия?
4. Почему успешное TCP-соединение ещё не означает, что пользователь подключился к правильному сервису?
5. Что дополнительно даёт TLS-сертификат?
6. Почему Wireshark показывает факты сетевого обмена, но не всегда позволяет установить намерение субъекта?
7. Почему PCAP нужно защищать как обычный чувствительный файл?
8. Чем capture filter отличается от display filter?
9. Почему несколько retransmission не являются доказательством DoS?
10. Как связаны наблюдаемость сети и способность расследовать инциденты?


## Ответы на итоговые вопросы

### 1. Чем MAC отличается от IP?

MAC служит локальной канальной доставке Ethernet, IP — маршрутизируемой сетевой адресации. Один нельзя использовать как полноценную замену другого.

### 2. Почему MAC удалённого сервера обычно не виден локально?

Потому что ваш ПК формирует Ethernet-кадр до следующего hop, а маршрутизаторы меняют L2-заголовок на каждом участке. Конечный IP остаётся ориентиром для L3-маршрутизации.

### 3. Почему DNS — часть цепочки доверия?

DNS выбирает сетевой адрес для имени. Ошибочный ответ может направить правильный пользовательский запрос к неправильному узлу.

### 4. Почему TCP-успех не подтверждает правильный сервис?

TCP проверяет транспортное соединение, а не организационную подлинность приложения. Можно успешно установить TCP к ошибочному/ложному серверу.

### 5. Что даёт TLS-сертификат?

Дополнительный криптографически проверяемый признак того, что сервер предъявил сертификат для ожидаемого имени в рамках доверенной PKI-цепочки. Он также используется внутри TLS для защищённого канала.

### 6. Почему Wireshark не устанавливает намерение?

Пакеты показывают действия протоколов. Один и тот же технический запрос может возникнуть из-за штатного приложения, ошибки, теста или злоупотребления. Намерение требует контекста и иных доказательств.

### 7. Почему PCAP защищают?

Потому что он может содержать сетевую карту действий, имена, адреса, незашифрованные данные и секреты. Это полноценный информационный актив.

### 8. Capture filter против display filter

Capture filter определяет, что попадёт в файл. Display filter работает уже после записи и только меняет представление на экране.

### 9. Почему retransmission не равен DoS?

Повтор TCP — симптом доставки. Причины включают обычные потери, Wi-Fi, перегрузку, задержку и особенности захвата. DoS — более широкий вывод об исчерпании доступности и требует дополнительных признаков.

### 10. Как наблюдаемость помогает расследованию?

Она связывает PCAP, DNS/DHCP/VPN/приложение, метрики и временную линию. Чем больше согласованных источников, тем меньше приходится строить выводы на догадках.

### Пример итогового вывода для версии с решением

В ходе работы был выполнен короткий захват собственного сетевого трафика в графическом Wireshark. Сначала DNS преобразовал имя `scanme.nmap.org` в IP-адрес, после чего клиент смог построить соединение к найденной сетевой точке. На канальном уровне Wireshark показал Ethernet II и локальные MAC-адреса, а на сетевом уровне — IP-адреса отправителя и удалённого назначения. Сравнение этих уровней показало, что Destination MAC исходящего кадра к удалённому ресурсу обычно относится не к самому интернет-серверу, а к локальному next hop, например шлюзу. TCP создал состояние соединения через последовательность SYN → SYN,ACK → ACK, после чего в потоке был передан HTTP-запрос. Обычный HTTP позволил увидеть метод и заголовок Host открытым текстом, что наглядно демонстрирует риск передачи чувствительных данных без TLS. DNS-ответ, MAC локального next hop, IP, маршрут и сертификат следует рассматривать как разные признаки сетевого доверия, а не как взаимозаменяемые доказательства. Наличие отдельного retransmission, необычного MAC или различия DNS само по себе не доказывает атаку: вывод должен подтверждаться журналами, конфигурацией, метриками и контекстом. Анализ Protocol Hierarchy показал, что один пользовательский сценарий опирается сразу на несколько вложенных технологий. Файл PCAPNG необходимо считать информационным активом, поскольку он может сохранять адреса, имена, HTTP-поля и другие чувствительные сведения. Поэтому безопасная работа с Wireshark включает не только чтение пакетов, но и минимизацию захвата, осторожную интерпретацию и защищённое хранение результата.
