# Практическая работа: создание и проверка SHA-256-хэшей с помощью OpenSSL

*Полная версия*

> **Главная идея:** хэш помогает проверить, совпадает ли текущее состояние файла с ранее зафиксированным эталоном. Хэш **не шифрует** файл, **не скрывает** его содержимое и сам по себе **не доказывает**, кто создал файл. В этой работе основной алгоритм — **SHA-256**.

> **Как использовать эталон:** точный SHA-256 зависит от точных байтов файла. Linux/WSL/macOS-команда `printf` из методики создаёт предсказуемые байты, но PowerShell может использовать другой формат перевода строк/кодировку в зависимости от версии. Поэтому в Windows оценивается **логика**: один и тот же файл даёт тот же хэш; изменённый файл — другой. Нельзя заставлять студента копировать хэш из этой версии.

# 3. Короткая теория

## 3.1. Что такое хэш-функция

**Хэш-функция** — математический алгоритм, который получает данные произвольного размера и создаёт значение фиксированной длины.

Например:

```text
файл → SHA-256 → хэш
```

Для SHA-256 результат содержит 256 бит. В привычном шестнадцатеричном виде это 64 символа.

Пример формы результата:

```text
212e217506f48a920fc4608b3ae7d4e3b1a68142326fe90e70641374e8259b72
```

Этот пример показывает **формат**, а не значение, которое нужно копировать в отчёт.

## 3.2. Что такое хэш, digest и контрольная сумма

В этой работе используются близкие по смыслу слова:

- **хэш** — результат работы хэш-функции;
- **message digest / digest** — «цифровой отпечаток» данных; OpenSSL использует термин `dgst`;
- **контрольный хэш** — хэш, сохранённый для последующего сравнения;
- **эталонный хэш** — контрольное значение, которому мы доверяем при проверке.

Слово **checksum / контрольная сумма** часто используется шире. В учебном отчёте лучше писать точно: **SHA-256-хэш файла**.

## 3.3. Почему одинаковый файл даёт одинаковый хэш

Хэш-функция детерминирована: одинаковые байты на входе дают одинаковый результат.

```text
Файл A → SHA-256 → H1
тот же Файл A → SHA-256 → H1
```

Если байты изменились:

```text
Файл A* → SHA-256 → H2
```

и `H2` должен отличаться от `H1`.

## 3.4. Почему даже маленькое изменение важно

Хэш считается **по байтам**, а не «по смыслу текста».

Измениться может:

- буква;
- цифра;
- пробел;
- перевод строки;
- кодировка;
- скрытый служебный байт.

Поэтому два документа, которые визуально кажутся одинаковыми, иногда имеют разные хэши.

## 3.5. Что такое avalanche effect

**Avalanche effect / лавинный эффект** — полезное свойство криптографической хэш-функции: небольшое изменение входных данных приводит к сильно отличающемуся результату.

Это не означает, что «изменился один символ хэша». Обычно изменяется большая часть отображаемого значения.

## 3.6. Хэш не является шифрованием

**Шифрование** предназначено для сокрытия содержания так, чтобы уполномоченная сторона могла восстановить исходные данные с помощью ключа.

**Хэширование** предназначено для получения контрольного значения. Нормальной операции «расшифровать SHA-256 обратно в файл» нет.

Упрощённо:

| Механизм | Главная задача | Можно штатно получить исходный файл обратно? |
|---|---|---|
| Шифрование | Конфиденциальность | Да, с правильным ключом |
| Хэширование | Контроль состояния/целостности | Нет |

## 3.7. Хэш и целостность

**Целостность** — свойство информации, связанное с сохранением правильного и ожидаемого состояния данных.

Упрощённая проверка:

```text
1. Вычислили SHA-256 исходного файла.
2. Сохранили хэш как эталон.
3. Позже снова вычислили SHA-256.
4. Сравнили значения.
```

Если значения различаются, байты файлов различаются.

## 3.8. Очень важное ограничение: совпадение хэшей не равно доказанной подлинности

Представьте, что злоумышленник смог заменить:

- сам файл;
- и текстовый файл рядом с ним, где записан «правильный» SHA-256.

Тогда проверка может показать совпадение, хотя оба объекта были заменены.

Поэтому есть два разных вопроса:

1. **Совпадает ли файл с контрольным значением?**
2. **Можно ли доверять самому контрольному значению?**

Для второго вопроса могут применяться цифровая подпись, доверенный HTTPS-источник, отдельный защищённый канал, PKI и организационные процедуры.

## 3.9. Что такое цифровая подпись

**Цифровая подпись** — криптографический механизм, который связывает данные с операцией, выполненной соответствующим закрытым ключом.

В этой работе мы подпись не создаём. Она нужна для понимания ограничения обычного хэша: подпись может дать дополнительную проверяемую связь с ключом, тогда как один SHA-256 такого свойства не создаёт.

## 3.10. Что такое коллизия

**Коллизия** — ситуация, когда два разных входных сообщения имеют одинаковый хэш.

Поэтому формулировка «хэш всегда абсолютно уникален» технически неверна.

Для современных криптографических алгоритмов задача состоит в том, чтобы практический поиск коллизий был чрезвычайно трудным. SHA-256 применяется именно как современный базовый вариант для подобных учебных проверок.

## 3.11. Почему в работе не используется MD5 как основной алгоритм

MD5 исторически встречается в старых системах и иногда используется для незащитных технических задач, но его нельзя выбирать как современный механизм защиты от намеренной подмены.

## 3.12. Почему SHA-1 тоже не выбирается как основной алгоритм

SHA-1 устарел для новых задач криптографической защиты. Современная практика должна использовать более сильные семейства, например SHA-2 или SHA-3. В этой лабораторной выбран SHA-256 из семейства SHA-2.

# 4. Что такое OpenSSL

**OpenSSL** — набор криптографических библиотек и консольных инструментов.

В этой работе нужен его командный интерфейс:

```text
openssl
```

Команда для хэширования будет выглядеть так:

```bash
openssl dgst -sha256 имя_файла
```

Разберём её:

- `openssl` — запускаем программу OpenSSL;
- `dgst` — работаем с message digest, то есть хэшем;
- `-sha256` — явно выбираем SHA-256;
- `имя_файла` — данные, для которых вычисляется хэш.

> OpenSSL умеет намного больше: работать с TLS, сертификатами, ключами, подписями. В этой лабораторной мы используем только безопасную операцию вычисления хэша.

# 7. Этап 1. Создайте новый учебный файл

В этой работе используется рабочий сценарий **контроля версии текстового манифеста выпуска**.

**Manifest / манифест** — небольшой файл, описывающий объект: название, версию, состояние или другие служебные свойства.

## Linux / WSL / macOS

```bash
printf 'Artifact: payroll-export\nVersion: v1\nStatus: approved\n' > release_manifest.txt
```

Покажите содержимое:

```bash
cat release_manifest.txt
```

## Windows PowerShell

```powershell
@(
  "Artifact: payroll-export",
  "Version: v1",
  "Status: approved"
) | Set-Content -Encoding utf8 release_manifest.txt
```

Покажите содержимое:

```powershell
Get-Content release_manifest.txt
```

### Что должно быть по смыслу

Файл должен содержать три строки:

```text
Artifact: payroll-export
Version: v1
Status: approved
```

### Вопросы

1. Что в этой работе считается входными данными хэш-функции?
2. Хэшируется «смысл текста» или конкретные байты файла?
3. Почему кодировка и перевод строки могут влиять на хэш?
4. Что такое манифест в данном учебном сценарии?


## Решение этапа 1

После создания файла студент должен увидеть три строки. На Linux/WSL/macOS при использовании указанного `printf`:

```text
Artifact: payroll-export
Version: v1
Status: approved
```

**Что проверяет преподаватель:** файл реально создан, студент понимает, что OpenSSL будет хэшировать не «смысл отчёта», а байты `release_manifest.txt`.

### Ответы

**1. Что является входными данными?**  
Байты файла `release_manifest.txt`. Технология здесь — криптографическая хэш-функция SHA-256. Она принимает последовательность байтов и вычисляет digest фиксированной длины.

**2. Хэшируется смысл или байты?**  
Байты. SHA-256 не понимает слова `Artifact`, `Version` или `approved`. Для алгоритма это последовательность двоичных значений.

**3. Почему кодировка/перевод строки важны?**  
Потому что они меняют байтовое представление. Даже если редактор показывает визуально одинаковый текст, разные служебные байты могут привести к другому SHA-256.

**4. Что такое манифест?**  
В нашем сценарии это маленький служебный файл с описанием выпуска: объект, версия, статус. Реальные manifest-файлы могут содержать намного больше данных, но логика контроля целостности та же.

### Вопросы

1. Что означает `dgst` в команде OpenSSL?
2. Зачем мы явно указываем `-sha256`?
3. Почему SHA-256 имеет 64 hex-символа, хотя в названии указано 256?
4. Можно ли по этому хэшу восстановить содержимое файла штатной обратной командой?
5. Скрывает ли этот хэш содержимое файла от человека, который уже имеет сам файл?


## Решение этапа 2

### Пример результата

На Linux/WSL/macOS при **точном** `printf` из этапа 1 один возможный эталонный вывод:

```text
SHA2-256(release_manifest.txt)= 212e217506f48a920fc4608b3ae7d4e3b1a68142326fe90e70641374e8259b72
```

Разные версии OpenSSL могут написать слева `SHA256` или `SHA2-256`. Это не ошибка.

### Заполненная таблица 1 — пример

| Параметр | Пример ответа |
|---|---|
| Имя файла | `release_manifest.txt` |
| Алгоритм | SHA-256 |
| Длина хэша в hex-символах | 64 |
| Первый SHA-256 | фактическое 64-символьное значение студента |
| Версия OpenSSL | результат `openssl version` |

### Почему 64 символа

Один hex-символ кодирует 4 бита. Поэтому:

```text
256 / 4 = 64
```

### Ответы

**1. Что означает `dgst`?**  
Это подкоманда OpenSSL для операций с message digest. В нашем случае она вычисляет цифровой отпечаток файла.

**2. Зачем `-sha256`?**  
Чтобы явно выбрать алгоритм SHA-256. Это делает команду понятной и воспроизводимой, даже если OpenSSL имеет настройки по умолчанию.

**3. Почему 64 hex-символа?**  
SHA-256 создаёт 256 бит. Hex представляет каждые 4 бита одним символом, поэтому получается 64 символа.

**4. Можно ли штатно восстановить файл?**  
Нет. SHA-256 не является обратимым шифрованием. По digest не существует команды «расшифровать обратно `release_manifest.txt`».

**5. Скрывает ли хэш сам файл?**  
Нет. Если человек уже имеет файл, хэш ничего от него не скрывает. Хэш используется для сравнения состояния, а не для конфиденциальности.

# 9. Этап 3. Измените только версию и пересчитайте хэш

Теперь создадим вторую версию манифеста.

# 13. Этап 7. Сохраните эталонный SHA-256

## Linux / WSL

openssl dgst -sha256 -r service_config.txt | awk '{print $1}' > service_config.sha256.ref

На Linux/macOS `awk` берёт первое поле строки — сам хэш — и не сохраняет имя файла.

### Что делает PowerShell `-split '\s+'`

Он разбивает строку по пробельным символам. `[0]` означает: взять первый элемент, то есть сам хэш.

# 14. Этап 8. Проверьте неизменённый файл

Сначала **ничего не меняйте** в `service_config.txt`.

## Linux / WSL

```bash
openssl dgst -sha256 -r service_config.txt | awk '{print $1}' > service_config.sha256.current
cmp -s service_config.sha256.ref service_config.sha256.current && echo "OK: HASH MATCH" || echo "ALERT: HASH MISMATCH"
```

## macOS

```bash
"$OPENSSL" dgst -sha256 -r service_config.txt | awk '{print $1}' > service_config.sha256.current
cmp -s service_config.sha256.ref service_config.sha256.current && echo "OK: HASH MATCH" || echo "ALERT: HASH MISMATCH"
```

## Windows PowerShell

```powershell
$CurrentHash = ((openssl dgst -sha256 -r service_config.txt) -split '\s+')[0]
$CurrentHash | Set-Content service_config.sha256.current

if ((Get-Content service_config.sha256.ref).Trim() -eq (Get-Content service_config.sha256.current).Trim()) {
    "OK: HASH MATCH"
} else {
    "ALERT: HASH MISMATCH"
}
```

### Термины

**Reference / эталон** — ранее сохранённое контрольное значение.

**Current / текущее значение** — хэш, вычисленный во время проверки.

**Match / совпадение** — значения одинаковы.

**Mismatch / несовпадение** — значения различаются.

### Вопросы

1. Что означает `HASH MATCH` в данной лаборатории?
2. Доказывает ли совпадение, что файл «безопасен вообще»?
3. Доказывает ли совпадение, кто является автором файла?
4. Почему важно знать, когда и кем был создан эталон?


## Решение этапа 8

Ожидаемый результат:

```text
OK: HASH MATCH
```

Это означает:

```text
текущий SHA-256 == сохранённый SHA-256
```

### Ответы

**1. Что означает match?**  
Проверяемый файл имеет тот же SHA-256, что и состояние, для которого был создан эталон. В практической задаче это сильный признак совпадения байтов с зафиксированным состоянием.

**2. «Файл безопасен вообще»?**  
Нет. В файле может быть логическая ошибка или даже заранее заложенное нежелательное содержимое. Хэш не анализирует смысл и безопасность кода.

**3. Кто автор?**  
Хэш не подтверждает автора. Для связи с ключом/издателем применяются подписи и доверенная инфраструктура ключей.

**4. Почему важно знать происхождение эталона?**  
Если эталон создан после несанкционированной модификации или получен из недоверенного источника, совпадение подтвердит не то состояние, которое организация считала правильным.

### Вопросы

1. Почему два разных инструмента должны дать одинаковый SHA-256 для одинаковых байтов?
2. Что нужно сравнивать: всю строку вывода или само значение digest?

## Решение этапа 10

Для одного и того же файла OpenSSL и системный инструмент должны вычислить одно и то же SHA-256-значение. Оболочка вывода может отличаться.

### Ответы

**1. Почему одинаковый SHA-256?**  
Алгоритм стандартизирован. Инструменты должны реализовывать один и тот же математический алгоритм над одинаковыми байтами.

**2. Что сравнивать?**  
Сам 64-символьный digest. Имя файла, подписи столбцов и регистр букв могут отличаться.

**3. Почему важно одинаковое состояние файла?**  
Если между двумя командами файл изменён, инструменты уже получают разные входные данные, и сравнение теряет смысл.

## Кейс 1. Файл и SHA-256 лежат в одной общей папке

### Термины

**Общая папка** — хранилище, доступное нескольким пользователям.

### Вопросы

1. Что подтверждает совпадение хэшей?

**5. Что в лаборатории?**  
SHA-256 как современный базовый digest для контроля целостности.

## Подробные ответы на итоговые вопросы

**1. Хэш-функция** преобразует данные произвольной длины в digest фиксированной длины.  
**2. Digest** — цифровой отпечаток сообщения/файла.  
**3. SHA-256 не шифрует**, потому что не предназначен для обратного восстановления данных.  
**4. Фиксированная длина** означает, что SHA-256 выдаёт 256 бит независимо от размера входного файла.  
**5. 64 hex-символа** получаются потому, что один hex-символ представляет 4 бита.  
**6. Лавинный эффект** означает сильное изменение выхода при небольшом изменении входа.  
**7. Коллизия** — два разных входа с одним digest.  
**8. MD5** не подходит как современный единственный механизм защиты от намеренной подмены из-за практической слабости коллизионной стойкости.  
**9. SHA-1** выводится из применения для новых задач криптографической защиты; для новых решений выбирают SHA-2/SHA-3 по требованиям.  
**10. Match** показывает соответствие текущего digest эталону.  
**11. Mismatch** показывает различие состояния данных.  
**12. Mismatch не равен атаке**, потому что изменение может быть штатным или случайным.  
**13. Эталон должен быть доверенным**, иначе проверяется неизвестно какое состояние.  
**14. Если заменяются файл и эталон**, простая проверка может показать ложное чувство корректности.  
**15. Цифровая подпись** добавляет проверяемую криптографическую связь данных с закрытым ключом.  
**16. Имя файла — метаданные**, оно не описывает все байты содержимого.  
**17. Перевод строки меняет байты**, значит меняется SHA-256.  
**18. Перекрёстная проверка** показывает, что алгоритм независим от конкретной утилиты.  
**19. `curl` получает ресурс**, OpenSSL вычисляет digest сохранённого файла.  
**20. Хэш не превращает HTTP в TLS**, потому что это разные уровни и задачи защиты.

## Пример итогового заключения

В работе для контроля состояния файлов использовался криптографический алгоритм SHA-256 и консольный инструмент OpenSSL. Для исходного манифеста был вычислен digest фиксированной длины. После изменения версии файла SHA-256 изменился, что показало чувствительность хэш-функции к изменению входных байтов. Повторное вычисление для неизменённого файла дало тот же результат, поскольку SHA-256 детерминирован. Во второй части контрольный SHA-256 был сохранён как эталон и затем использован для проверки текущего состояния конфигурационного файла. Для неизменённого файла проверка дала `HASH MATCH`, а после изменения параметра — `HASH MISMATCH`. Несовпадение хэша позволяет утверждать, что текущие данные отличаются от эталонного состояния, но не позволяет автоматически объявить изменение атакой. Для установления причины нужны журналы, история версий и рабочий контекст. Также было показано, что доверие к эталонному хэшу является отдельной задачей: если эталон можно подменить вместе с файлом, обычного сравнения недостаточно. Хэширование не является шифрованием и не подтверждает автора документа. Для более сильной проверки происхождения используются цифровые подписи и доверенная инфраструктура ключей.

# 22. Типовые ошибки новичка

## Ошибка 1. «Хэш — это зашифрованный файл»

Нет. Хэш — контрольное значение, а не обратимо зашифрованная копия.

## Ошибка 2. «У двух разных файлов хэш всегда гарантированно разный»

Нельзя давать абсолютную математическую гарантию: существуют коллизии. Практическая безопасность зависит от стойкости выбранной функции.

## Ошибка 3. «Совпало — значит файл точно от правильного автора»

Нет. Нужно отдельно доверять эталонному значению и источнику.

## Ошибка 4. «Не совпало — значит нас взломали»

Нет. Причиной могут быть нормальная новая версия, повреждение, другая кодировка, ошибка копирования или иное изменение.

## Ошибка 5. Копировать хэш из методички

Хэш должен быть вычислен для **вашего фактического файла**.

## Ошибка 6. Сравнивать всю строку OpenSSL и Get-FileHash

Сравнивайте само шестнадцатеричное значение. Формат оболочки может отличаться.

## Ошибка 7. Использовать MD5/SHA-1 по привычке в новой защитной задаче

Наличие команды не означает, что алгоритм подходит для новой криптографической защиты.
