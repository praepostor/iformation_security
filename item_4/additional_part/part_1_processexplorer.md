# Анализ процессов и защитный мониторинг с Process Explorer

> **Практический смысл:** научиться смотреть на процесс не как на «непонятную строку в диспетчере задач», а как на объект, у которого есть имя, PID, родитель, путь запуска, командная строка, пользователь, цифровая подпись, открытые файлы, модули и сетевые соединения. Эти сведения помогают отличать обычную работу системы от ситуации, которую нужно дополнительно проверить.

> **Главное правило ИБ:** неизвестный процесс, высокая нагрузка, отсутствие подписи или сетевое соединение **сами по себе не доказывают вредоносность**. Вывод строится по совокупности признаков и контексту.

---

# 1. Что будет сделано в работе

В ходе практики вы:

1. разберётесь, что такое процесс, PID, PPID, родительский и дочерний процесс;
2. установите Process Explorer на Windows из официального источника;
3. поймёте, почему Process Explorer нельзя нативно установить в Linux, macOS и внутрь WSL;
4. научитесь получать аналогичные сведения в консоли на Windows, Linux, WSL и macOS;
5. создадите безопасный учебный процесс и исследуете его;
6. восстановите цепочку parent → child;
7. определите путь к исполняемому файлу и командную строку;
8. проверите цифровую подпись там, где она применима;
9. вычислите SHA-256 исполняемого файла;
10. увидите открытый файловый дескриптор/handle;
11. изучите загруженные модули на Windows;
12. создадите **одно безопасное HTTP-обращение только к `http://scanme.nmap.org/`** и свяжете его с процессом;
13. научитесь отделять факт от индикатора и от гипотезы;
14. разберёте рабочие кейсы;
15. подготовите краткое аналитическое заключение.

---

# 2. Безопасные границы

Работа предназначена для **наблюдения за собственной учебной системой**.

Не нужно:

- завершать неизвестные системные процессы;
- приостанавливать системные потоки;
- закрывать чужие handles;
- изменять чужие процессы;
- сканировать внешние системы;
- подбирать пароли;
- загружать рабочие файлы в сторонние сервисы проверки;
- использовать VirusTotal с автоматической отправкой неизвестных файлов;
- исследовать чужие компьютеры;
- работать с заданным преподавателем списком IP-адресов.

Если в сетевом этапе требуется внешний ресурс, используется только:

```text
http://scanme.nmap.org/
```

В отчёте не требуется фиксировать числовой удалённый IP-адрес. Нас интересует связь:

```text
процесс → сетевое соединение → учебный домен scanme.nmap.org
```

# 3. Важная техническая оговорка: Process Explorer и консоль

## 3.1. Что такое Process Explorer

**Process Explorer** — утилита Microsoft Sysinternals для Windows. Она показывает активные процессы и помогает исследовать:

- дерево процессов;
- пользователя процесса;
- путь к исполняемому файлу;
- командную строку;
- сведения о цифровой подписи;
- производительность;
- открытые handles;
- загруженные DLL;
- сетевые endpoints процесса.

В верхней части окна Process Explorer отображается список процессов. Нижняя панель может показывать handles либо DLL для выбранного процесса.

## 3.2. Process Explorer — не консольная программа

Это принципиально важно.

Process Explorer — **графическое Windows-приложение**. Официальной нативной версии Process Explorer для Linux, macOS или Linux-среды WSL нет.

Поэтому технически корректная схема этой работы такая:

| Среда | Что используем |
|---|---|
| Windows | настоящий Process Explorer + PowerShell для создания безопасных объектов и проверки результатов |
| WSL | Process Explorer запускается на стороне Windows; Linux-процессы внутри WSL изучаются Linux-командами |
| Linux | консольные средства `ps`, `/proc`, `lsof`, `sha256sum` и др.; это аналоги по изучаемым данным, но не Process Explorer |
| macOS | консольные `ps`, `lsof`, `codesign`, `shasum` и др.; это не Process Explorer |

> **Нельзя писать в отчёте:** «я установил Process Explorer на Linux». Корректно: «Process Explorer не имеет нативной Linux-версии; для аналогичного анализа использованы системные консольные средства Linux».

# 4. Термины: что именно мы наблюдаем

## 4.1. Программа и процесс — не одно и то же

**Программа** — исполняемый файл или набор кода на диске.

**Процесс** — выполняющийся экземпляр программы в операционной системе.

Пример:

```text
powershell.exe на диске → программа
запущенный powershell.exe с PID 1234 → процесс
```

Один и тот же исполняемый файл может быть запущен несколько раз и создать несколько процессов с разными PID.

## 4.2. PID

**PID (Process Identifier)** — идентификатор процесса.

Это число, которое операционная система использует для различения активных процессов.

Важно:

- PID не является постоянным идентификатором программы;
- после завершения процесса его PID позже может быть использован другим процессом;
- поэтому PID всегда нужно связывать со временем наблюдения.

## 4.3. PPID

**PPID (Parent Process Identifier)** — PID родительского процесса.

Он помогает понять, какой процесс запустил исследуемый процесс.

## 4.4. Родительский и дочерний процесс

Если процесс A запускает процесс B:

```text
Process A
   └── Process B
```

A — **parent / родитель**, B — **child / дочерний процесс**.

Дерево процессов полезно потому, что имя конечного процесса без контекста иногда мало что говорит. Нам важно знать, **как он появился**.

## 4.5. Исполняемый файл

**Executable / исполняемый файл** — файл, код которого запускается как программа.

В Windows это часто `.exe`, но процессы могут быть связаны и с другими типами компонентов.

## 4.6. Полный путь

**Путь к файлу** показывает, где исполняемый файл находится на диске.

Пример логики:

```text
имя: helper.exe
путь: C:\Program Files\Vendor\helper.exe
```

и

```text
имя: helper.exe
путь: C:\Users\...\Downloads\helper.exe
```

— это два разных файла, даже если имя одинаковое.

Необычный путь — **признак для проверки**, но не готовый диагноз.

## 4.7. Command line / командная строка

**Командная строка процесса** — команда и аргументы, с которыми процесс был запущен.

Она помогает понять не только «какая программа», но и «что ей поручили выполнить».

Например, два процесса PowerShell могут выполнять совершенно разные задачи.

## 4.8. User / пользователь процесса

Процесс выполняется в определённом **security context / контексте безопасности**.

Для новичка достаточно понимать: важно знать, под какой учётной записью работает процесс, потому что от этого зависят его права.

## 4.9. Digital signature / цифровая подпись исполняемого файла

Цифровая подпись помогает проверить криптографическую связь файла с издателем и обнаружить изменение подписанного содержимого.

Важно:

- наличие корректной подписи — полезный признак доверия;
- отсутствие подписи **не равно malware**;
- корректно подписанная программа **не гарантирует**, что её использование в конкретном контексте безопасно;
- название `Company Name` без криптографической проверки подписи само по себе не является доказательством издателя.

## 4.10. Hash / хэш

**SHA-256** — криптографический отпечаток файла.

Хэш полезен для идентификации состояния файла и сопоставления с ранее зафиксированным эталоном.

Хэш сам по себе:

- не говорит, что файл безопасен;
- не показывает, кто его запустил;
- не доказывает злой умысел.

## 4.11. Handle / дескриптор

**Handle** в Windows — ссылка процесса на объект операционной системы: файл, ключ реестра, событие, процесс и др.

Если приложение открыло файл, процесс обычно получает handle к нему.

На Linux/macOS близкое по учебному смыслу понятие — **file descriptor (FD)**, файловый дескриптор.

## 4.12. DLL / библиотека

**DLL (Dynamic-Link Library)** — динамически подключаемая библиотека Windows.

Процесс может загружать множество DLL. Они содержат функции, которые процесс использует во время работы.

Загруженная DLL сама по себе не означает проблему. Анализируется её путь, издатель, подпись и связь с программой.

## 4.13. Socket / сетевой сокет

**Сокет** — программная конечная точка сетевого взаимодействия.

Процесс может открыть сокет, чтобы установить сетевое соединение.

Сетевой факт отвечает на вопрос:

```text
процесс работал с сетью?
```

Но не отвечает автоматически на вопрос:

```text
это вредоносная передача данных?
```

## 4.14. CPU и память

**CPU usage** показывает, какую долю вычислительного времени использует процесс.

**Memory / память** показывает, сколько памяти связано с работой процесса.

Высокое потребление ресурсов может быть связано с:

- законной тяжёлой задачей;
- ошибкой программы;
- зависанием;
- обновлением;
- компрессией;
- нежелательной активностью.

То есть высокая нагрузка — сигнал, но не доказательство атаки.

# 5. Как Process Explorer связан с защитой информации

В рамках методов и средств защиты Process Explorer относится прежде всего к слою:

```text
наблюдение → диагностика → проверка → реагирование
```

Он не заменяет:

- антивирус;
- EDR;
- firewall;
- IDS/IPS;
- контроль доступа;
- резервное копирование;
- организационные процедуры.

Он помогает получить **контекст процесса**.

Например:

```text
неизвестный процесс
        ↓
путь запуска
        ↓
родитель
        ↓
командная строка
        ↓
подпись / хэш
        ↓
handles / DLL
        ↓
сетевой факт
        ↓
контекст пользователя и времени
        ↓
предварительный вывод
```

Это соответствует Defense in Depth: Process Explorer является одним диагностическим слоем, а не всей защитой.

# 6. Установка: Windows

## 6.1. Какой источник использовать

Используйте только официальный Microsoft Sysinternals.

Для практики удобнее скачать **Sysinternals Suite**, потому что в нём есть:

- Process Explorer;
- PsList — консольный список и дерево процессов;
- Handle — консольный просмотр handles;
- Sigcheck — консольная проверка подписи/сведений файла;
- ListDLLs — консольный просмотр загруженных DLL;
- Tcpvcon — консольный вариант TCPView;
- Autorunsc — консольный просмотр автозапуска.

Мы не будем использовать опасные команды изменения процессов. Нужны только функции наблюдения.

## 6.2. Откройте PowerShell

Нажмите:

```text
Пуск → введите PowerShell → открыть Windows Terminal / PowerShell
```

Для скачивания административные права не нужны.

## 6.3. Создайте папку

```powershell
$Sysinternals = "$HOME\Tools\Sysinternals"
New-Item -ItemType Directory -Force $Sysinternals | Out-Null
```

Проверьте:

```powershell
$Sysinternals
```

## 6.4. Скачайте официальный архив

```powershell
$Zip = "$env:TEMP\SysinternalsSuite.zip"
Invoke-WebRequest -Uri "https://download.sysinternals.com/files/SysinternalsSuite.zip" -OutFile $Zip
```

### Что означает команда

- `Invoke-WebRequest` — PowerShell-команда для HTTP/HTTPS-загрузки;
- `-Uri` — адрес ресурса;
- `-OutFile` — куда сохранить файл;
- `$env:TEMP` — временная папка текущего пользователя.

## 6.5. Распакуйте

```powershell
Expand-Archive -Path $Zip -DestinationPath $Sysinternals -Force
```

## 6.6. Убедитесь, что Process Explorer есть и выберите подходящий файл

Сначала выведите все варианты Process Explorer из официального архива:

```powershell
Get-ChildItem $Sysinternals -Filter "procexp*.exe" |
    Select-Object Name, FullName
```

В Sysinternals могут присутствовать варианты для разных архитектур процессора. Чтобы новичку не выбирать файл вручную и не привязываться только к x64, создайте переменную `$ProcExpExe`:

```powershell
$ProcExpExe = if ($env:PROCESSOR_ARCHITECTURE -eq 'ARM64' -and (Test-Path "$Sysinternals\procexp64a.exe")) {
    "$Sysinternals\procexp64a.exe"
} elseif ($env:PROCESSOR_ARCHITECTURE -eq 'AMD64' -and (Test-Path "$Sysinternals\procexp64.exe")) {
    "$Sysinternals\procexp64.exe"
} else {
    "$Sysinternals\procexp.exe"
}

$ProcExpExe
```

### Что такое архитектура процессора

**Архитектура процессора** — семейство команд, которое понимает процессор и операционная система. На современных Windows-компьютерах чаще встречаются x64 (`AMD64`) и ARM64.

Для учебной работы не нужно запоминать имена всех бинарных файлов: команда выше выбирает нативный вариант, если он присутствует, и использует обычный `procexp.exe` как запасной вариант.

> На официальной странице Sysinternals Suite Microsoft также публикует отдельную ARM64-сборку. Если учебный компьютер работает на Windows ARM64 и политика организации требует нативные ARM64-инструменты, используйте именно официальный ARM64-пакет или вариант, предоставленный администратором.

### Важное требование по Windows

На актуальной официальной странице Microsoft для текущего Process Explorer указаны поддерживаемые клиентские системы **Windows 11 и выше**, а серверные — **Windows Server 2016 и выше**. Если у вас Windows 10, актуальная версия может запускаться, но Microsoft уже не указывает Windows 10 как поддерживаемую клиентскую ОС. В учебной среде используйте версию и ОС, разрешённые преподавателем или организацией.

## 6.7. Проверьте цифровую подпись файла Process Explorer

```powershell
Get-AuthenticodeSignature $ProcExpExe |
    Select-Object Status, StatusMessage,
        @{Name='Signer';Expression={$_.SignerCertificate.Subject}}
```

### Что такое Authenticode

**Authenticode** — технология Windows для проверки цифровой подписи исполняемых файлов и скриптов.

Ожидается, что официальный бинарный файл Microsoft имеет корректную подпись. В отчёт запишите фактический `Status`.

> Если статус отличается от ожидаемого, не запускайте случайно скачанный файл. Сначала перепроверьте источник загрузки.

## 6.8. Запустите Process Explorer из PowerShell

```powershell
Start-Process $ProcExpExe
```

При первом запуске может появиться лицензионное окно Sysinternals. Прочитайте его и подтвердите запуск только если вы используете официальный инструмент.

### Нужен ли запуск от администратора

Для части сведений о системных процессах обычных пользовательских прав может быть недостаточно.

Если преподаватель разрешил повышенный режим на учебном компьютере:

```powershell
Start-Process $ProcExpExe -Verb RunAs
```

`-Verb RunAs` запрашивает запуск с повышенными правами через UAC.

Для большинства учебных шагов достаточно исследовать собственный процесс без вмешательства в системные процессы.

## 6.9. Подготовьте пути к консольным утилитам Sysinternals

Чтобы далее не привязываться к конкретному имени `*64.exe` или `*64a.exe`, используйте небольшую безопасную функцию выбора файла:

```powershell
function Get-SysinternalsTool {
    param([Parameter(Mandatory)][string]$BaseName)

    $preferred = if ($env:PROCESSOR_ARCHITECTURE -eq 'ARM64') {
        "${BaseName}64a.exe"
    } elseif ($env:PROCESSOR_ARCHITECTURE -eq 'AMD64') {
        "${BaseName}64.exe"
    } else {
        "${BaseName}.exe"
    }

    $preferredPath = Join-Path $Sysinternals $preferred
    if (Test-Path $preferredPath) {
        return $preferredPath
    }

    $fallbackPath = Join-Path $Sysinternals "${BaseName}.exe"
    if (Test-Path $fallbackPath) {
        return $fallbackPath
    }

    $candidate = Get-ChildItem $Sysinternals -Filter "$BaseName*.exe" -ErrorAction SilentlyContinue |
        Select-Object -First 1 -ExpandProperty FullName

    if ($candidate) {
        return $candidate
    }

    throw "Не найдена утилита Sysinternals: $BaseName"
}

$SigcheckExe = Get-SysinternalsTool 'sigcheck'
$HandleExe   = Get-SysinternalsTool 'handle'
$ListDllsExe = Get-SysinternalsTool 'listdlls'

$SigcheckExe
$HandleExe
$ListDllsExe
```

### Что делает эта функция

Она ищет подходящий исполняемый файл в уже скачанном официальном Sysinternals Suite. Функция **ничего не устанавливает и ничего не меняет в системе** — только возвращает путь к найденной утилите.

# 7. Windows: первоначальная настройка Process Explorer

Этот раздел нужен, чтобы студент понимал, **где смотреть данные**, даже если основная фиксация выполняется командами.

## 7.1. Дерево процессов

После запуска список процессов в верхней панели должен быть представлен иерархически.

Если дерево не видно:

```text
View → Show Process Tree
```

### Что смотреть

Отступ дочерней строки вправо означает связь с родительским процессом.

## 7.2. Добавьте полезные столбцы

Откройте:

```text
View → Select Columns...
```

В зависимости от версии названия могут быть сгруппированы по вкладкам.

Полезно включить:

- PID;
- User Name;
- Command Line;
- Image Path / Path, если доступно как колонка;
- Company Name;
- Verified Signer;
- Start Time, если доступно.

Нажмите `OK`.

## 7.3. Проверка цифровых подписей

Откройте:

```text
Options → Verify Image Signatures
```

После этого Process Explorer может выполнять проверку подписей. Некоторые проверки статуса сертификатов могут требовать сетевого доступа.

> **Не включайте автоматическую отправку неизвестных файлов в VirusTotal в учебной работе.** Рабочие и персональные файлы нельзя загружать во внешние сервисы без разрешения организации.

## 7.4. Свойства процесса

Выберите процесс → двойной щелчок либо:

```text
Right click → Properties
```

Для базового анализа особенно полезна вкладка `Image`.

Там ищите:

- путь;
- command line;
- parent;
- user;
- время запуска;
- сведения об издателе/подписи.

## 7.5. Нижняя панель

Включается:

```text
View → Show Lower Pane
```

Режимы:

```text
View → Lower Pane View → Handles
```

или

```text
View → Lower Pane View → DLLs
```

Это визуальные аналоги того, что в консоли Windows мы будем проверять `handle.exe` и `listdlls.exe`.

# 8. Установка и подготовка: WSL

## 8.1. Что такое WSL

**WSL (Windows Subsystem for Linux)** — Linux-среда, запускаемая внутри Windows.

Важно понимать две среды:

```text
Windows host
   ├── Windows-процессы → Process Explorer
   └── WSL
```

# 10. Установка и подготовка: macOS

Process Explorer нативно для macOS не выпускается.

Большинство нужных средств уже есть:

```bash
ps -p $$ -o pid=,ppid=,user=,comm=
lsof -v
curl --version
codesign --help 2>&1 | head
shasum --help 2>&1 | head
```

Первая команда — не просто «проверка наличия `ps`». Она сразу показывает текущий shell-процесс: его PID, PPID, пользователя и имя команды. На macOS используется BSD-вариант `ps`, поэтому GNU-опция `ps --help` здесь специально не применяется.

Для базовой работы достаточно системных:

- `ps` — список и свойства процессов;
- `lsof` — открытые файлы и сетевые объекты;
- `codesign` — сведения о кодовой подписи;
- `shasum -a 256` — SHA-256;
- `curl` — сетевой клиент.

Установка Process Explorer через Wine в этой лабораторной **не рекомендуется**: это не является официальной нативной средой инструмента и усложняет интерпретацию результатов.

# 12. Этап 2 — создайте безопасный учебный процесс

Нам нужен процесс, происхождение которого полностью известно.

## Windows PowerShell

В текущем окне PowerShell:

```powershell
$LabProcess = Start-Process powershell.exe `
    -ArgumentList '-NoProfile','-Command','Start-Sleep -Seconds 3600' `
    -PassThru

$LabProcess.Id
```

### Что произошло

Текущий PowerShell запустил второй PowerShell, которому поручено выполнить:

```text
Start-Sleep -Seconds 3600
```

То есть дочерний процесс будет существовать до одного часа или до ручного завершения в конце лабораторной и ничего опасного не делает.

`-PassThru` возвращает объект запущенного процесса, поэтому его PID сохраняется в `$LabProcess.Id`.

## Linux / WSL — Bash или Zsh

```bash
sleep 3600 &
LAB_PID=$!
echo "$LAB_PID"
```

### Если у вас Fish

Не используйте `LAB_PID=$!` — в Fish такой синтаксис не работает.

Используйте:

```fish
sleep 3600 &
set LAB_PID $last_pid
echo $LAB_PID
```

## macOS

По умолчанию чаще используется zsh:

```bash
sleep 3600 &
LAB_PID=$!
echo "$LAB_PID"
```

### Контрольная точка

Запишите PID учебного процесса.

> **Почему процесс ждёт 3600 секунд:** один час выбран не потому, что работа должна длиться час, а чтобы процесс не завершился, пока новичок переключается между терминалом и Process Explorer. В конце практики мы явно завершим **только созданный нами учебный процесс**.

# 16. Этап 6 — цифровая подпись и происхождение файла

## Windows

Получите путь:

```powershell
$ExePath = (Get-Process -Id $LabProcess.Id).Path
$ExePath
```

Проверьте Authenticode:

```powershell
Get-AuthenticodeSignature $ExePath |
    Select-Object Status, StatusMessage,
        @{Name='Signer';Expression={$_.SignerCertificate.Subject}}
```

Если установлен Sysinternals Suite, можно получить дополнительную информацию через Sigcheck:

```powershell
& $SigcheckExe -nobanner -a -h -i $ExePath
```

`$SigcheckExe` был определён на этапе установки с учётом архитектуры и фактически найденных файлов.

### Process Explorer

Для выбранного процесса:

```text
Properties → Image
```

Посмотрите сведения об издателе и verified status.

### Linux / WSL

У Linux нет универсального Authenticode для всех исполняемых файлов. Вместо этого в базовой практике фиксируется происхождение пакета.

Ubuntu/Debian:

```bash
EXE_PATH=$(readlink -f "/proc/$LAB_PID/exe")
echo "$EXE_PATH"
dpkg -S "$EXE_PATH" 2>/dev/null || echo "Файл не найден в базе dpkg"
```

Arch:

```bash
EXE_PATH=$(readlink -f "/proc/$LAB_PID/exe")
pacman -Qo "$EXE_PATH"
```

Fedora:

```bash
EXE_PATH=$(readlink -f "/proc/$LAB_PID/exe")
rpm -qf "$EXE_PATH"
```

> Проверка принадлежности пакету — это **не то же самое**, что Windows Authenticode. Она отвечает на другой вопрос: какой пакет установил этот файл.

## macOS

Для `sleep` сначала определите имя команды и полный путь к системному бинарному файлу:

```bash
CMD_NAME=$(basename "$(ps -p "$LAB_PID" -o comm= | xargs)")
EXE_PATH=$(command -v "$CMD_NAME")
echo "$EXE_PATH"
```

### Что происходит

- `ps ... -o comm=` получает имя/путь исполняемой команды процесса;
- `basename` оставляет только имя, например `sleep`;
- `command -v` находит фактический путь команды в текущей среде, например системный каталог macOS.

Затем:

```bash
codesign -dv --verbose=4 "$EXE_PATH" 2>&1 | head -n 20
```

И дополнительная системная оценка:

```bash
spctl -a -vv "$EXE_PATH" 2>&1
```

> Результат `spctl` зависит от типа объекта и политики macOS. Если системный консольный бинарный файл не оценивается так же, как обычное приложение, зафиксируйте фактический вывод. Сам по себе неожиданный текст `spctl` **не является доказательством вредоносности**.

# 18. Этап 8 — создайте безопасный открытый файл и найдите handle/FD

## 18.1. Windows

Создайте файл:

```powershell
$LabFile = "$HOME\process_lab_note.txt"
"Process Explorer training file" | Set-Content $LabFile
```

Откройте его в текущем PowerShell и **не закрывайте пока**:

```powershell
$Stream = [System.IO.File]::Open(
    $LabFile,
    [System.IO.FileMode]::Open,
    [System.IO.FileAccess]::Read,
    [System.IO.FileShare]::ReadWrite
)
```

Теперь найдите файл через Sysinternals Handle:

> **Важно про права:** официальная документация Microsoft указывает, что консольный `Handle` требует административных прав. Если преподаватель или политика организации не разрешают повышение прав, **не обходите это ограничение** — используйте нижнюю панель Process Explorer для собственного процесса, как показано ниже.

Если повышенный PowerShell разрешён в вашей учебной среде, откройте его через **Пуск → PowerShell/Terminal → Запуск от имени администратора**. Новое окно не наследует переменные из предыдущего PowerShell, поэтому задайте путь заново:

```powershell
$Sysinternals = "$HOME\Tools\Sysinternals"
$HandleExe = Get-ChildItem $Sysinternals -Filter "handle*.exe" |
    Sort-Object Name |
    Select-Object -First 1 -ExpandProperty FullName

$HandleExe
& $HandleExe -nobanner "process_lab_note.txt"
```

Здесь `Get-ChildItem` только ищет установленный файл Handle. Мы не закрываем handles и не используем опасный параметр принудительного закрытия.

Если команда не выполняется из-за недостатка прав, это **не ошибка студента и не признак неисправности Process Explorer**. Продолжайте через GUI-способ.

# 20. Этап 10 — безопасное сетевое наблюдение

## Цель

Создать **одно** контролируемое HTTP-обращение к разрешённому учебному ресурсу и увидеть, что сетевой факт связан с конкретным процессом.

Мы не выполняем сканирование.

## 20.1. Windows

Запустите ограниченное по скорости безопасное получение страницы, чтобы у новичка было больше времени найти процесс:

```powershell
$Curl = Start-Process curl.exe `
    -ArgumentList '--limit-rate','100','--max-time','90','http://scanme.nmap.org/','-o','NUL' `
    -PassThru -NoNewWindow

$Curl.Id
```

> `--limit-rate 100` ограничивает скорость получения данных, а `--max-time 90` ограничивает максимальную длительность команды. Это сделано только для удобства наблюдения. Если публичная страница оказалась маленькой и `curl` завершился раньше, просто повторите команду и сразу перейдите к просмотру процесса. Сообщение о достижении `--max-time` также не означает атаку или неисправность — это заданное нами ограничение времени.

Подождите около двух секунд:

```powershell
Start-Sleep -Seconds 2
```

Проверьте процесс:

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=$($Curl.Id)" |
    Select-Object Name, ProcessId, ParentProcessId, CommandLine
```

Посмотрите сетевой endpoint **без фиксации числового удалённого адреса**:

```powershell
Get-NetTCPConnection -OwningProcess $Curl.Id -ErrorAction SilentlyContinue |
    Select-Object State, RemotePort, OwningProcess
```

`Tcpvcon` в этом шаге специально не запускается: его обычный вывод может показывать числовые удалённые адреса. В данной учебной работе целевой ресурс фиксируется только как доменное имя `scanme.nmap.org`, поэтому для отчёта достаточно Process Explorer и PowerShell-команды выше, из которой поле `RemoteAddress` намеренно исключено.

В отчёт зафиксируйте только:

- имя процесса;
- PID;
- факт TCP-соединения;
- удалённый сервис/порт, если виден;
- что командная строка явно содержит `scanme.nmap.org`.

### Process Explorer

Пока `curl.exe` работает:

1. найдите PID `$Curl.Id`;
2. откройте `Properties`;
3. откройте вкладку `Image` — найдите command line;
4. откройте вкладку `TCP/IP` — зафиксируйте только факт сетевого endpoint; если интерфейс показывает числовой адрес, не переписывайте и не используйте его как цель дальнейших действий;
5. не выполняйте `Close Connection`.

## 20.2. Linux / WSL — Bash/zsh

```bash
curl --limit-rate 100 --max-time 90 http://scanme.nmap.org/ -o /dev/null &
CURL_PID=$!
echo "$CURL_PID"
sleep 2
ps -o pid=,ppid=,user=,comm=,args= -p "$CURL_PID"
```

Если `ps` уже ничего не показывает, `curl` успел завершиться. Это нормально: повторите команду запуска и быстрее выполните шаг наблюдения.

Покажите, что процесс имеет открытый socket, не выводя адрес назначения:

```bash
ls -l "/proc/$CURL_PID/fd" 2>/dev/null | grep 'socket:' || true
```

Fish:

```fish
curl --limit-rate 100 --max-time 90 http://scanme.nmap.org/ -o /dev/null &
set CURL_PID $last_pid
echo $CURL_PID
sleep 2
ps -o pid=,ppid=,user=,comm=,args= -p $CURL_PID

```

## 20.3. macOS

```bash
curl --limit-rate 100 --max-time 90 http://scanme.nmap.org/ -o /dev/null &
CURL_PID=$!
sleep 2
ps -p "$CURL_PID" -o pid=,ppid=,user=,comm=,args=
```

Если процесс уже завершился, повторите запуск `curl`: маленькая публичная страница может загрузиться раньше максимальных 90 секунд.


Соединение к `scanme.nmap.org` в этом этапе **ожидаемо**, потому что вы сами только что запустили `curl` с такой командной строкой.

# 20.4. Завершите созданные учебные процессы

После того как PID/PPID, путь, command line, подпись/происхождение, хэш, handle/FD, DLL и сетевой контекст уже зафиксированы, завершите **только те процессы, которые создали сами в этой лабораторной**.

## Windows PowerShell

```powershell
if ($LabProcess -and -not $LabProcess.HasExited) {
    Stop-Process -Id $LabProcess.Id
}

if ($Curl -and -not $Curl.HasExited) {
    Stop-Process -Id $Curl.Id -ErrorAction SilentlyContinue
}

if ($Stream) {
    $Stream.Dispose()
}
```

`Stop-Process` здесь используется только по сохранённым PID наших учебных процессов. Не подставляйте PID чужих или системных процессов.

```bash

kill "$CURL_PID" 2>/dev/null || true
```

## Fish

```fish
kill $CURL_PID 2>/dev/null
```

## macOS

```bash

kill "$CURL_PID" 2>/dev/null || true
```

### Что означает `kill`

Несмотря на название, обычная команда `kill PID` в Unix-подобных системах по умолчанию отправляет процессу сигнал `TERM` — просьбу штатно завершиться. Мы используем её только для собственных специально созданных процессов.

# 24. Как правильно классифицировать наблюдение

Используйте три уровня.

## Факт

То, что непосредственно зафиксировано.

Пример:

```text
Процесс имеет PID ... и был запущен с командой Start-Sleep.
```

## Индикатор / признак

Наблюдение, которое может повышать или снижать риск.

Пример:

```text
Файл не имеет проверенной подписи.
```

Это ещё не вывод «malware».

## Гипотеза

Объяснение фактов, которое нужно проверить.

Пример:

```text
Возможно, процесс относится к сторонней программе, установленной пользователем.
```

# 25. Кейс 1 — системное имя, но необычный путь

## Термины

**Masquerading / маскировка именем** — ситуация, когда имя объекта похоже на известный системный компонент. Само совпадение имени ничего не доказывает.

**System directory / системный каталог** — каталог, где обычно находятся компоненты операционной системы.

**User profile / профиль пользователя** — каталоги, принадлежащие конкретному пользователю: документы, загрузки, AppData и др.

## Рабочая ситуация

На рабочей станции специалист замечает процесс с именем, похожим на стандартный компонент Windows. Process Explorer показывает, что файл находится не в обычном системном каталоге, а внутри пользовательской папки загрузок. В `Verified Signer` нет подтверждённого издателя. Родителем является браузер, а время старта совпадает с моментом загрузки пользователем неизвестного установщика.

Сетевое соединение в описании не зафиксировано. Никаких данных о повреждении файлов или краже информации пока нет.

# 28. Кейс 4 — PowerShell как дочерний процесс офисного приложения

## Термины

**Living-off-the-land** в защитной аналитике — использование штатных системных инструментов в необычном контексте. Сам термин описывает подход, но не означает, что любой запуск PowerShell вредоносен.

**Parent-child anomaly / необычная цепочка запуска** — связь процессов, которая не соответствует ожидаемому рабочему сценарию и требует проверки.

# 32. Что нельзя писать в итоговом выводе

Плохо:

```text
Процесс без подписи — вирус.
```

Плохо:

```text
У процесса есть соединение, значит он крадёт данные.
```

Плохо:

```text
Высокая CPU означает майнер.
```

Плохо:

```text
Process Explorer доказал, что компьютер безопасен.
```

Лучше строить вывод так:

```text
Подтверждено ...
Дополнительное внимание вызывает ...
Этот признак сам по себе не доказывает ...
Контекст показывает ...
Для окончательной оценки необходимо ...
```
